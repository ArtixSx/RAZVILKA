# RAZVILKA: исходные изменения и продолжение V2

Дата: 30.09.2026. База: `817783493f0c2784ccc70aa73868cd64e9437634` (0.19.3).

## Сначала прочитать

Это **невыпущенный набор исходных изменений**, не готовая прошивка. Изменения подготовлены по точным файлам GitHub; полный репозиторий в среду загрузить не удалось. Отдельные производственные модули и точные функции проверены изолированно. **Полная компиляция RAZVILKA и интеграция новых файлов ещё не подтверждены.** Нельзя устанавливать пакет на рабочий роутер как проверенный выпуск.

`prepare_project.py` в корне внешнего комплекта получает точный исходный commit либо использует чистую локальную копию этой ревизии, создаёт **новую** рабочую директорию, проверяет Git blob каждого изменяемого файла и единственность каждого якоря. Никакая исходная пользовательская рабочая копия не перезаписывается. После применения создаются полный source ZIP, diff и manifest. При несовпадении базы сборщик отказывает, а не делает reset/force.

Варианты запуска из распакованного внешнего комплекта:

```sh
python prepare_project.py --download --output ../RAZVILKA-research
# либо при уже скачанной чистой точной базе:
python prepare_project.py --source ../RAZVILKA-base --output ../RAZVILKA-research
```

В Windows допустимо `py -3` вместо `python`. Требуются Git и штатный Go/gofmt. `--no-gofmt` разрешён только для подготовки исходников, не заменяет проверку форматирования. Интернет нужен для `--download`, но не для локального варианта. Входной checkout с более новым HEAD или незакоммиченной работой не трогать: перенести изменения по diff/смыслу в отдельной ветке, сохранив чужую работу.

## Команда исполнителю

1. Прочитать действующие AGENTS/CLAUDE-инструкции, V2 и этот delta. Не создавать V3, Autopilot2 или второй scheduler.
2. Проверить `git status --short`, `git rev-parse HEAD`, `git diff --check`, `go version` и неизменный `go.mod` (`go 1.26.0`, `toolchain go1.26.5`). Нельзя понижать его до Go 1.23 ради локального стенда из этого архива.
3. Просмотреть `RESEARCH_CHANGES.patch`, новые файлы и `RESEARCH_BUILD_MANIFEST.json`. Сборщик сам тесты полного проекта не запускает.
4. Запустить baseline на чистом 0.19.3 и те же проверки на подготовленной копии. Минимум:

```sh
go mod verify
go test ./...
go test -race ./...
go vet ./...
sh scripts/check.sh
```

`-race` требует подходящей платформы/компилятора. В Windows без gcc не объявлять его пройденным. Установочные shell-тесты выполнять на подходящей Linux/BusyBox-среде; не направлять их на живой `/opt` без изоляции.

5. В первую очередь запустить добавленные repo-тесты пакетов config, app, dataplane, community, strategylab, netresolve. Они являются настоящими тестами этих пакетов, но в этой сессии полный project context для них недоступен. Исправить найденные несовпадения интерфейсов, не ослабляя проверки.
6. Принять изменения небольшими коммитами: registry; canary WG/AWG; typed update outcomes+batch+receipts; catalogue checkpoint; cancellation+legacy memory; документы.
7. Затем завершить реальные Xray/WG/AWG-пути и общий исполнитель V2. Все оставшиеся шаги — в `REMAINING_PLAN_RU.md`, точные сценарии — `ACCEPTANCE.json`.

## Границы внесённых изменений

- Registry унифицирует допустимые IDs. Он не означает, что каждый движок аппаратно проверен. Нужны прежние guards, capability, native validation, scope, service evidence.
- Canary проверяет сервис из адреса временного туннеля. Это **не** доказательство пути реального LAN-клиента и не разрешение Apply. Sources не стираются.
- Pending-метка обслуживания предотвращает повтор неизвестной операции новой программой, но не восстанавливает содержимое пакета сама. **Полный журнал пакета/конфигураций/зависимостей после powerloss остаётся задачей.**
- Метки используют существующие два поля Maintenance; JSON-схема не расширена. Это устраняет отказ текущего декодера, но **не доказывает совместимость семантики со старой программой при downgrade**. Старый процесс может не понимать pending. Откат приложения при незавершённой компонентной операции запрещать либо выполнять через совместимый recovery-helper; отдельно испытать.
- После unknown native precheck операция консервативно остаётся требующей проверки: нельзя утверждать отсутствие всех временных сетевых изменений по одному факту «opkg ещё не запускался». Уточнить типизацию safe precheck vs cleanup-unknown в последующей интеграции.
- Подтверждённое ручное ManagedUpdate того же компонента может снять его pending; время, перезапуск и обновление другого компонента — нет. Общий запрет всех ручных конфликтующих операций пока требуется связать с coordinator.
- Снимок GA — только публичный индекс, а не секреты, включение сервисов или доказательство доступности. Он сохраняется отдельно от исходного каталога и перечитывается с исходным временем. Для UI/API добавлен getter статуса; отображение пока нужно подключить.
- Изменения не включают новые WARP-регистрации, внешнюю отправку ключей, случайные AWG-поля, глобальное отключение IPv6/offload, новый движок DNS либо исполняемый общий catch-all. `NETWORK_POLICY_EXECUTOR_REQUIRED` не удалён.

## После каждого шага

Обновлять один журнал V2: commit, изменённые файлы, точные команды/exit codes, реальные native/HIL-результаты и оставшиеся ограничения. Статусы `source_prepared`, `unit_isolated_passed`, `integration_passed`, `native_passed`, `HIL_passed` не заменяют друг друга. Не публиковать выпуск и не обновлять роутер без отдельного разрешения владельца.
