# Общая транзакция черновиков и восстановление до запуска

Локальный этап 31 августа 2026 года, продолжение PR-1.1 после provider adapter
(`30a81fa`). Это защита сохранённых настроек, **не ремонт WARP и не активация
маршрутов**. Изменения не опубликованы и не устанавливались на роутер.

## Реализовано

- `internal/privaterestore` связывает пять типов хранилищ: config, пользовательский
  каталог, устройства, черновики обходов и копии Cloudflare. Используются реальные
  типизированные адаптеры, их проверки формата и блокировки обычных writers.
- Внутренний `RestoreOffline` работает только до загрузки кэшей и запуска API/
  фоновых задач. Все выбранные файлы захватываются в фиксированном порядке до
  подготовки изменений. Полный payload, digest, содержимое черновиков и ссылки
  сервисов проверяются до первой записи. Ссылки сверяются с точным результатом
  объединения каталога, а не только с присланным архивом.
- Импортирует желаемые маршруты, пользовательские сервисы, метаданные устройств,
  draft-файлы и копии аккаунтов. Применённые маршруты, engine order, Safe Mode,
  учётные данные UI, DNS, рабочие профили, процессы и firewall не меняются.
  Cloudflare-копии остаются `imported-unverified`.
- До записи сохраняется общий журнал before/after. Незавершённая подготовленная
  транзакция откатывается; подтверждённая проверяется и завершается. Восстановление
  сначала проверяет все записанные цели. Неизвестная внешняя правка, повреждённый
  журнал или неподходящий layout блокируют восстановление без угадывания.
- Сохранены лимиты: 4 МиБ на образ, 8 МиБ суммарно на before+after, 2 МиБ на
  отдельный engine draft. Обычный Cloudflare Store не уменьшен до размера журнала.
- Реальный `main` вызывает recovery **до config.Load, создания токена, остальных
  Store, API и фоновых задач**. `-migrate-config` проходит тот же gate; `-check`
  остаётся только чтением и не чинит журнал. Успешный `-check` поэтому не доказывает
  возможность запуска при повреждённом recovery state.
- Журнал расположен в `private-restore` рядом с config. Его OS lease удерживается
  до завершения процесса. Другой новый экземпляр с этим каталогом, включая
  `-migrate-config`, отказывает до загрузки Store. `StartRuntime` необратимо
  закрывает offline API, но не освобождает lifetime lease.
- Чистый запуск не читает и не создаёт необязательные provider/staging файлы.
  Подготовка может создать каталог журнала и постоянный `.restore.lock`; файл
  `restore.private.json` без операции импорта не создаётся.

## Границы и эксплуатация

Это **не переключение HTTP-импорта на новый журнал**. UI-импорт по-прежнему
использует прежнюю защищённую компенсацию внутри процесса; общий импорт
`ProviderSnapshots` остаётся закрытым. `RestoreOffline` пока не выставлен как
HTTP endpoint или пользовательская CLI-команда. Он предназначен для дальнейшей
интеграции и протестирован на временных файлах.

Lifetime lease исключает только экземпляры, использующие новый startup gate
и один journal root. Старые бинарники, прямые shell-записи, файловые алиасы и
процессы, не соблюдающие протокол, этим не блокируются. Per-file leases защищают
участвующих writers во время транзакции. Чтение нескольких файлов внешним
процессом не становится атомарным. После загрузки кэшей использовать offline API
нельзя; для online restore нужны Store sessions и единое владение мутациями.

Пути приходят только из доверенной конфигурации запуска, не из backup.
Пересекающиеся роли отвергаются до создания каталога. Scope связан со всем
layout и версией набора допустимых слотов. Изменение путей/набора слотов не должно
автоматически переносить прежний журнал на новые цели — нужна явная миграция.
Это относится и к сохранённому idle-журналу. Лексическая проверка путей не является
защитой от администратора, меняющего ancestor links или hardlinks.

При отказе старта нельзя удалять журнал/lock или заменять config пустым файлом.
Нужно остановить конкурирующие экземпляры, сохранить приватную копию состояния
и выяснить конфликт. Журнал содержит секретные before/after: не публиковать его
в issue, диагностических логах или GitHub. Неизвестные протокольные маркеры
автоматически не удаляются. Обычный restart не является разрешением на утрату
неподтверждённой транзакции.

## Проверено локально

- Полный `go test ./... -count=1 -timeout=90s` и `go vet ./...` на Windows.
- `privaterestore` и `cmd/razvilka` — пять повторов. Настоящие дочерние процессы
  принудительно завершены после prepare, каждой из семи целевых записей,
  в середине rollback и после завершения. `Open` восстанавливает данные до Load.
  Проверены absent/empty/incomplete drafts и исходно отсутствующий provider file.
- Во время незавершённой операции второй coordinator не запускается; обычные
  config/device/staging writers и leases каталога/provider не могут вмешаться.
  При внешней правке, другом layout, повреждённом журнале или неизвестном lock
  цели и журнал сохраняются без частичного отката.
- Проверены полное offline-применение, неизменность live/gate-полей, unrelated
  drafts, неизвестные сервисы, плохой digest/provider, отмена, занятый файл,
  общий бюджет, освобождение leases, запрет offline API после runtime/Close.
- Дочерний реальный `main` проверен для server и migration: повреждённый журнал
  или занятый lifetime lease останавливают его до создания config/credentials/
  остальных хранилищ; приватные данные не попадают в сообщение ошибки.
- Синтаксис app.js и шесть JS suites прошли. Все Go-пакеты и новые coordinator/
  startup test binaries скомпилированы для Linux arm64/mips/mipsle (softfloat).

Linux-бинарники **не запускались**. Linux/race, Entware shell regression,
аппаратная проверка, отключение питания и browser visual QA не выполнялись.
Завершение процесса не доказывает сохранность при отключении питания.
Зависимости не изменены; роутер, DNS, маршруты и GitHub не менялись.

## Следующий блок

1. Согласовать API, асинхронные задачи, discovery и Store sessions с одним online
   coordinator. Не держать только request mutex: запись может продолжаться после
   ответа HTTP или отмены клиента. Повторный запуск должен загружать уже
   восстановленные кэши; online rollback должен обновлять существующие кэши.
2. Аудит install/upgrade/rollback: общий layout для normal start и migration,
   сохранение приватного журнала и совместимость при смене версии. Скрипты этого
   этапа не менялись. До этого не выпускать данный блок как стабильную версию.
3. Подключить общий router+provider backup/restore только после этих gates;
   отдельно проверить Linux/race, сбои записи и аппаратный baseline.
