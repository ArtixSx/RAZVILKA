## Цель

В одной RAZVILKA два взаимозаменяемых способа локального обхода DPI:

| Исполнитель | Как ищет воздействие | Чем исполняет |
| --- | --- | --- |
| **По стратегиям** | Библиотека проверенных рецептов, быстрый и глубокий подбор, личные рецепты (как z2k) | `nfqws2` + Lua (стоковый nfqws2-keenetic или управляемый пакет RAZVILKA) |
| **Динамический** | Измерения проблемного соединения → проверка гипотез → типизированный план (как d2k) | Отдельный собственный процесс-пакетообработчик |

Общими остаются:
- списки сервисов, исключения, область устройств;
- DNS, внешние резервы (VLESS/WG/WARP);
- автопилот, журнал операций, восстановление;
- интерфейс.

Пользователь выбирает политику:
- **auto** — система сама выбирает подходящий исполнитель;
- **prefer** — сначала выбранный, при подтверждённой проблеме допустим другой;
- **pinned** — другой локальный исполнитель автоматически не выбирается.

Разрешение на внешний резерв — отдельный переключатель.

## Что уже есть в коде и что можно переиспользовать

- **Единственный владелец сети** — `dataplane.Manager`: Snapshot / Stage / Validate / Canary / Activate / Health / Commit / Rollback / VerifyRollback, журнал транзакций, fence и pending-владельцы. Второй исполнитель подключается как ещё один адаптер этого же Manager. Отдельный планировщик и отдельный хозяин правил не создаются.
- **Адаптер NFQWS2** (`internal/dataplane/nfqws2*.go`, `nfqws_scoped_*`) уже реализует жизненный цикл дочернего процесса, проверку собственной очереди, readback правил и откат. Это образец для второго адаптера.
- **Захват в очередь** — правила ядра «клиенты области → NFQUEUE N» с отрицательными исключениями (`nfqws_scoped_direct_selector.go`, packet compiler). Компилятор области и исключений не зависит от исполнителя; у каждого исполнителя меняется только номер очереди.
- **Подбор стратегий** — `internal/strategylab`. Хранит выбранный рецепт, совместимость с пакетом и замороженный выбор.
- **Сосуществование с z2k** — уже определяется: при работающем z2k стоковый план NFQWS2 отказывает (`EXTERNAL_NFQUEUE_OWNER`).

## Предлагаемая граница адаптера

Новый публичный API не нужен. Второй исполнитель реализует уже существующие фазы адаптера Manager и добавляет одну типизированную возможность:

```
DetectCapabilities() -> {binary sha256, abi, intercept: nfqueue, protocols: tcp/udp, families: v4/v6,
                         isolated_probe: bool, limits: {queues, rss}}
Prepare(scope, plan)     — материал без пользовательского трафика
Probe(test_scope, plan)  — только в выделенной тестовой области (свои метки/очередь)
Activate / Health / Rollback / VerifyRollback / Deactivate — как у NFQWS2
Observe()                — измерения для автопилота, без права менять политику
```

Неизвестная возможность не становится «поддерживается» автоматически.

## Кто владеет потоком и как не обработать пакет дважды

- **Один поток — один исполнитель.** Правила захвата пишет только Manager. Активному исполнителю принадлежит одна очередь, и исходный поток попадает ровно в одну очередь.
- **Защита от повторного захвата.** Пакеты, созданные исполнителем, получают его метку (как `0x40000000` у nfqws2), и правила захвата их пропускают.
- **Одновременная работа двух исполнителей над одним потоком запрещена.** Сначала один активный исполнитель на всю управляемую область. Разделение по сервисам или устройствам — позже и только с доказанным классификатором.

## Изолированная проба

- **Что проверяется.** Кандидат B проверяется на собственной очереди и метке. Трафик — только от служебного клиента или отдельной разрешённой тестовой области; домашняя сеть не переключается.
- **Защита от ложного успеха.** Проба через A не засчитывается B: к результату привязаны номер очереди, счётчики правил B и hash плана.
- **Блокировки.** Длительная проба не держит глобальную блокировку, Stop остаётся доступным.

## Переключение A → B как одна операция Manager

1. Зафиксировать намерение: политика, область, исключения, WAN, версии и рабочая конфигурация A.
2. Prepare и Probe для B в тестовой области.
3. Перед активацией заново проверить актуальность. Новое исключение, Stop, смена WAN или конфигурации отменяют устаревшее намерение.
4. Одной транзакцией: правила захвата переводятся с очереди A на очередь B, B активируется, A выводится.
5. Health для B на реальном сценарии выбранного клиента. Состояние процесса и результат приложения проверяются отдельно.
6. При отказе — откат к A, если политика не изменилась. Stop никогда не перезапускает обход.

**Цена перехода:**
- время подготовки и пробы B;
- короткий разрыв новых соединений при смене очереди;
- старые соединения не переносятся.

Бесшовность не обещается. Длительность разрыва измеряется.

## Динамический исполнитель: адаптировать или писать свой

- **d2k** (`necronicle/d2k`, проверен коммит `bc1ac5c98c9145991f55475a5c1a9d06601e2cab`):
  - лицензионного файла **на собственный код нет**;
  - есть только `THIRD_PARTY_NOTICES.md` для заимствованных из z2k данных (MIT) и OpenSSL (Apache-2.0);
  - без явной лицензии код по умолчанию «все права защищены», переносить его в RAZVILKA **нельзя**, пока автор не даст разрешение или не добавит лицензию;
  - описание архитектуры (C-движок, AF_UNIX-контроллер, TLV-планы) можно использовать только как идею.
- **z2k** (`necronicle/z2k`, MIT) — можно переиспользовать с сохранением уведомления: Lua-дополнения, пробные гипотезы (`files/fake/*.bin`), формат профилей.
- **zapret2 / nfqws2** — используется как готовый исполнитель стратегий через поставку nfqws2-keenetic (MIT-обёртка). Лицензию самого бинарника проверить отдельно перед расширением поставки.

**Рекомендация:**
1. Собственный ограниченный динамический исполнитель: отдельный процесс на C или Go, без CGO в управляющей программе.
2. Отдельно — измерительный контроллер внутри управляющей программы на Go, как внутренний работник автопилота.
3. Начать с минимального набора воздействий, который можно проверить на ARM64 NC-1812: fake, split, disorder, TTL для TCP/443 и QUIC Initial.

Параллельно имеет смысл спросить автора d2k о лицензии: прямая адаптация сэкономила бы много работы.
