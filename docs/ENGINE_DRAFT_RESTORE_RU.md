# Черновики обходов: владение записью и восстановление

Локальный этап 31 августа 2026 года, продолжение PR-1.1 после config,
пользовательского каталога и устройств. На рабочий роутер не устанавливался.

## Что исправлено

Пакетное сохранение раньше откатывало только файлы, запись которых вернула
успех. Если ошибка произошла после фактической замены очередного файла,
этот файл мог остаться новым. Теперь перечитывается и учитывается **также
файл неудавшейся записи**. Ошибка обратной записи тоже проверяется чтением:
только точные исходные байты подтверждают возврат.

Каждый слот StageRoot/engine/file.draft использует системный per-file lease
и compare-and-swap FileTarget. Экспертный редактор, простой редактор,
публичный/приватный импорт, Discard и потребление черновика старым Apply
участвуют в одном протоколе. В простом редакторе lease берётся **до**
чтения исходника, чтобы не потерять параллельную правку другого Manager.
Другой слот остаётся независимым; текущий Manager также защищён mutex.

Для набора черновиков все ID проверяются до подготовки каталогов, блокировки
берутся в стабильном порядке, снимки читаются до первой записи. При отказе
подготовки ранее захваченные leases освобождаются, файлы не меняются.
Пакет ограничен суммой before/after 8 МиБ и отдельным файлом 2 МиБ.

Добавлен StagePrivateWithRollback: после успешного сохранения последующая фаза
импорта может вернуть исходные черновики. Перед undo заново захватывается весь
набор, проверяется привязка к тому же корню и все текущие образы. Неизвестная
внешняя правка блокирует undo до первой замены; посторонние слоты не затрагиваются.
Общий приватный импорт уже получает этот guarded undo. Это ещё не durable
HTTP/startup recovery.

Результат пакетной записи секретного слота больше не содержит Content:
возвращаются Sensitive, ID и hash. Сообщения UI различают сохранённый старый
черновик, неполный откат и запись рабочего файла с неподтверждённой очисткой.
Общее сообщение неизвестного результата не обещает остановку всех записей:
config/cache stores запрещают свои последующие записи, staging кэш не имеет.

## Адаптер для журнала

- engineconfig.OpenRestoreTarget открывает только allowlisted draft slot.
  Пути live-конфигураций не принимаются из архива и не являются targets.
- Пустой, отсутствующий и незавершённый черновики — разные допустимые исходные
  образы. Undo не требует синтаксически правильного JSON/INI в старой правке.
  Новый импорт проверяет ValidatePrivateContent через Image/Images.
- Manager.BeginRestore держит Manager mutex и leases выбранных слотов.
  Targets выдаёт ограниченные интерфейсы для журнала; после Close они недоступны.
  Binding учитывает ID набора, пути и версию адаптера; Images только строит план.
- До первого journal prepare могут создаваться приватные каталоги и постоянные
  lock markers; конфигураций в них ещё нет. Пустые каталоги после отказа не
  удаляются автоматически. Неизвестный старый lock не перезаписывается.
- На POSIX StageRoot, подкаталоги и существующие draft-файлы должны быть приватными.
  Неверные права блокируют операцию, не исправляются массовым chmod.
  Root/slot/file symlinks, FIFO и не-обычные файлы отвергаются.
- Чтение черновиков ограничено через owned root/FileTarget; ошибка staged-файла
  не скрывается переходом на live. В старом readLimited также ограничено чтение
  после открытия, а не только исходный размер stat.

Никакие регистрации, DNS, службы обходов и рабочие маршруты в этом этапе не
переключались. Метод Apply держит lease своего черновика и теперь сообщает ошибку
его удаления после записи live; это не новая реализация live/dataplane ownership.
Тест Apply проверяет отказ на занятом lease **до** live-операций.

## Проверки

Полный go test ./... -count=1 -timeout=90s и go vet ./... прошли на Windows.
Engineconfig прошёл десять повторов, включая дочерние процессы с принудительным
завершением после prepare, каждой из трёх целевых записей, во время rollback и
после полного commit. Проверены byte-exact возврат отсутствующего/пустого/
незавершённого черновика, межпроцессный запрет expert/guided/discard и
независимость постороннего слота.

Fault injection использует настоящий CAS writer, а не отдельный файловый
алгоритм: отказ до/после замены, отказ/неопределённость обратной записи,
подготовка плохого каталога, отсутствие частичного undo при внешней правке.
App regression проверяет компенсацию успешной staging-фазы после последующей
ошибки и безопасное сообщение при отказе undo.

Синтаксис app.js и шесть JS suites прошли. Все Go-пакеты и engineconfig/App test
binaries собраны для Linux arm64/mips/mipsle. Linux-only проверки symlink/FIFO/
POSIX permissions только скомпилированы, локально не выполнялись. Linux/race,
Entware shell regression, browser visual QA, HIL и потеря питания не проверялись.
Синхронизация файлов/каталогов не заменяет power-loss gate всей установки.

## Cloudflare: результаты чтения кода и следующий шаг

Provider Store в этом этапе **не изменён**:

1. Его ordinary writers уже используют постоянный .import.lock и kernel lock.
   Новый adapter обязан брать эту же блокировку: отдельный .state-lock сам
   по себе не остановит существующих provider writers.
2. accounts.private.json ограничен storeLimit = 32 × 256 КиБ × 2 + 64 КиБ
   (16 МиБ + 64 КиБ). Journal сейчас допускает только 4 МиБ на Image и 8 МиБ
   на весь before/after plan. Нельзя незаметно расширить journal или уменьшить
   существующую standalone ёмкость. Для первого coordinated restore нужен
   ранний отказ oversized-плана без записи; более крупные snapshots требуют
   отдельного формата/ограниченного хранения.
3. commit сейчас использует ownedfs.WriteAtomic, но не отдельный directory sync
   после замены. Для journal target нужен durable CAS под общей writer lease,
   bounded nonblocking read и явная классификация неопределённой записи.
4. Store читает документ заново и не держит кэш аккаунтов. При запуске recovery
   должен идти до обычного использования Store; отсутствие файла допустимо
   для пустого provider, в отличие от config/catalog/devices.

Далее: provider adapter/ordinary writer coordination, общий порядок захвата
всех stores/API/background, recovery до Load и изменение общего archive API.
ProviderSnapshots в общем импорте по-прежнему запрещён. Старые бинарники,
shell/root writers, alias paths и внешние runtime не считаются участниками
нового staging-протокола. GitHub, рабочая сеть и зависимости не менялись.
