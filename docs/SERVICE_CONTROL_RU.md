# Управление сервисами и маршрутами

23 сентября 2026 года. Описание локально реализованного контракта; аппаратная
приёмка объединённой сборки и публичный выпуск подтверждаются отдельно.

«Проверить» проверяет до 64 выбранных сервисов через сохранённый применённый
способ. Если маршрута нет, отдельно проверяется прямой доступ с роутера;
это не доказательство работы обхода или пути выбранного ПК. Для точного
узла используется существующая проверка сервиса по имени и публичному IPv4,
затем проверяется собственный применённый runtime. Открытый порт не считается
успешной проверкой сервиса. Метрика времени подписывается как время проверки.

«Подобрать подключение» проверяет максимум три сохранённых узла на сервис,
не более 12 сервисов за задание. В приоритете свежий успех для этого сервиса
и сети, затем ещё не проверенные кандидаты. Повторный запуск переходит к
следующей выборке, а недавние неудачи проверяет позже. Исчерпание трёх
кандидатов не объявляет весь каталог неработоспособным. Подбор имеет общий
лимит пять минут и предлагает результат без применения. Просмотр и применение
идут через существующий node-intent с явной областью устройств. Неизвестная
область показывается как неизвестная, а не как разрешение на всю LAN.

Общий режим «Ручной» сохраняется в конфигурации и блокирует автоматическую
замену узлов и автоматическую ротацию WARP. Правила сервисов и WARP при этом
сохраняются. «Автопилот» разрешает работу уже настроенных поддержанных правил,
не создавая новых разрешений. Проверки по таймеру продолжаются в ручном режиме.
Таймер хранит список сервисов и интервал 60–86400 секунд. Его запускает общий
серверный reconciler; открытый браузер не нужен. Следующий срок сохраняется
в журнале, результаты прошлого процесса не воспроизводятся как свежий PASS.

Общий выключатель останавливает только применённые маршруты проекта через
существующую транзакцию и проверки владения адаптеров. Сохраняются полная
предыдущая применённая конфигурация, область устройств и ожидающие изменения.
Включение восстанавливает только сохранённый выбор после свежих проверок;
ошибка оставляет возможность повторить действие. Чужие процессы не
останавливаются. Без сохранённых маршрутов предлагается выбрать сервис,
автоматического применения ожидающих изменений нет.

Явное просмотренное применение при остановленном проекте включает только
маршруты этого плана и снимает остановку. Остальные сервисы остаются
остановленными, их желаемые настройки сохраняются. Применение только маршрута
сохраняет прежнюю область устройств из снимка остановки. Ошибка транзакции
возвращает весь снимок. Обычное редактирование настроек не включает маршруты.

## API

- `GET /api/v1/service-control`: `config_revision`, `mode`, `runtime_state`,
  `running`, `can_stop`, `resume_available`, `safe_mode`, `schedule`, `job`,
  `results`, `notice`. `running` требует свежего наблюдения собственных
  процессов, интерфейса и правил; запись committed сама по себе недостаточна.
  Доступность конкретных сервисов показывается отдельно.
- `PUT /api/v1/service-control`: `expected_revision`, необязательные `mode`
  и `schedule:{enabled,interval_seconds,service_ids}`,
  `confirm:"SAVE_SERVICE_CONTROL"`. Возвращает обновлённый плоский DTO.
- `POST /api/v1/service-control/jobs`: `expected_revision`,
  `idempotency_key`, `kind:"check"|"select"`, `service_ids`, необязательные
  `node_ids` (до трёх, только для select). Ответ 202 с сохранённым заданием.
  Один coordinator выдаёт допуск на сетевую операцию; повтор того же ключа
  возвращает исходное задание. Проверки уступают место восстановлению маршрутов.
- `POST /api/v1/node-checks` для выбранных подключений: `expected_revision`,
  `idempotency_key`, `node_ids` (1–64), `mode:"tcp"|"service"`; для service
  нужен `service_id`. Ответ 202 означает сохранение задания. После перезапуска
  проверяются прежние ссылки на узлы, актуальные настройки и сеть; старый PASS
  не воспроизводится. Секреты не включены в журнал очереди. Для всего каталога:
  `scope:"all-vless"`, `generation` из GET nodes, `mode:"service"`, `service_id`,
  `confirm:"CHECK_ALL_VLESS"`, revision и ключ. Сервер фиксирует все подходящие
  VLESS (до 512), независимо от страниц и фильтров. Изменение каталога до приёма
  возвращает 409; повтор уже принятого ключа возвращает прежнее задание даже
  после обновления результатов или новых импортов. Очередь проверяет по одному
  узлу, пропускает удалённые/отключённые записи и после рестарта начинает свежую
  проверку того же списка. В памяти остаются последние 64 подробных результата.
  Получение источника с последующей проверкой пока использует прежний путь,
  без этого контракта перезапуска. `GET /api/v1/node-checks/current` доступен во время
  проверки; `DELETE` требует `?job_id=N`.
- `GET /api/v1/service-control/current`: состояние из памяти, доступно во
  время задания. `DELETE` по тому же пути требует `?job_id=N`; другой номер
  даёт 409 и не отменяет новое задание. Очистка заканчивается до освобождения
  права на операцию. Задание не зависит от длительности HTTP-запроса запуска.
- `POST /api/v1/service-control/runtime`: `expected_revision`,
  `idempotency_key`, `action:"stop"|"resume"` и соответствующее подтверждение
  `STOP_OWNED_ROUTES` или `RESUME_OWNED_ROUTES`. Ответ 202 подтверждает приём
  задания; итог читается через current. Stop имеет приоритет и ждёт cleanup
  отменённой проверки. Безопасный режим не обходится.

У результата различаются `kind`, `checked_route`, `applied_route` и
`recommended_node_id`. Также возвращаются `valid_until`, `network_profile`,
`config_revision`, `stale`, `freshness_verified`, `scope_required` и `scope`.
GET control сверяет срок, сеть, конфигурацию и проверенный сервис; ответ из
памяти подтверждает только срок и выставляет `freshness_verified:false`.
Успех рекомендации не обозначает работающий применённый маршрут.

Новые кандидаты не импортируются и не включаются в разрешённые резервные
группы автоматически. Это рабочие ручные действия и таймер проверок на базе
AUTO0, а не завершение AUTO2 и последующих этапов полной автоматизации.
