# PR-1.1 — восстановление записи копий после сбоя процесса

31 августа 2026 · локальная разработка `0.18.1-dev`, без публикации и установки.

## Что изменилось

До этого блокировка записи была пустым файлом, который удалялся при обычном
завершении. После падения процесса файл оставался, и импорт или восстановление
копий больше не могли записать результат.

Теперь `.import.lock` — постоянный файл известного формата без секретов.
На время записи программа получает неблокирующую исключительную системную
блокировку его открытого дескриптора. После завершения процесса система
освобождает блокировку; следующий запрос может продолжить работу. PID, возраст
файла и предположение «процесс, наверное, умер» для этого не используются.

Это относится только к приватному хранилищу копий Cloudflare: импорт из файла,
явное копирование старого профиля и добавление копий из зашифрованного архива.
Ни регистрация аккаунта, ни работающий USQUE/WARP, ни маршруты не меняются.

## Протокол и границы

- Linux: `flock(LOCK_EX | LOCK_NB)`; Windows для разработки: `LockFileEx` с
  `EXCLUSIVE_LOCK | FAIL_IMMEDIATELY`. Неудача не включает небезопасный fallback.
  Другие ОС требуют отдельного проверенного адаптера; запись там запрещена,
  пассивные операции чтения сохраняются.
- Пока первый writer работает, второй экземпляр/процесс получает прежний
  безопасный ответ `ErrBusy` (API `409`). Внутренняя очередь одного Store
  сохраняет отмену по контексту. API-лимиты операций не изменены.
- Файл создаётся `O_EXCL` с `0600`, маркер записывается и синхронизируется под
  системной блокировкой. В следующих запросах маркер только читается с лимитом.
- Проверяются обычный тип файла, приватные POSIX-права, точный формат и
  совпадение открытого файла с закреплённым путём. На Linux финальный open
  использует `O_NOFOLLOW | O_NONBLOCK`, чтобы symlink/FIFO не стал обходом или
  зависанием между проверкой и открытием. Windows по-прежнему требует ACL.
- Lock-файл **не удаляется и не заменяется** при освобождении: иначе два
  процесса могли бы получить блокировки разных файлов под одним именем.
  Старый бинарник с протоколом `O_EXCL` также откажет в записи, а не станет
  конкурировать с новым. Чтение старого формата аккаунтов не изменено.
- Старый пустой, повреждённый или неизвестный lock не исправляется и не
  удаляется автоматически, даже если системная блокировка свободна.
  Прерывание самого первого создания маркера может оставить такой файл:
  в этом случае нужен разбор владельца, а не автоматическая очистка.
- Перед изменением заново читается и проверяется всё хранилище. Повреждённый
  JSON не обнуляется. Запись по-прежнему атомарна, повтор одинакового импорта
  возвращает прежний ID; повтор архива сохраняет существующие копии.
- Частичные `.transaction-*` не становятся рабочим состоянием и не удаляются
  общим wildcard. Их безопасный учёт/очистка после сбоя — отдельная задача;
  они могут содержать приватные данные и требуют той же защиты каталога.

Поддерживается координация сотрудничающих процессов на локальной файловой
системе. Это не защита от root, вручную удаляющего lock, и не распределённая
блокировка между устройствами на NFS/SMB. Проверка блокировки также не доказывает
сохранность при отключении питания: полный durable commit с синхронизацией
каталога, reboot/power-loss и общая транзакция router+provider ещё не завершены.

Поведение системных механизмов сверено с первичными источниками:
[Linux man-pages: flock](https://man7.org/linux/man-pages/man2/flock.2.html) и
[Microsoft: LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex).

## Проверки

- Отдельный дочерний процесс удерживает writer, затем принудительно завершается:
  до commit с синтетическим частичным временным файлом и после реального commit.
  Проверены исключение второго writer, продолжение записи, сохранение старого
  аккаунта, отсутствие дубликата уже записанного и неизменность lock-файла.
  Сбой до commit моделируется подготовленным временным файлом, не перехватом
  каждого системного вызова `WriteAtomic`.
- Восемь независимых Store одновременно добавляют разные копии: ничего не
  теряется. Отдельно проверены отмена ожидающего запроса и совместимость отказа
  со старым `O_EXCL` writer.
- Пустой, частичный, чужой, лишний/слишком большой маркер, директория,
  повреждение хранилища; проверка точных байтов/mtime/идентичности неизвестного
  lock после отказа. Preview по-прежнему не создаёт файлов.
- Набор `TestWriter*` прошёл 20 повторов на Windows, включая настоящие аварийные
  завершения дочерних процессов. POSIX-права и symlink на этом хосте пропущены;
  Linux FIFO test добавлен, но локально не выполнялся.
- Полный Go test, Go vet и четыре JS regression suites прошли локально.
- Все Go-пакеты и provider test binaries собраны для Linux arm64/mips/mipsle;
  это включает новый Linux-only FIFO test, но не его выполнение.

Перед выпуском нужны Linux/race, выполнение Linux-only тестов и аппаратная
проверка на поддержанных файловых системах Entware. Кросс-компиляция не является
таким подтверждением. Результат не следует называть исправлением подключения
WARP или гарантией доступности Telegram.
