## Новое в этой итерации

### IM01 — адрес проверен и применён согласованно

В исходном ExactNodeChecker endpoint.Pinned присваивался addresses[0]. Отдельная транспортная предварительная проверка могла успешно подключиться к другому адресу. prepareSession всё равно писал первый. Новая SelectEndpoint возвращает конкретный успешный IP; вызываемый prefilter получает ровно этот IP. Проверка public destinations и original hostname/TLS сохраняются. UDP не получает фиктивный TCP ping; остаётся реальная протокольная проверка. Перебор UDP-адресов здесь не реализован.

Проверены отказ первого/успех второго, отмена до/после, дубликаты, предел16, неправильный адрес/зона, скачок времени и реальные loopback TCP sockets. Это не native VLESS/WG.

### IM02 — отдельные диагностические измерения

Новый bounded process-local nodequality.Cache: максимум1024 последних target-observations, срок хранения24ч, без goroutine и дисковых записей. TCPConnectMS — успешная отдельная TCP-попытка; ProxyResponseMS — запрос→заголовки ответа последней точной сервисной пробы через SOCKS; TotalCheckMS — вся проверка. 0 означает <1мс, nil — не измерено. Это не ICMP, не throughput и не универсальный RTT.

Измерение связывается с node/service/network/route/probe_id/checked_at/expiry и авторитетной записью NodeStore. В DTO нет PASS/Available, IP/URL/ключей. Оно не продлевает право Apply. При ошибке RecordCheck измерение не публикуется. Центральный checkAndRecordNode обновляет этот read-model и для ручного, и для автономного пути.

**Ограничение:** схема приватного NodeStore не изменена. Legacy LatencyMS остаётся длительностью проверки. Новые timings теряются после restart и появляются с новой проверкой; долговечная versioned миграция остаётся отдельной задачей. Исторические результаты не превращаются в свежий ping.

### IM03 — карточки и независимое чтение

В node-browser показаны отдельно «TCP до сервера», «Ответ через узел», состояние конкретного сервиса и общая длительность в подробностях. Автоматические TCP-измерения доступны той же карточке; не требуется отдельное нажатие «Пинг» после service-check. Возраст/сеть/идентичность/новая проверка продолжают инвалидировать старые числа. Старый общий duration не копируется в ping.

Сбой вторичного node-autofallback API не отбрасывает успешное чтение node-checks. Ошибка401 в любом ответе по-прежнему требует повторного входа; ошибка основного чтения не скрывается. Источник новой модели — код внутри node-browser, который новый JS-тест извлекает прямо из интегрированного файла. Здесь протестирована эта модель/запросы, не весь DOM/сборка интерфейса.

### IM04 — рейтинг без штрафов за поломку проверяющего механизма

ERROR, неизвестный PARTIAL/MISROUTED и direct-leak не становятся отрицательной репутацией всех узлов и зеркал. Подтверждённое service BLOCKED оценивается только для данного сервиса, а не как «сервер мёртв». Признак attempted отделён от успеха/неуспеха, чтобы изменения репутации не сбивали порядок проверки. Повтор одного probe_id не удваивает историю; дубли одного source_id не удваивают его вес.

Legacy LatencyMS исключён из сравнения скорости. Новое число используется только с совпадающей свежей авторитетной записью. Здоровый keep сохраняет первое место. Measurement и attempted индексы строятся до сортировки; нет повторного дорогостоящего обхода истории в компараторе. Полные publisher cohorts/exploration quotas остаются V07.

### IM05 — ограниченная диагностика недоступного DIRECT-контроля

Когда проксированный egress отвечает, а прямой oracle не отвечает, допускается одна сервисная проба в оставшемся бюджете (до5сек, без запуска при остатке<2сек). Она отвечает на вопрос «сервис вообще отвечает через проверочный канал?». Available остаётсяfalse, verdict INCONCLUSIVE, egressне публикуется и успешное Evidence не переносится в авторизацию. Старый guard сохранён. Альтернативный exact-path proof для автоматического Apply в ограниченной сети **НЕ реализован**.
