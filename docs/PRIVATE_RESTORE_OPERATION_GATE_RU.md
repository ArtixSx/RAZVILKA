# Исключение параллельных операций при приватном импорте

Локальный этап 31 августа 2026, продолжение PR-1.1 после `9a7dcf2`.
Это подключённая защита текущего HTTP-импорта, **ещё не перевод HTTP на durable
journal**. Новых endpoint, регистраций, маршрутов или фоновых подписок нет.

## Что проверено в коде

- Проверки только HTTP POST/PUT недостаточно: `GET /devices` вызывает discovery
  и сохраняет метаданные. Другие GET читают несколько хранилищ для одного ответа.
- В текущих обработчиках probe/DNS goroutines ожидаются через WaitGroup до
  возврата. У фонового цикла App отдельное время жизни, не связанное с запросом.
  Завершение/отмена HTTP само по себе не доказывает завершение дочерней работы.
- Conntrack читает config, каталог и имена устройств. Он не должен читать их
  между разными фазами восстановления. Его телеметрия не входит в backup.
- Auth пишет отдельные credentials, которые этот импорт не восстанавливает.
  SSE connections читает только telemetry; держать общий допуск весь срок
  бесконечного SSE-соединения означало бы постоянно запрещать импорт.

## Реализовано

1. `internal/operationgate`: обычные операции допускаются параллельно;
   восстановление получает исключительный допуск только при отсутствии активных
   операций. Нет очереди, принудительной отмены, автоматического повторного
   импорта или освобождения занятой операции по таймеру. Закрытие идемпотентно.
2. App использует один gate для HTTP и фонового цикла. Аутентификация/Origin
   проверяются раньше допуска. Все control API, включая GET, участвуют;
   исключены static, auth и GET SSE connections. Новые исключения требуют
   проверки источников чтения/записи, а не только метода HTTP.
3. POST private-backups/import получает исключительность до чтения/decrypt/
   preview и держит её до завершения. Другие запросы при конфликте получают
   `409 RESTORE_OPERATION_BUSY`, `not_started:true`, `Retry-After: 2`, no-store.
   Уже отменённый запрос получает `408 OPERATION_CANCELED` без начала работы.
   Ответ не раскрывает приватные причины и не утверждает, что что-то откатилось.
4. Внутренний `restorePrivateDraft` тоже требует допуска и повторяет валидацию
   под ним. HTTP-контекст того же App переиспользует активное исключительное
   владение; обычный, просроченный или уже используемый для restore контекст
   не позволяет обойти gate. Уже принятая restore-подоперация сохраняет владение
   до своего завершения даже при более раннем возврате родительского handler.
5. Фоновый цикл RefreshCommitted/WARP/SmartRoute/Autopilot держит обычный допуск
   через все свои шаги и ожидаемые дочерние проверки. Если импорт уже идёт,
   раунд пропускается до следующего штатного запуска. Если раунд уже начался,
   импорт отказывает до начала, не прерывая проверку. На загруженном роутере
   пользователю может потребоваться дождаться завершения текущего раунда.
6. Main передаёт тот же gate сборщику conntrack. Допуск удерживается во время
   Collect, но не между раундами. Пауза из-за импорта не публикуется как отказ
   сети: последняя телеметрия остаётся с прежними данными/временем, не обновляется
   до нового успешного сбора. Результат Collect публикуется отдельно в telemetry.
7. UI отдельно объясняет отказ **до начала**. Пароль/архив/preview сбрасываются
   так же, как при остальных неудачных попытках; бесконтрольного автоповтора нет.
   После завершения текущей операции архив нужно снова выбрать и проверить.

## Границы

Это только исключение участвующих операций **внутри одного App**, не системная
блокировка чужих программ и не сериализация всех обычных операций друг с другом.
Старые бинарники, прямые записи через shell, отдельные Store-объекты и вызовы
нижних методов в обход admission этим не защищены. Existing per-file CAS/leases
по-прежнему необходимы. Кэши online Store пока обновляет прежняя компенсация.

HTTP-restore всё ещё не использует общий журнал из `privaterestore` и не принимает
ProviderSnapshots. Не выдавать данную блокировку за восстановление UI-импорта
после падения процесса/отключения питания. `RestoreOffline` по-прежнему запрещён
после StartRuntime; подменять им HTTP handler нельзя. Автоматического снятия
неопределённого состояния хранилища здесь не добавлено.

Не запускать новые detached writers с одним лишь унаследованным контекстом:
им нужен собственный учитываемый допуск, сохраняемый до последней записи и
cleanup. Текущий механизм вложенного владения специально ограничен restore.
Обычные фоновые процессы dataplane и ожидание завершения OS-процессов не
становятся владельцами приватных Store только из-за наличия gate.

## Локальные проверки

- Полный `go test ./... -count=1 -timeout=90s` и `go vet ./...` на Windows.
- Новые gate/App/conntrack сценарии прошли десять повторов: параллельный admission,
  двойное закрытие, отмена, блокированный body настоящего import handler,
  конфликт GET discovery/PUT/Apply/Cloudflare/другого импорта, успешный импорт
  после снятия паузы, аутентификация до gate, очистка после panic.
- Проверены просроченный контекст, запрет двух restore через один контекст,
  сохранение вложенного владения после возврата handler, ожидание фоновых probe
  goroutines после cancellation и отсутствие ложной ошибки telemetry при паузе.
- Синтаксис app.js и шесть JS suites, включая новые busy/canceled import cases.
- Все Go-пакеты и operationgate/App/conntrack test binaries собраны для Linux
  arm64/mips/mipsle (softfloat), **не запускались**.

Linux/race, Entware shell, роутер, power-loss и browser visual QA не проверялись.
Зависимости и версия не изменены. Push/release и изменения рабочей сети не делались.

## Следующий шаг

Session-backed online coordinator: перед записью захватить Store sessions и
их файловые leases, сверить привязки с lifetime coordinator, построить общий
план, исполнить журнал и согласованно обновить кэши. При неопределённом исходе
не разрешать дальнейшее применение/фоновую запись без recovery. Отдельно
проверить crash между фазами и состояние после следующего старта. Аудит
install/upgrade/rollback и переносимости journal остаётся обязательным до релиза.
В том же аудите проверить health/supervisor: `/api/v1/status` тоже участвует в
gate и во время импорта может временно вернуть 409. Занятость нельзя выдавать
за поломку обхода или использовать для немедленного перезапуска. В текущем init
start уже имеет ограниченный повтор health, отдельного нового watchdog нет.
