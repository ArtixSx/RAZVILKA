# Каталог и устройства: защищённая запись и адаптеры восстановления

Локальный этап 31 августа 2026 года, продолжение PR-1.1 после
[адаптера конфигурации](CONFIG_RESTORE_ADAPTER_RU.md).

## Реальные изменения

Обычные записи пользовательского каталога и реестра устройств теперь используют
тот же FileTarget, что и config: постоянный per-file OS lease, bounded read
до 4 МиБ, сравнение точных исходных байтов и атомарную замену с правами 0600.
На Linux синхронизируются файл и каталог. Два новых Manager/процесса не могут
молча затереть изменения друг друга. Создание, изменение, удаление, импорт,
ReplaceAll, компенсации импорта и сохранение discovery участвуют в протоколе.

При ошибке после возможной записи результат перечитывается под блокировкой.
Только точное совпадение с исходным файлом означает подтверждённый отказ без
изменений. Иначе запись из старого кэша блокируется до разбора/перезагрузки.
Это не автоматический повтор или автоматический перезапуск службы.

Добавлены customservices/devices.OpenRestoreTarget и Manager.BeginRestore:

- можно открыть существующие файлы до загрузки Manager и фонового обнаружения;
- проверяется тип/схема/лимит; удаление реестра через адаптер не допускается;
- Binding учитывает тип, схему и закреплённый путь, а не значения из архива;
- сессия удерживает mutex Manager и системную блокировку файла;
- MergeImage строит кандидат теми же проверками и объединением, что обычный
  импорт, без записи; несвязанные записи сохраняются;
- после завершения файл перечитывается под блокировкой и кэш согласуется с ним;
- ошибка перечитывания блокирует последующие записи старого кэша.

В устройствах используется единая проверка имён, групп и обнаруженных метаданных
при загрузке/записи. Некорректный или слишком большой файл не сбрасывается
молча в пустой. Старые недопустимые метаданные могут потребовать разбора.
Валидация общего архива, ссылок между хранилищами и назначений сервисов остаётся
обязанностью будущего координатора, не этих файловых адаптеров.

## Обнаружение устройств

Раньше List игнорировал ошибку записи и сохранял новый снимок в памяти как будто
он записан. Теперь ListWithStatus возвращает наблюдения и отдельный результат
сохранения. При отказе новые наблюдения можно показать временно, но подтверждённый
кэш метаданных остаётся прежним; следующий discovery повторно пытается сохранить
изменения. Неопределённый результат блокирует запись и не скрывается даже при
пустом обнаружении. Переполнение лимита 512 устройств не рассогласует диск/кэш.

При восстановлении точный rollback/no-op сохраняет прежние in-memory discovery
поля. Если постоянные метаданные изменились, реестр загружается offline:
сохранённая запись не является доказательством подключения. Следующее обнаружение
подтверждает статус заново. Регистрации, DNS и рабочие маршруты не меняются.

Панель запрашивает /api/v1/devices?view=status и показывает текстовое предупреждение
о неподтверждённом сохранении, в том числе при пустом списке. Старый запрос без
параметра сохраняет array-контракт для клиентов. UI принимает и старый array-ответ
при обновлении сервера. Технические причины/пути в предупреждение не выводятся.

## Проверки

- Устаревшие Manager не могут писать ни обычными методами, ни через restore;
  undo импорта отказывается затирать изменения другого Manager.
- Занятые сессии отклоняют вторую сессию/запись другого Manager.
- MergeImage не пишет файл; commit/rollback согласует кэш с диском.
- Неверные/отсутствующие/слишком большие образы, чужая схема, занятая запись,
  отменённая сессия, закрытая сессия и ошибка reread проверены.
- Неопределённая запись до/после замены, discovery retry и переполнение лимита.
- Настоящие дочерние процессы завершаются после prepare, записи config,
  каталога, устройств, посреди rollback и после завершённого commit.
  Новый процесс использует три production target до загрузки кэшей:
  неподтверждённые файлы возвращаются байт-в-байт, завершённый результат сохраняется.
  Applied YouTube и Safe Mode остаются неизменны. Все три OS lease проверены
  записью из другого процесса. Неизвестное внешнее состояние блокирует recovery
  без изменения остальных целей.
- Полный go test ./... -count=1 -timeout=90s и go vet ./... прошли на Windows.
  Каталог/устройства прошли 10 повторов; новый App recovery/API-набор — 3 повтора.
  Синтаксис app.js и шесть JS suites, включая новый warning UI, прошли.
- Все Go-пакеты и тестовые бинарники customservices/devices/App собраны для
  Linux arm64/mips/mipsle. Это cross-build, не выполнение Linux-тестов.

## Не завершено и продолжение

Журнал ещё НЕ подключён к общему HTTP-импорту или main/startup.
Интеграционный тест трёх реестров — проверка адаптеров, не включение production
восстановления. Следующий этап: engine staging/provider, общий порядок захвата
и исключение всех конкурирующих writers, затем startup recovery перед Load/API/
background. ProviderSnapshots в общем импорте остаётся запрещённым.

Старые бинарники, shell-редакторы/root и alias-пути не участвуют в lease-протоколе.
Windows проверки подтверждают process-crash сценарии, не сохранность при потере
питания. Linux/race, Entware shell regression, browser visual QA, роутер/HIL и
power-loss в этом этапе не выполнялись. Зависимости, GitHub и рабочая сеть не
изменялись. Следующую стабильную публикацию делать после общей проверки, не для
одних этих локальных изменений.
