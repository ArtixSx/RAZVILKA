# RAZVILKA: единый план завершения

**Документ управления дальнейшей разработкой, а не отчёт о выполненных функциях.** Проверенная база — 0.18.10 / c3722365. Наследует план 20 сентября (PR-00…14), дополнение по каталогу, Stage 1/2 и настоящую перепроверку. При расхождении с исторической формулировкой использовать актуальный код и эту сверку; не откатывать новые исправления.

## Цель

Человек один раз выбирает нужные сервисы, устройства, разрешённые источники/транспорты и виды обслуживания. Программа сама подготавливает и поддерживает рабочий доступ. Проблема одного источника, узла, проверяющего механизма или визуального компонента не лишает пользователя управления всей панелью. Ошибка внешней сети не превращает всё в «удалено», а отсутствие результата — в «работает».

Сохранить Go и рабочие компоненты. Нет оснований пересобирать проект на другом языке вместо завершения сценариев управления. Все сетевые изменения — через один существующий coordinator и транзакцию, не отдельный процесс в каждом разделе.

## U0. Приёмка общего патча и базовой среды

**Сейчас подготовлено:** объединение Stage 1/2, точечные исправления UI/сборки/проверок и чистый кандидат парсера каталога. Подробно AUDIT_FIXES и TEST_REPORT.

В Codex: новая ветка от актуального дерева, сохранённый diff, правильный Go toolchain. Полный baseline scripts/check.sh, затем preflight и перенос общего патча, полный regression. Обновить только устаревшие тесты композиции интерфейса, не удалять проверки авторизации, proof, происхождения, возврата маршрутов и сохранения пользовательских данных. Шесть основных разделов заменяют семь намеренно; число старых DOM anchors не должно навсегда определять продукт.

**Выход:** настоящий браузер с реальным HTTP backend открывает сервисы, проверка остаётся в карточке, возвращаются актуальные route/scope/control, ошибка одного renderer не удерживает общий UI busy. Единая версия frontend/backend и один воспроизводимый CSS. Полный CI, точные исходники и результаты явно записаны.

## U1. Панель, которая остаётся управляемой

**Код:** internal/app/operations.go, app.go, operationgate, snapshot models, cmd/razvilka/web/app.js и UI модели.

Сохранить быструю memory-only доступность отдельно от route health. Добавить версионированный read-model: типизированные DTO состояния панели/сервисов/задач/источников. Публиковать неизменяемые снимки после завершённых переходов с revision, generated_at, data_age и ограниченной свежестью. Чтение интерфейса не делает opkg, netlink sweep, DNS-запросы и файловые транзакции. Защищённый snapshot доступен только после общей аутентификации; после logout старые ответы и приватные поля очищаются.

Не снимать Gate на период незавершённого cleanup/restore. Не разрешать все GET: часть нынешних чтений имеет побочные записи. Рендер не получает право менять сеть. Для недоступного Store показывать сохранённую пригодную презентацию, а не вычислять новый план на полуприменённом состоянии.

Длинные вспомогательные загрузки вывести из эксклюзивной сетевой секции. Делить операцию: bounded read/prepare вне неё → admission → сверка config/network/ownership → применение/проверка/откат → публикация. Один общий mutex не заменять набором несогласованных locks. Замерять длительность и причины ожидания; deadline измеряется на том этапе, который реально занимает время.

**Приёмка:** 30–90-секундная проверка не блокирует навигацию и чтение безопасного снимка; ошибка каталога не скрывает установленные компоненты; графики и сервисы не ждут общего status; live panel/no proof видны раздельно; auth/fenced invariants не изменены.

## U2. Одна durable-очередь и простые действия

**Код:** reconciler.go, autonomy_worker.go, node_checks.go, node_bulk.go, service-control jobs, nodeRecovery, store/journal; UI callbacks.

Развивать уже существующие worker/очереди. Тип DurableJob: ID, idempotency key, вид, приоритет, service references, immutable scope/definition, желаемая revision, budget/deadline, cursor, attempts, not_before, стадия, cleanup outcome. Не сохранять приватные VLESS-ссылки и ключи в публичном job DTO.

Одинаковый idempotency key после потерянного ответа возвращает исходное задание, а не выполняет его заново. Отмена старого ID не затрагивает новое. Logout/закрытие браузера прекращает клиентский polling, но не обрывает уже принятую безопасную server transaction; отзыв разрешений на сервере останавливает продолжение на допустимой границе. После crash нельзя продолжить прежний context: сначала журнал/owned ресурсы/политика/сеть, затем новое действие.

Приоритеты: очистка и ручной Stop → ремонт потерянного пути → короткое наблюдение → обслуживание → пополнение → массовые пробы. Aging и квоты не дают фону голодать, а ошибки контрольной сети не заставляют бесконечно выполнять пустой recovery.

Единый desired state на сервис и один владелец: manual pin, индивидуальная policy либо общая autonomy. Нельзя одновременно держать legacy fallback и autonomy для одного сервиса. Разрешённые изменения частоты/резерва сохраняются простой формой без полного мастера; scope/source/transport expansion требует осмысленного согласования один раз. Серверные CAS и anti-stale проверки остаются.

**Приёмка:** двойной клик, два окна, потерянный POST-ответ, restart в каждой фазе, снятие/возврат разрешения, cancel во время cleanup, ручная настройка одновременно с автоподбором, изоляция черновиков разных сервисов.

приоритеты — `LAN_EXCLUSIONS_RU.md`, LE-001…LE-040.

Разделять область устройств и полноту трафика: `lan_except` не значит весь
интернет через VPN. Прежние индивидуальные scope не расширять миграцией.
Исключения применять одинаково к NFQWS2, proxy/TUN и per-client DNS; ручные
правила не затирать обновлением. Исчезновение native policy не делает scope
всеобщим. Обновление DNS/WARP не авторизует смену LAN/traffic режима.

Сформировать модель при U1/U2, исполнение — вместе с D1; затем регрессия U3/U5/U6/U7.
В существующей навигации показать отдельные Устройства/Исключения, не новый
конкурирующий раздел автоматики. all-except — отдельная возможность с проверкой
нагрузки/согласия, не обязательный default слабого роутера.

**Выход:** реальные два клиента с разными режимами, включая IPv6/DNS; российский
сайт по базовому пути, выбранный иностранный через работающий обход; shared IP
не расширяет direct; перезапуск/обновление/неисправный источник не теряют исключения.
Все новые LE-сценарии запланированы, существующие прогоны их не подтверждают.

## D1. DNS и Smart DNS — ранний сквозной этап

**Приоритет изменён уточнением 2026-09-22.** DNS — не только служебный ремонт и не
последняя вкладка лаборатории. Обычный resolver является частью каждого проверяемого
пути, а разрешённый Smart DNS gateway — отдельным кандидатом доступа. Полный контракт:
`DNS_SMARTDNS_PRIORITY_RU.md`; приёмка: `DNS_ACCEPTANCE.json` (24 planned-сценария).

После минимальных U1/U2 довести одну комбинацию DNS+маршрут до точной проверки,
клиентской области, транзакционного применения и восстановления. Чистую модель и
интеграционные проверки разрабатывать параллельно с U3; не ждать новых движков.
Сохранить рабочий путь и ограниченный shortlist вместо универсального DNS-first
перебора и всех DNS×узлы×стратегии. Не менять DNS всего роутера, не выключать проверки
и не переводить `AllowedForAutoPilot` в true без готового исполнителя и приёмки.
Пауза/Stop, права источников и одного владельца сетевых ресурсов сохраняются.

## U3. Реальное восстановление и резерв

**Код:** systemprobe/network_epoch*.go, forwarding_recovery.go, autonomy_worker/recovery, dataplane/nodecheck/proxy, nodestore/route_snapshot.

Закрыть event-drain: безопасные reason codes, boot/network epoch, причина переоткрытия наблюдателя, ограниченная повторная подписка, полный свежий снимок и проверка согласованности. Реальная смена WAN должна менять identity; временный разрыв наблюдения не должен давать ложный PASS или вечную ручную остановку. Не игнорировать epoch.

Разделить причины: WAN, DNS, endpoint, credential/transport, service rejection/region, HTTP rate limit, local process/TUN, network observation, cleanup, чужие ресурсы. Исправный удалённый узел при неисправном локальном TUN требует ремонта TUN, а не удаления узла. Ошибка общего компонента не портит репутацию каждого кандидата.

Путь: подтвердить отказ A → проверить B в текущем контексте → применить B → свежая проверка собственного фактического клиентского пути. Если Apply/postcheck B неудачен, завершить и проверить rollback, классифицировать точную причину. Только кандидатный отказ даёт временный scoped quarantine B и продолжение C. Неудачный rollback/ownership/неизвестная сеть запрещают следующий Apply. После исправленного общего runtime повторить прежний разрешённый путь, а не обязательно менять ключ.

INCONCLUSIVE не равен FAIL. Разрешены безопасные ограниченные исследования резерва, но основание переключения должно быть достаточным. Стабильный локальный путь не менять из-за ping, новой выдачи или внешнего рейтинга. Предпочтения транспортов применять не только при пустом current; NFQWS2-only pin не обходит явного запрета на VPN.

**Главный результат:** A→B-apply-fail→verified rollback→C→новый LAN HTTPS/UDP сценарий, а другой сервис и исключённый клиент не затронуты. Проверить случай, когда виноват общий движок: B не карантинить. Измерить время обнаружения, пробы, rollback, активации и первого клиентского успеха отдельно.

## U4. Каталоги и подписки без ручного перебора

Здесь три разные сущности: определения сайтов, узлы/ключи и рецепты NFQWS2. Интерфейс/хранилища/права не смешивать. Подробный контракт сервиса Geo-Aggregator — в CATALOG_SOURCES.

**Определения сайтов:** встроенная небольшая нормализованная библиотека + bounded persistent snapshots + дополнительные источники. Каталог открывается без GitHub; источник обновляется в фоне. Показать происхождение, digest, дату, состояние частей. Из preview импортировать ровно тот immutable snapshot, а не скачивать новую версию после клика. Автоматическое обновление разрешённого состава — отдельная политика, а не blanket-доверие любому новому CIDR или домену. В 128-slot registry не загружать все внешние записи: разделить browsing metadata и выбранные рабочие определения.

**Подписки узлов:** сохранить bounded snapshot выдачи и cursor, а не брать каждый раз первые 32. На неизменной выдаче найти 33-й пригодный узел, не отменяя пределы. 304 с сохранённым snapshot продолжает разрешённое сканирование, не продлевает proof. Изменился digest — корректно пересчитать курсор. Limit snapshot bytes, entries, CPU, wall time, RAM/disk и concurrency; секретные snapshots только в защищённом хранилище.

Пополнять по дефициту до выбранного числа (например основной +2 резерва), учитывать независимость server/transport/provider и не считать разные названия одного профиля разными запасами. Перебирать разрешённые источники по полезности, ошибкам и cooldown. Retry-After/jitter должны переживать restart, polling не сбрасывает штрафы. Истечение/отзыв прав не маскируются под вечный LKG, но частичная выборка не означает отзыв всех узлов вне выборки.

GC сохраняет active/pinned/group/reserve/suspended/rollback references. Публичные чужие checker-сайты не получают приватные профили. Получение источника не замыкается на умершем узле: отдельный разрешённый служебный bootstrap. Это не право выпустить защищённый пользовательский трафик напрямую.

**Приёмка:** работа без GitHub, 304 без кэша, повреждённый снимок, 429/503, outage, неполная доменная/IP часть, 33-й узел, новый D после исчерпания B, отсутствие места, reordering, revoke, duplicate names, источник удалён пользователем.

## U5. NFQWS2 с реальным автоподбором

**Код:** onboarding, nfqws_mode/starter, engineconfig, strategylab, recipehints, dataplane/nfqws2, компоненты.

Мастер завершается разрешённой установкой нужных зависимостей и применением проверенного пути, а не только staged draft. MODE_LIST/AUTO-автохостлист/автоподбор стратегии/право уйти в VPN — четыре разных понятия. MODE_ALL не включать по умолчанию. Выбор шести карточек не ограничивает сам по себе расширенный auto-hostlist. Пользовательские списки и исключения не изменять под видом установки defaults.

При повторно подтверждённом отказе: WAN/DNS/runtime → LKG → совместимые локальные/community candidates → canary → транзакция → postcheck → новая LKG либо откат. Небольшой бюджет и возможность уступить очередь более важному ремонту. Согласовать внутренний подбор стратегии и внешний выбор транспортов, чтобы они не перестраивали один маршрут одновременно.

Отдельно vendor, user, community, результаты и frozen applied version. Семантически важный порядок аргументов и Lua stages не сортировать. Проверять версии движка, features, ресурсы/blobs, TCP клиента, IP family/UDP. Не загружать произвольный shell/Lua из комментариев или доверять подписи как разрешению выполнять любой root-код. Runtime от z2k не зависит.

YouTube web, начало видео, googlevideo/CDN, QUIC; Discord web, voice/media — разные сценарии. Веб-PASS не распространяется на звонки. Общие домены и IP нескольких сервисов должны иметь references; выключение одного не удаляет ресурсы другого. Не расширять единичный сайт до всей CDN без отдельной модели охвата.

## U6. Развитие DNS, компоненты и жизненный цикл WARP/USQUE

**Начальная сквозная DNS-функция перенесена в ранний D1. Здесь её расширение, не причина отложить реализацию.**

**DNS:** заменить all-or-nothing refresh на per-domain ledger: A/AAAA/CNAME, TTL/negativeTTL, resolver/location, epoch, source, references, bounded grace. Timeout сохраняет прежний ответ только в границах grace; достоверный NXDOMAIN не замораживает остальные домены. Общий домен не удаляется под другим сервисом. Не применять смешанный private/public RRset автоматически. Адрес сайта и endpoint прокси — разные объекты.

DNS-assisted proof: выбранный resolver→точный IP→подтверждённый путь→оригинальные SNI/Host→сертификат→семантика сервиса. Не резолвить снова через системный DNS после пробы. Smart DNS меняет доверяемую инфраструктуру; обычный resolver и gateway не одно и то же. Bootstrap, loop, клиентский кэш/DoH, IPv6, NXDOMAIN и convergence должны иметь реальные тесты.

**Граф исполнения:** один источник истины для backend, sidecar, бинарников/версий/features, kernel ABI, конфигов, init/hooks и ownership. UI, install plan, readiness и dataplane читают тот же граф. Для managed USQUE SOCKS учитывать реальный sidecar; native TUN — отдельный вариант только после исполнения и приёмки. Исправление описания зависимости не равно реализации native-режима.

**USQUE/WARP/AWG:** актуальный upstream и pinned artifact выбираются при реализации, CLI/schema проверяются. Старый owned бинарник/конфиг сохраняются для rollback. H3 и H2 — разные transport identities, открытый TCP443 не доказывает H2 data path. Не отключать сертификаты/pin. Сначала ремонт endpoint/runtime старой регистрации; новые Cloudflare devices только по отдельным правам, с durable uncertain outcome и лимитами. Register, enroll/readback, generation, activate — разные стадии. Не применять к стандартному WARP-peer изменения wire-format, требующие неподдержанного серверного AWG. Отдельно допускается испытание действительно client-only совместимого подмножества на точной версии; оно не называется полной поддержкой AWG 3.1 сервером Cloudflare. Матрица полей и native-приёмка обязательны.

Mihomo/HEV: завершить native adapters после U3. Нативная проверка профиля не должна незаметно скачать чужой UI/geodata/provider. HEV — TUN→SOCKS sidecar, не новый VPN. Измерить TCP/UDP, MTU, UDP ASSOCIATE, CPU/RSS/FD на одной базе; не выдумывать поддержанный --check. Backend/sidecar/credential входит в route identity. До сравнения прежний рабочий путь остаётся default.

## U7. Автообслуживание с проверенным возвратом

В проверенной версии check/prepare уже есть, unattended installation не закончена. Не переключать один metadata-флаг в true и не вызывать общий opkg upgrade.

Manifest: происхождение издателя, подпись/digest, версия/sequence/expiry, architecture/ABI/features, schema/dependencies, revocation/rotation. Test keys разрешены только на тестовом стенде, не как production roots. Trust highwater нельзя откатить обычным backup/rollback. HTTPS+SHA обеспечивают не ту же гарантию, что подпись доверенного издателя; отразить различия.

Транзакция: discovery → metadata verify → immutable staging → offline/native validate → snapshot прежнего комплекта → activation в разрешённом окне → readback фактической версии процесса/зависимостей → runtime/client check → commit. Неудача → согласованный возврат. Условия места и хранения старого комплекта проверяются заранее. Учитываются и библиотеки opkg, hooks, права, конфиги/схемы, старые executables. При неподдержанном точном rollback automatic installation данного компонента не разрешается.

Внешний trusted supervisor/helper должен восстановить старую версию, даже когда новая панель не стартует. Не считать произвольный marker доказательством успеха. Не обновлять единственный активный путь без разрешённого резерва/окна перерыва. Reboot ядра — отдельное разрешение, не побочный эффект обновления панели. Failed artifact digest получает карантин, чтобы не повторять ту же неудачу каждую ночь.

Metadata и аварийный ремонт — круглосуточно; activation обновлений — в окне. Поддержать timezone, DST, переход через полночь, плохие часы после boot, skipped window. Не использовать прошедшее окно как разрешение на дневной перерыв. Пользовательские стратегии, ключи, разрешения и backup сохраняются.

Community стратегии: сначала download-only signed snapshots; затем opt-in публикация обезличенных результатов через отдельный приём. Никаких PAT/shared publisher secrets на роутерах. Рейтинг подсказка, а не право применения; учитывать freshness/compatibility/independence и противодействие накрутке. IP источника соединения виден приёмному серверу, не обещать абсолютную анонимность.

## U8. Выпуск только по реальным сценариям

Сначала controlled A/B/C/D и два физических клиента, а не тысячи случайных публичных ключей. Затем множество сервисов, профилей WAN, native engines. Разные цели: amd64 software lab, ARM64 hardware, MIPS/MIPSel hardware. Сборка под архитектуру не означает физическую приёмку этой архитектуры.

Снять исходное состояние сети с успешными exit codes; два одинаковых сообщения command-not-found не являются одинаковыми правилами firewall. Счётчики исключаются только из статического diff правил, но сохраняются как часть свидетельств клиентского потока. Проверить IPv4/IPv6 и UDP отдельно, безопасное совместное владение с внешними службами, запрет глобального flush на production.

24 часа, затем 72 часа: закрытый браузер; повторяемые WAN outages, смерть owned process, failure apply/rollback, DNS changes, недоступные источники, storage full, reboot и отключение питания на тестовом стенде в durable фазах. Отслеживать RSS/FD/process count/flash writes/CPU и latency стадии. Никакого SLA «восстановление за 30 секунд» до измерений.

Каждый результат имеет commit, artifact SHA, toolchain/platform, точную команду и статус уровня. Unit/component_passed не заменяет real_http_passed, native_passed, hardware_passed и soak_passed. Ошибка фиксируется; тест не отключается ради зелёного выпуска.


## R: внешнее исследование, уточняющее U/D, не второй roadmap

Результаты сайтов, первичных форумных отчётов и документации находятся в
`EXTERNAL_RESEARCH_RU.md`; подробные контракты генератора и сравнения серверов
в соседних файлах. 21 idea и 48 EXP-сценариев — запланированное продолжение.

| Этап | Что добавляет исследование |
|---|---|
| U0/U1/U2 | Fail-closed scope; отсутствие двойной регистрации; bounded события; отдельная доступность панели |
| U3/U5 | Наблюдаемость NFQWS2 при offload и firmware reset; ограниченные совместимые recipes вместо слепого применения чужих строк |
