# Внешние источники: что перенести в RAZVILKA

**Сверка 22 сентября 2026.** Это исследовательское дополнение к общему комплекту, а не новый работающий обход. Реестр первоисточников с датами, платформой и ограничениями: `EXTERNAL_SOURCES.json`. Обозначения E01…E31 ниже разрешаются именно в этом файле. Предлагаемые действия RAZVILKA не являются заявлениями, что upstream уже выполняет их или что код проекта изменён.

## 1. Главные выводы и приоритет

Сохранить общий план U0–U8 и ранний D1. Следующая цель — законченный автоматический цикл существующих обходов, а не увеличение числа вкладок. Сайты генераторов полезны разделением параметров и экспортом, форумы — набором реальных симптомов, документация — проверяемым контрактом конкретного инструмента. Это три разных вида свидетельств.

Сначала закрыть причины, которые могут делать бессмысленным любой перебор: отсутствие выбранной политики устройств, невидимость части пакетов для NFQWS2, неопределённый результат регистрации, петлю служебного подключения через сломанный туннель и перегрузку локального проверяющего механизма. Уже после этого сравнивать стратегии, MTU, DNS и транспорт. Такой порядок — инженерное предложение для RAZVILKA, не измеренный рейтинг методов.

База проекта повторно подтверждена как `c3722365` / 0.18.10 [E31]. Полного checkout, доступа к роутеру, controlled VPS и сетевых испытаний в этой сессии нет. Регистрации WARP, генерация ключей на чужих сайтах и сканирование диапазонов не выполнялись. Старые результаты тестов исходного пакета сохранены, но заново не приписываются этой работе.

## 3. WARP: улучшить жизненный цикл, а не частоту генерации

Документация Cloudflare разделяет инфраструктуру управления и туннельного трафика; сведения Cloudflare One имеют собственную продуктовую область [E01]. Поэтому предлагается реестр endpoint с назначением и совместимостью: consumer/Zero Trust, WireGuard/MASQUE-H3/MASQUE-H2, IPv4/IPv6, источник и ревизия. Недоступность регистрационного API, туннельного входа и одного сайта должна давать разные причины отказа.

Пользовательская кнопка «Подключить WARP» должна запускать серверную задачу: найти пригодную сохранённую регистрацию, проверить исполнителя, подготовить допустимый профиль, проверить его отдельно, применить и подтвердить результат. Повторное сохранение DNS/MTU/формата или экспорт не создают новый аккаунт. Только отдельное разрешение на первичную регистрацию/необходимое enrollment даёт право на соответствующий внешний запрос. Потерянный ответ сохраняется как неопределённый исход, а не как причина повторить создание устройства.

В коде генератора llimonix на ревизии `552833d7` WireGuard-ветка при генерации создаёт ключ и выполняет регистрацию. Там же community DNS принудительно переводит запрос в `siteMode=all` и очищает выбранные сервисы [E08]. Это пригодно как пример отличия одноразового генератора от контроллера. В RAZVILKA экспорт должен быть чистым преобразованием сохранённого материала, а сервисная область — отдельным неизменным ограничением. Не утверждается, что источник хранит ключи злонамеренно или что проверена его размещённая серверная часть.

Локальную генерацию WireGuard-ключей поддерживает штатный инструмент [E04]. Для проекта предлагаются защищённое хранилище, типизированные ключи, запрет передачи private key внешнему генератору по умолчанию и минимальный публичный DTO. Для регистрации передаются только необходимые конкретному API сведения; схема должна проверяться по выбранному провайдеру. Данные учётной записи и адреса из readback нельзя заменять произвольными шаблонными значениями.

Выбор входа не равен выбору страны выхода. Cloudflare consumer FAQ связывает выходной IP с приблизительным местоположением и не гарантирует ближайший центр [E03]. В предлагаемом ранжировании RAZVILKA успешность нужного сервиса важнее TCP ping. Здоровый текущий путь сохраняется, рядом поддерживаются проверенные резервные кандидаты. Несколько IP одного Anycast-пула не объявляются независимыми провайдерами.

Подробный собственный контракт генератора — `WARP_LIFECYCLE_RU.md`. Не вводить постоянные тесты сотен адресов. Первоначальный бюджет: несколько документированных кандидатов последовательно, затем cooldown; точные числа устанавливать после замеров на минимальном поддерживаемом роутере.

## 4. USQUE: HTTP/2 и режим исполнения

Upstream документирует `--http2`, отдельные H2 endpoint-поля и возможное отличие TLS pin; полное автообнаружение H2-метаданных через минимальный API не гарантировано [E06]. Для RAZVILKA это полезный альтернативный транспорт, когда подтверждённо проблемен UDP-путь. Не считать открытый TCP/443 готовым туннелем; проверять передаваемые данные и нужный сервис. Не отключать TLS/pin для положительного результата.

Контракт изменения: transport identity включает endpoint, семейство адресов, SNI/аутентификацию сервера, конфиг, исполнителя и разрешённый путь. Сначала bounded probe кандидата, затем общий Apply с повторной сверкой и откатом. Нельзя выбирать случайный WG-адрес как H2 endpoint или выдумывать IPv6 по аналогии с IPv4. Изменение протокола не обязано быть чисто локальным: необходимость enrollment должна определяться API и сохранённым состоянием, с предварительным снимком.

USQUE предлагает native TUN, обычные proxy-режимы и TCP-only L4. Native TUN создаёт интерфейс, но маршруты надо организовать отдельно; L4 не заменяет IP-туннель для UDP. Connect/disconnect hooks запускаются асинхронно, и конечное завершение процесса не покрывается обычным disconnect hook [E05].

Предлагается сравнить два исполнения на одном аккаунте и пути: текущий managed SOCKS+sidecar и native TUN под существующим координатором. Не удалять sidecar до native-проверок. L4 оставить кандидатом только для подтверждённого TCP-only сценария, не для всей сети. Поддержку H2 у L4 нельзя выводить из общего наличия --http2: проверяется именно комбинация mode/transport выбранного бинарника. Новые инструменты должны явно связываться с loopback, а не становиться открытыми прокси.

Hooks подключать как короткие события в ограниченную очередь, не как дополнительные shell-владельцы маршрутов. Номер процесса/запуска и последовательность события проверяются; запоздалый disconnect старого запуска не останавливает новый туннель. Crash/Stop очищает собственные ресурсы независимо от получения hook. Повторная серия reconnect не должна плодить зависшие helper-процессы или держать UI. Поддержку конкретной архитектуры и native binary проверять отдельно — строка «написано на Go» не заменяет такой тест.

## 5. NFQWS2: сначала видеть трафик и сохранить область

В nfqws2-keenetic документировано поведение при отсутствии именованной политики: обработка может охватить весь трафик [E12]. Для RAZVILKA нужен противоположный контракт: ненайденная/изменённая политика не расширяет область. Отложить применение с понятной причиной, сохранить ранее допустимое состояние и перепроверить платформенный объект. Это P0 независимо от полезности какой-либо стратегии.

Автор z2k описывает на определённой Keenetic/MediaTek платформе потерю видимости повторов и ответов из-за ускорения; применён ограниченный per-flow подход [E13]. Это серьёзная гипотеза для сравнения z2k и RAZVILKA, но не установленная причина на пользовательском роутере. Требуется наблюдать оба направления и повторные пакеты в контролируемом потоке, а не только наличие NFQUEUE-правила.

В эксперименте RAZVILKA сначала обнаруживает реальные возможности PPE/connskip и прошивку. Затем сравнивает видимость, результат подбора, скорость длительной передачи и нагрузку для неизменного сервиса/клиента. Глобальное отключение ускорителя и широкое правило на все порты не должны быть штатным автоматическим исправлением. При отсутствии нужной capability нет права ставить похожую команду наугад. Любая узкая льгота принадлежит RAZVILKA и имеет обратимое применение, счётчики и проверку после перезаписи таблиц прошивкой.

Режим auto-hostlist и автоподбор стратегии — разные полномочия [E12]. В продукте их следует подписать соответственно «Находить новые сайты» и «Подбирать параметры для выбранных сайтов». Вторая возможность не разрешает первую и не отменяет ручное закрепление NFQWS2-only. Пользовательские исключения и списки хранятся отдельно от поставляемых.

Рецепты из форумов — кандидаты с origin, версией, IP family, TCP/UDP и required features. Сначала сверить синтаксис по точному бинарнику и ресурсы Lua/fake, затем offline/native validation. Порядок стадий и `--new` сохраняется. Даже README может содержать исторический пример; нельзя добавлять строку в конфиг только потому, что рядом написано nfqws2. Один успешный TLS-тест не подтверждает все поддомены, CDN, браузер и медиапоток.

Предлагаемый подбор: рабочая конфигурация → локально успешная история для сопоставимой сети → ограниченный пул совместимых кандидатов → изолированная проба → общий Apply → постпроверка → сохранение. Внешний рейтинг сокращает очередь, но не заменяет локальную проверку. Не требуется отдельный сетевой демон для лаборатории.

## 6. MTU и производительность: параметры должны соответствовать симптому

Cloudflare отдельно описывает PMTUD и накладные расходы транспорта [E02], quic-go — GSO, буферы UDP и обнаружение возможностей [E26]. Для RAZVILKA необходимо разделять размер внешнего пути, внутренний MTU TUN и MSS TCP. Число из инструкции другого клиента не копируется в соседнее поле. Успех короткого ping не доказывает успешную передачу крупных UDP-датаграмм или файла.

Предлагается пассивно собирать bounded метрики во время обычной работы: CPU, память, ошибки сокетов, drops, фактический темп и задержку. При повторяемом зависании больших передач запускать ограниченный разрешённый тест размера, а не новый WARP-register. Использовать существующий PMTUD библиотеки, где он реально поддержан. Не объявлять отсутствие ICMP строгим доказательством MTU-проблемы.

На старых ядрах возможности отличаются от современного VPS. Проверка версии полезна, но недостаточна при backports. Отсутствие GSO не должно блокировать весь проект: нужен корректный обычный путь и отражённый ресурсный бюджет. Удалённая опция `gso` TUN в одном core не равна отсутствию QUIC GSO в другой библиотеке [E27,E26].

## 7. Серверная сторона: несколько проверяемых профилей, не один победитель

Для собственной серверной базы предлагается сначала сравнить TCP-путь VLESS/REALITY с совместимым клиентом и, при пригодном UDP и достаточных ресурсах, отдельный UDP-путь. XHTTP — дополнительный кандидат для собственного согласованного HTTP/CDN-тракта, а не автоматический режим для любой CDN. Требования к транспортам и REALITY проверяются по документации выбранной версии [E18,E19,E21,E22].

Сравнение включает установление соединения, длительную передачу, задержку под нагрузкой, reconnect, CPU/RAM/FD и работу целевого сервиса. Не выбирать сервер только по стране или ping. Конкретный VPS/ASN нельзя рекомендовать без измерений из нужной сети; здесь таких измерений нет. Источники сети и независимые провайдеры полезнее двух названий одного и того же выхода.

Для REALITY сверять peer-настройки и поведение fallback. Административный API панели/прокси не должен оказаться опубликованным без защиты; серверный лимит и журнал без приватных URI важнее числа галочек. Не переносить все сервисы в WARP на VPS: служебный SSH/control-path должен оставаться восстановимым. Если требуется иной выход для конкретного сервиса, маршрутизировать именно его и подтвердить источник DNS на удалённой стороне.

В Xray есть TCP congestion settings [E20]; Linux публикует доступные механизмы и ограничения [E23]. Предлагается измерять BBR/CUBIC на TCP-пути, а не выполнять универсальный sysctl-пакет. Эти изменения не являются тюнингом внутреннего QUIC-контроля Hysteria. В Hysteria bandwidth связан с Brutal; завышение пропускной способности не гарантирует ускорение [E25]. Значения буферов из серверной инструкции не распространяются на малопамятный роутер [E24].

## 8. AWG: уточнение прежнего слишком широкого запрета

Не запрещать любой AWG-клиент с WARP только по названию клиента. Надо различать стандартно-совместимую передачу с допустимыми клиентскими добавлениями и режим, который требует поддержки peer. Документация описывает разные изменения формата пакетов [E10], а сайт генератора заявляет специальный WARP-compatible subset [E09]. Заявленный subset допускается лишь как кандидат для wire/native-тестов, не как сертифицированная совместимость.

Матрица задаёт точную версию клиента, каждое изменённое поле, ожидаемый wire-format и способность удалённого узла принять его. Peer-required изменения не применяются к стандартному Cloudflare WireGuard-серверу. Такой контракт сохраняет полезную идею клиентских режимов без обещания «WARP стал полноценным AWG 3.1».

Отдельная проблема — миграция. В официальном руководстве Amnezia описана процедура переустановки с удалением старых пользователей/подключений [E11]. Это не годится как фоновое обновление RAZVILKA. Для собственного AWG-сервера нужны inventory peers, экспорт/снимок, явные последствия, координация обеих сторон и проверенный путь возврата. Где обратимость не обеспечена, автоматическая установка этого изменения запрещена по конкретной причине.

## 9. DNS и Telegram остаются отдельными проверками

Ранний этап D1 сохраняется. Smart DNS — доверенный пользователем шлюз, а не заменяемый без последствий обычный резолвер; заявления Xbox — только подсказки [E30]. Выбор community DNS не разрешает расширить список сайтов или отправить через него регистрацию/обновления. Сохранить три независимых поля: кто разрешает имя, как идёт запрос DNS и как идёт прикладной поток.

Telegram описывает дата-центры с IP/port и отдельным media_only; передача файлов имеет собственную клиентскую логику [E28,E29]. Поэтому DNS может не затронуть уже выбранный literal-IP путь, а отсутствие роста скорости не обязательно означает неисправный DNS. Для медиа нужен согласованный клиентский тест, не GET главной страницы. Не выгружать пользовательскую историю, файлы и токены в диагностический сервис.

## 10. Как внедрять без разрастания программы

Не создавать новую панель генератора, новый планировщик и отдельные runtime-владельцы. Пользователь видит «Восстанавливаем подключение», «Подбираем совместимый вариант» или конкретную причину; в подробностях доступны стадия и identity. Повторные допустимые проверки идут без модальных подтверждений. Нужны одна постоянная политика и ограниченный автоподбор, а не постоянное ручное одобрение каждой команды.

Сначала U0/U1/U2 и P0-инварианты из backlog; D1 выполнять рано. Далее WARP reuse/export и USQUE transport probe, NFQ visibility и bounded adaptation, затем comparative performance. Новый серверный транспорт не становится причиной отложить восстановление существующего. Все EXP-сценарии в `TRANSPORT_ACCEPTANCE.json` имеют статус planned: выполнение фиксировать отдельно по уровням unit, integration, native, hardware, soak.
