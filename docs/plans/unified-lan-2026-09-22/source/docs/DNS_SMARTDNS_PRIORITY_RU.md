# DNS и Smart DNS — полноценная часть автопилота RAZVILKA

**Уточнение от 22 сентября 2026. База: c3722365 / 0.18.10.**
Это изменение приоритетов и требований к реализации, а не готовый DNS-исполнитель.
В данном дополнении производственный код, прежний патч и его тесты не изменены.
Новые сетевые, браузерные и аппаратные проверки DNS здесь не запускались.

## 1. Что требуется пользователю

Пользователь ранее просил селективный Xbox DNS для отдельных сайтов, в частности
сообщал об успешном опыте с Gemini/ChatGPT, и просил сочетать DNS с NFQWS2,
WARP/USQUE и VLESS. Не подменять эту задачу глобальной сменой DNS всего роутера.
Не переводить весь трафик LAN через Smart DNS и не включать его автоматически
для служебных запросов регистрации, обновлений и загрузки подписок.

Новый результат: человек выбирает сервис и устройства, один раз разрешает
допустимых поставщиков DNS/Smart DNS и способы подключения. Дальнейшая работа
и восстановление идут на роутере без окна браузера и повторных согласований
каждого обычного DNS-ответа. Экран показывает результат и причину выбранного пути,
а не заставляет вручную перебирать IP-адреса DNS.

## 2. Проверенные основания и ограничения вывода

**Xbox DNS.** На официальной странице оператор описывает специальный шлюз для
выбранных платформ. Поэтому это Smart DNS, а не просто иной рекурсивный resolver.
Указанные на странице IPv4 111.88.96.50 и 111.88.96.51 — проверка документации,
не результат локального сетевого испытания. Поддержка конкретных сервисов,
скорость и отсутствие журналов не подтверждены этим дополнением. [S1]

**Скриншот 3x-ui.** Видны исходящие `DNS Xbox / freedom` и `warp / wireguard`.
Тег — имя настройки, не доказательство её реализации. Встроенный DNS Xray
поддерживает выбор серверов для доменов, а Freedom — исходящее соединение из
того узла, где работает Xray. Полную конфигурацию и правила ролика мы не получили.
Если это VPS, участок клиент→VPS уже может идти через прокси; его нельзя объявлять
прямым пользовательским соединением только из-за Freedom на VPS. [S2, S3]

**Разные эффекты DNS.** Выбор DNS может менять возвращаемые адреса CDN;
географически зависимые ответы/ECS документированы Google. Cloudflare отдельно
различает DNS-only и передачу трафика через WARP. Это разные механизмы. [S4, S5]

**Telegram.** API описывает IP-адреса дата-центров и признак media_only. Из этого
следует, что изменение системного DNS не обязано менять соединение приложения,
уже использующего literal IP. Веб-доступ к telegram.org не доказывает загрузку
файлов или звонки. Скриншот и описание ролика указывают на WARP для медиатрафика,
но не доказывают одинаковый эффект у любого провайдера. [S6]

**Что уже есть в RAZVILKA.** В `internal/dnscontrol/provider_metadata.go` Xbox и
ряд других Smart DNS классифицированы как `smart-dns-gateway`, но имеют `Scope=lab`,
`Experimental=true`, `AllowedForAutoPilot=false`. Автоматическая регистрация USQUE
через них запрещена отдельно. Это точная проверка кода c3722365. [R1]
Исторический DC1 уже описывал комбинации DNS+маршрут, но не завершённый live adapter.
Не создавать заново «DNS-модуль 2» и не снимать ограничение одним изменением флага. [R2]

## 3. Изменение очередности master plan

Этап **D1** выделяется из общего U6 и выполняется сразу после минимально устойчивых
U1/U2 (доступная панель, серверные задания, согласованные снимки). Разработку чистой
модели и интеграционных DNS-тестов можно вести параллельно с U3. Не ждать внедрения
Mihomo/HEV, больших публичных подписок и всех вариантов туннелей.

Закончить одну вертикаль: один выбранный веб-сервис → разрешённый DNS/Smart DNS →
точная сервисная проба → клиентская область → обратимое применение → проверка
нового клиентского соединения → автоматический ремонт/разрешённый резерв.
U3 с A/B/C не отменяется; D1 и U3 используют одну очередь и одну транзакцию.

### D1.1. Модель и исполнитель с настоящими возможностями

Расширить существующие `dnscontrol`, `routeprobe`, `dataplane`, `autonomy`.
Разделить как минимум:

- `resolver_kind`: обычный resolver, фильтрующий, Smart DNS gateway;
- `resolution_actor`: выбранный клиент/локальный resolver/локальный движок/
  управляемый удалённый сервер/неуправляемый удалённый сервер;
- `dns_query_path`: как DNS-запрос достигает resolver;
- `application_path`: куда отправляется соединение сервиса;
- `dns_policy_revision`, resolver endpoint/bootstrap, IP family и покрытие ответа;
- service/scenario/definition, device scope, WAN/boot epoch, binary/config identity.

Это проектные поля; адаптировать их к существующей модели без второй БД истины.
Сначала сверить реальные `internal/dnscontrol/*`, `internal/app/dns_service_compare.go`,
`internal/routeprobe/*`, `internal/dataplane/address_refresh.go`,
`internal/app/autonomy_worker.go`, `internal/app/dns*.go` в актуальном checkout.

Для каждой версии Xray/Sing-box отдельно подтвердить, какие настройки определяют
DNS назначения, а какие — имя самого proxy endpoint. Имена параметров из старого
DC1 не переносить без проверки exact version. Настроенный DNS в панели сам по себе
не доказывает, что прикладное соединение использовало его. [S2, S3]

### D1.2. Сравнение проверяемых комбинаций, а не чисел пинга

Проверять не голый ответ resolver, а связанную последовательность:

`разрешённый DNS → A/AAAA/CNAME/TTL → точный адрес → выбранный выход →
исходные SNI/Host + TLS → семантика сервисного сценария`.

Для лабораторной пробы не использовать pooled-соединение другого кандидата,
не выполнять незаметный системный re-resolve, проверять redirects в пределах
сценария. Сохранять фактическое покрытие адресов/семейств. Один успешный адрес
подтверждает только проверенную область, а не весь набор.

DNS-время, TCP handshake, TLS, первый байт и ограниченная загрузка — отдельные
измерения. Скорость DNS-ответа не равна скорости видео. Для медиасценариев нужен
явный byte/time budget; коммерческие API и пользовательские cookies не использовать
в автоматической пробе без отдельного разрешения.

Примеры допустимых кандидатов: тот же transport+другой обычный resolver;
Smart DNS gateway через разрешённый WAN; обычный resolver+NFQWS2;
обычный resolver+WARP/USQUE; разрешённый Smart DNS+существующий proxy.
Комбинация допустима только при реальном управлении соответствующим DNS и пути.

Не делать обязательной цепочку «любой DNS → NFQWS2 → любой VPN» для всех сервисов.
Сохранять рабочий путь. При поломке только одного сайта сначала ограниченно проверить
перспективную DNS-вариацию того же пути. При отказе самого туннеля приоритет имеет
восстановление/резерв U3. Для доменных геоограничений включать разрешённый Smart DNS
в ранний shortlist; для literal-IP сценария DNS не становится универсальным ремонтом.
Начальный бюджет: не более двух DNS-кандидатов за раунд — параметр для измерений,
не неизменный аппаратный предел. Не перебирать DNS×все узлы×все стратегии.

### D1.3. Область устройств и сетевые правила

DNS и маршрут применять одной обратимой операцией через существующего владельца.
Нужны согласованные DNS-правила, IPv4/IPv6, исключения gateway/endpoint, readback,
очистка только собственных временных ресурсов и согласованный rollback.

Не обещать «только выбранный телефон», если исполнитель Keenetic поддерживает
лишь общую доменную настройку на LAN. В этом случае использовать другой уже
разрешённый scoped executor либо вернуть конкретное ограничение, не расширяя область.
Общий домен нескольких сервисов требует refs и разрешения конфликтов. Общий gateway IP
не даёт права отправить через него все домены других клиентов.

Собственный DoH приложения, DNS-cache и старые QUIC/TCP-соединения могут ограничивать
эффект изменения. Показывать `pending_cache_convergence` или неподдержанное управление,
не выдавать поддельный PASS и не отключать IPv6/QUIC/ECH/защиту сертификата глобально.
DNSSEC-политику не ослаблять молча ради синтетического ответа Smart DNS: совместимость
и изменение доверия должны быть явно определены для выбранного исполнителя/области.

### D1.4. Автоматическое восстановление без повторных кликов

Ошибка одного resolver: ограниченный retry/backoff → заранее разрешённый DNS-кандидат
или другой путь для этого сервиса. DNS-timeout не означает мёртвый VLESS, не удаляет
резервы и не вызывает новую регистрацию WARP. Общий DNS/WAN сбой не запускает шквал
переключений всех сервисов.

Хранить per-domain ledger и ограниченный кэш последнего принятого состояния.
Истечение TTL не является разрешением держать IP бесконечно; bounded grace и отрицательные
ответы учитываются отдельно. Изменение разрешённого DNS-ответа в прежней политике
обрабатывается автоматически, без ручной галочки на каждый IP. Новые источники,
переход с обычного resolver на чужой gateway и расширение device/domain scope
требуют только предусмотренного пересмотра полномочий, а не каждой фоновой проверки.

Не менять скрытно DNS для GitHub/Entware, регистрации Cloudflare и подписок.
Для них отдельный разрешённый bootstrap path, работающий и при поломке сервисного пути.
Прежнее пожелание проверить DNS для USQUE — отдельное диагностическое задание:
существующая регистрация сохраняется; её повторное создание не является DNS-проверкой.

### D1.5. Представление в простой панели

В обычной карточке: «Подключение: автоматически». Детали результата, например
«Способ: Smart DNS · Xbox» или «Способ: NFQWS2; DNS: выбранный resolver», только
из подтверждённой комбинации. Физический WAN до gateway не подписывать как
«Без посредников». При отсутствии нового результата — «Проверяем»/«Нет свежих данных».

DNS — обычная часть подбора, не спрятанная обязательная лаборатория. Настройки
доступны из карточки сервиса и общей страницы автопилота; пользователь не обязан
знать, что такое Freedom, DNS-tag, targetStrategy или название внутреннего модуля.
Внесение постоянных разрешений выполняется один раз, повторные пробы и замена
разрешённого resolver не сопровождаются модальными подтверждениями.

## 4. Приёмка

24 сценария в `DNS_ACCEPTANCE.json` — **все planned**, не выполненные тесты.
Первый аппаратный сценарий: контрольный веб-сервис не проходит исходный путь,
разрешённый Smart DNS проходит точную пробу и применяется только выбранному клиенту;
второй клиент остаётся на прежней политике. Затем отказ gateway, восстановление,
перезагрузка, кэш и разрешённый резерв. Для Telegram media — отдельная приёмка,
не перенесённый результат проверки веб-страницы.

Успех DNS-функции не объявлять по наличию выбора провайдера в форме, резолву A-записи,
200 от unrelated URL, пингу сервера или одному позитивному community-отзыву.
Отзывы и service hints сокращают shortlist, но не заменяют локальное доказательство.
