# Предлагаемый жизненный цикл WARP и генератора

**Проектный контракт, не реализованный новый API.** Дополняет U2/U3/U6 и D1. Основание исследования: E01–E11 из `EXTERNAL_SOURCES.json`; краткие факты изложены в `EXTERNAL_RESEARCH_RU.md`. Ни одна запись ниже не подтверждает работоспособность конкретного внешнего endpoint.

## Сущности без дублирования действующих хранилищ

Расширять существующие cloudflareprovider/warp/awgprofile/NodeStore, а не вводить вторую базу аккаунтов.

| Сущность | Хранимые связи | Не подменяет |
|---|---|---|
| AccountRef | Провайдер, режим аккаунта, ссылка на credential, разрешения | Transport config или здоровье сайта |
| KeyRef | Алгоритм, public identity, private material только в защищённой области | Универсальные bytes для любого протокола |
| EnrollmentReceipt | Результат внешней операции, выделенные адреса, режим, digest, uncertain state | Результат локальной проверки |
| ExecutionSpec | Core/версия/features, транспорт, endpoint, DNS actor, MTU, sidecar | Пользовательскую область устройств |
| ScopeRef | Сервисная definition revision и точные устройства | AllowedIPs в экспортируемом формате |
| MaterializedCandidate | Неизменный профиль и его hash + ссылки на предыдущие сущности | Разрешение активировать |
| ActiveReceipt | Применённая identity, owned resources, результаты readback/postcheck | Бесконечно свежий PASS |

Ключи протоколов не конвертируются сменой названия поля. Нельзя использовать WireGuard private material как MASQUE key без соответствующего типизированного механизма. Адрес endpoint и адрес внутри туннеля также не взаимозаменяемы.

## Операции и права

**Сохранить/экспортировать:** локально сериализовать сохранённый материал в формат конкретного поддержанного core. Ноль регистрационных запросов. В экспорте отличать профиль для RAZVILKA, где маршрутами управляет координатор, от профиля для самостоятельного клиента. Там, где импорт клиентом изменит всю маршрутизацию, показать это заранее и не маркировать такой экспорт «только выбранные сервисы».

**Проверить:** получить ограниченный проверочный контекст и выполнить probe допустимого кандидата без изменения текущего маршрута. Не копировать общие process-wide настройки живого адаптера; новый ExecutionSpec должен быть отдельным снимком.

**Переподключить/сменить endpoint:** использовать пригодную сохранённую identity, сначала наблюдать WAN/DNS/runtime. Разрешённая смена адреса не создаёт новое устройство. Истёкшее доказательство требует повторной пробы, но не автоматически удаляет активный профиль.

**Register / enroll:** разрешены только в согласованных пределах. До внешнего изменяющего запроса записать job ID, стадийный receipt, попытку и лимит. На timeout отметить unknown outcome. Если API позволяет readback прежней операции — сначала readback. Если не позволяет — не выдумывать идемпотентность провайдера; предложить контролируемое восстановление. Общая очередь и backoff переживают reboot.

**Активировать:** общий transaction executor сверяет scope/network/config/credential/engine revisions, сохраняет снимок, применяет только owned изменения, читает фактическое состояние и проверяет новый путь. После ошибки сначала rollback+readback. Другой сервис и административный доступ не меняются.

**Удалить:** проверить ссылки active/reserve/suspended/rollback. Удаление локального экспорта не равно удалению регистрации на сервере. Отзыв удалённого устройства — самостоятельная операция с понятным последствием.

## Состояния

Предлагаемые состояния задачи: discovered → validating-capabilities → reuse-existing / needs-enrollment → enrolling / enrollment-uncertain → materializing → probing → prepared → applying → verifying → active. Ошибки ведут в bounded-retry, paused-by-policy, rollback или recovery-required. Нет перехода «любой timeout → register».

Неизвестное состояние регистрации, поломка DNS и отсутствие service proof различаются. UI сообщает стадию и следующую допустимую попытку. «Профиль создан» означает материализацию; «Подключение проверено» — конкретную проверку; «Работает на выбранном устройстве» — только соответствующую клиентскую проверку.

## Endpoint registry

Один runtime-кандидат содержит family, protocol (WG/H3/H2), account_mode, адрес/порт, SNI/проверяемую серверную identity, ревизию источника и срок пересмотра. Адреса из официального Cloudflare One не объявляются автоматически совместимыми с consumer API или USQUE. Успех на H3 не подтверждает H2, IPv4 не создаёт адрес IPv6.

Загрузка метаданных endpoint отделена от внешней регистрации. Проверять только ограниченный известный пул. Для HTTPS API применять существующий SSRF-safe publicfetch или соответствующий проверенный transport. Для нативного туннельного адреса — типизированная валидация диапазона/назначения и scoped bootstrap route. Нельзя автоматически выполнять весь пул адресов из произвольного пользовательского JSON как команды.

Первоначальные бюджеты для экспериментального стенда: до трёх кандидатов endpoint за задачу, последовательный запуск; до двух согласованных DNS-вариантов у перспективного кандидата. Это не гарантированные лимиты производственного роутера: окончательные значения принять по измерениям слабейшей поддержанной платформы. Повтор не обходит Retry-After, лимит API или действующий Stop.

## DNS, AllowedIPs и исключения

DNS не имеет права менять ScopeRef. Если формат/режим не может обеспечить выбранное сочетание Smart DNS и split routing, материализация сообщает несовместимость или использует заранее разрешённое другое исполнение. Она не заменяет выбор на «все сайты».

AllowedIPs у WireGuard определяет допустимые назначения peer и может участвовать в установке маршрутов конкретным клиентом. Одно значение 0.0.0.0/0 внутри контролируемого tunnel peer ещё не доказывает, что весь LAN направлен через него; фактическая область определяется policy routing/правилами. И наоборот, самостоятельный клиент при импорте такого файла может установить default route. Проверка должна учитывать конкретный исполнитель, а не только искать строку /0.

LAN-адрес панели, собственный внешний endpoint, служебный bootstrap и локальные сервисы получают необходимые собственные исключения без удаления правил прошивки. IPv6 проверяется отдельно. Не делать исключением весь CDN или весь внешний Интернет ради исправления одной петли.

## Совместимость AWG

Две независимые политики: стандартный WARP peer и собственный AWG peer согласованной версии. Клиентский WARP-compatible режим допускает только проверенное подмножество, не меняющее обязательный серверный wire-format несовместимо. Header protection, magic headers и padding нельзя разрешать одним глобальным enable_amnezia. Для каждого поля хранить required-peer-capability и доказательство на точной версии.

Опциональное добавление клиентских junk/probe-пакетов не называется повышением криптографической стойкости WARP. Случайность параметров не является доказательством успешного обхода. Сохранённый последний рабочий набор проверяется прежде нового эксперимента.

## Производительность и сохранность

Профили «роутер/ПК/телефон» — стартовые ограничения ресурса, не обещание максимальной скорости. Подбор MTU не трогает ключи. Keepalive изменяется только в рамках допустимого режима и наблюдаемой задачи восстановления после простоя. Нагрузочная проверка имеет ограничения трафика, длительности и параллельности; автоматике не разрешается постоянно скачивать большие файлы.

Политика экспорта секретов согласуется отдельно. В публичный диагностический отчёт попадают только algorithm/редакции/безопасные причины, а не profile URI, QR с ключом, регистрационный токен, сырой ответ API и содержимое пользовательского трафика. Резервная копия, export и shared community recipe имеют разные уровни приватности.

## Испытания

Обязательны: повторный экспорт без API, потерянный register response, 429 после reboot, повреждённый ключ, сохранение рабочей регистрации при плохом WAN, H2 с неверной серверной identity, смена режима с необходимым enrollment, all-sites expansion, различия самостоятельного и управляемого клиента, rollback после неожиданного изменения адресов, сохранённый доступ к панели и второй исключённый клиент.

Их конкретные условия и статусы — EXP-001…EXP-016 и смежные случаи в общей матрице. Здесь не создавались рабочие конфиги, пользовательские аккаунты или новые endpoint-пулы.
