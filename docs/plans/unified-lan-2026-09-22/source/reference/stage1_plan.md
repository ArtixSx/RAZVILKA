# RAZVILKA: простое управление и законченная автономность

Аудит привязан к `c3722365dcbcee8e1c5e5909aabbbf907e457a22` от 20 сентября 2026 года. Документ подготовлен 21 сентября. Это план продолжения действующего проекта, а не предложение заменить его другой программой.

## 1. Решение по направлению

Оставить Go и работающие сетевые компоненты. Сейчас главные задачи — завершить пользовательские сценарии, изолировать ошибки и сделать восстановление автоматическим. Переход на Rust, C++ или новый интерфейсный framework не добавит отсутствующие переходы состояний сам по себе.

Полезный следующий результат: пользователь изменяет настройку или выбирает сервис, интерфейс сразу показывает принятое действие, сервер самостоятельно выполняет разрешённые шаги, а состояние и навигация остаются доступными при отказе отдельного компонента.

Не добавлять новый независимый автопилот поверх `autonomyRound`, `Operations`, существующего reconciler и `Dataplane.Apply`. Не переносить сетевую автоматику в браузер. Не устанавливать z2k как обязательный управляющий стек. Его совместимые стратегии и архитектурные решения можно изучать/импортировать отдельно.

### Граница текущей работы

Подготовлены и компонентно проверены изменения интерфейса, одноразового согласования политики и отдельной диагностики доступности панели. Полная интеграция этого патча, полная сборка и аппаратные испытания остаются следующими обязательными действиями. Причины и точные результаты перечислены в `TEST_REPORT_RU.md`.

## 2. Что обнаружено в исходниках

### 2.1. Занятость — это не обязательно зависание

`internal/operationgate/gate.go` использует короткий mutex для допуска. `Exclusive` не ждёт бесконечно: при конфликте возвращает `ErrBusy`. Но длительная фоновая операция удерживает исключительное владение, и большинство обычных API не допускаются. `Fence` отдельно запрещает новые операции после неопределённого восстановления.

Следовательно, симптом «всё не отвечает» может иметь несколько причин: HTTP 409 из-за допуска; зависший запрос; ошибка JS-отрисовки; неисправность наблюдателя; реальная остановка процесса. Их нужно показывать отдельно, а не объединять в «проект сломан».

**Не исправлять это снятием gate со всех GET.** Часть внешне читающих обработчиков может обновлять обнаруженные устройства, кеши или инвентарь. Даже чистое чтение нескольких Store во время восстановления может дать несогласованный набор ревизий.

### 2.2. Частичная загрузка уже существовала, но сохранялись общие барьеры

В `cmd/razvilka/web/app.js` уже есть `settlePanelReads`, четыре параллельных работника, состояния загрузки разделов и сохранение последнего корректного ответа. Однако сначала ожидались `refreshNodeActivity()` и `/api/v1/status`. Ошибка/задержка на этих этапах останавливала запуск последующих чтений.

Первый пакет убирает именно оставшиеся барьеры. Аутентификация остаётся обязательной. Общий статус становится одним из независимых чтений, а сбор сведений об активности не удерживает начальную загрузку.

Это не устраняет серверный запрет чтения занятых Store. Для полной доступности информации во время применения нужен этап S2.

### 2.3. Навигация сама по себе не требует подтверждения

В `setView()` модального согласования нет. Но до переключения DOM-страниц вызывается `consoleViewChanged`, далее — несколько незащищённых от ошибок функций отображения. Ошибка такого блока могла прервать переход.

В патче сначала меняются выбранная страница и базовые элементы навигации, затем отдельно выполняется необязательная отрисовка. Ошибка фиксируется ограниченным ключом в `uiRenderIssues`; черновик не удаляется и никакая запись на сервер не отправляется.

Нельзя считать это реализацией независимых черновиков для всех редакторов: при переходе между разными файлами обходов вопрос сохранения ещё нужно решать отдельно.

### 2.4. Подтверждения имеют разный смысл

`needsApplyReview()` уже пропускает повторный диалог для небольших изменений сервисов/маршрутов без изменения устройств. Значит, вводить ещё один глобальный переключатель «не спрашивать» вместо действующей логики не нужно.

При этом `saveWizard()` требовал галочку при каждом сохранении политики. Новый чистый классификатор оставляет согласование при расширении разрешений, а для повторного сохранения и ограниченной настройки использует прежнюю согласованную политику. Неизвестное новое поле с изменившимся значением трактуется консервативно.

Общий `askConfirmation()` мог привязать два ожидания к закрытию одного диалога. В локальном сравнительном тесте исходная функция подтвердила оба ожидания, новая — только первое. Это отдельная проблема корректности, а не основание убирать защиту удаления.

### 2.5. Автоматика уже есть, но не все её остановки имеют путь восстановления

В `internal/app/autonomy_worker.go` имеются серверный цикл, проверка области разрешений, свежести сети, текущего пути, резервов и транзакционное применение. Есть `unconfirmed`, `network-unknown`, `requires-review`, `apply-refused` и другие состояния.

Остановиться без опасного изменения правильно. Незаконченный сценарий возникает там, где устранимая причина оставляет систему остановленной без собственного восстановления. Приоритеты: восстановление наблюдения сети, различение неисправного кандидата и неисправного проверяющего механизма, безопасное продолжение после подтверждённого отката.

Стартовый `runNFQWS2Starter()` намеренно не меняет транспорт на VLESS/USQUE/WARP без соответствующего режима и разрешения. Повторение прежнего теста NFQWS2 не равно обучению новым стратегиям. Эти функции должны оставаться различимыми.

## 3. Как должен выглядеть пользовательский сценарий

### Первый запуск

Один мастер: проверка возможностей роутера; выбор сервисов; выбор устройств или явно всей LAN; разрешённые источники/транспорты; окно обслуживания; один понятный итог с разрешением автоматической работы.

Сведения о том, какие внешние действия разрешены, должны быть конкретными: получать подписки, устанавливать перечисленные зависимости, проверять узлы, менять маршрут внутри выбранной области, создавать WARP-учётную запись при отдельном разрешении, обновлять компоненты в заданном окне. Разрешение «делать всё» не использовать.

После итогового согласования сервер завершает последовательность без цепочки дополнительных модальных окон. Неподдержанная архитектура, отсутствующий обязательный системный модуль или невозможность безопасно восстановить журнал показываются как конкретное препятствие, а не как просьба подтвердить ту же операцию ещё раз.

### Повседневная работа

Выбрать сервис → переключить «Включён» → увидеть «Принято / готовим / проверяем / применяем / доступ подтверждён». Пока операция выполняется, можно открыть другой раздел. Работа продолжается с закрытым браузером.

Сервис со сменившимся составом или областью требует пересогласования только тогда, когда действительно расширяются разрешения. Обновление разрешённого каталога с тем же идентификатором не должно автоматически означать согласие на произвольные новые домены и сети: нужны подписанная версия определения, классификация изменения и серверная политика.

Обычная настройка должна показывать различие между «сохранено желаемое состояние», «поставлено в очередь» и «применено к сети». Зелёный статус нельзя показывать сразу после успешного сохранения JSON.

### Матрица подтверждений

| Действие | Целевое поведение |
|---|---|
| Переход, поиск, фильтр, открытие подробностей | Сразу, без модального окна и без сетевой записи |
| Обновление отображаемых данных | Сразу, ограниченный GET, ошибка только соответствующего раздела |
| Сохранение визуальных предпочтений | Сразу; только безопасные UI-предпочтения могут храниться в браузере |
| Редактирование черновика | Сохранение отдельно от применения; видимые состояния записи и ошибки |
| Включение/выключение сервиса в согласованной области | Один явный переключатель; выполнение на сервере, без второго согласия |
| Повторная проверка разрешённого сервиса | Один запуск; ограничение нагрузки и понятный прогресс |
| Восстановление прежнего разрешённого пути | Автоматически, после актуальной проверки и в пределах бюджета |
| Новый источник, транспорт, устройство, расширение LAN | Одно согласование изменения разрешений |
| Удаление ключа, определений, резервных копий; сброс | Одно конкретное предупреждение с последствиями |
| Снятие неопределённого rollback-fence | Не скрывать; сначала подтвердить восстановление или выполнить специальную процедуру |

Stage 1 реализует только часть этой матрицы. Универсальное автосохранение и задания применения ещё не добавлены.

## 4. Архитектурные правила продолжения

### Разделить четыре состояния

1. **Желаемое:** сохранённый выбор пользователя и разрешённая политика.
2. **Выполняемое:** задание и его фаза, текущая область изменения, отмена и очистка.
3. **Применённое:** состояние, подтверждённое журналом и конкретной ревизией.
4. **Наблюдаемое:** процесс, сетевые ресурсы, фактический путь, результат сценария сервиса и время проверки.

Отдельно отображать свежесть источников и ответ самой панели. HTTP 200 availability endpoint не обновляет ни одну отметку доступности сервиса.

### Один владелец сетевых изменений

Существующий coordinator остаётся владельцем firewall, policy routing, TUN и процесса переключения. Подбор кандидатов, проверка источников и интерфейс могут работать независимо только там, где они не захватывают общие сетевые ресурсы. Нельзя запускать два независимых переключателя маршрута одного сервиса.

Единицей блокировки в следующем этапе должен быть фактически изменяемый ресурс. Но сначала нужно описать ресурсы и конфликтующие операции: простая замена `Exclusive` на `Enter` без такого описания недопустима.

### Ревизии — только существенных зависимостей

Проверить места, где изменение всего Config или общего поколения Nodes отменяет операцию, хотя выбранный узел и его разрешения не изменились. В перспективе разделить ревизии пользовательского интерфейса, определения сервиса, политики, выбранного узла и применённого сетевого плана.

Это не разрешение пропускать проверку актуальности: fingerprint должен включать все существенные зависимости, включая внешние источники, срок разрешения, сеть, состав сервиса и область устройств. Изменение постороннего UI-поля не должно требовать ручного согласования маршрута; изменение ключа выбранного узла должно отменять старое применение.

## 5. Последовательность реализации

### S1. Интеграция подготовленного патча — сделать первой

Файлы: `changes/edits.json`, `overlay/`, действующие `app.js`, `console-autonomy.js`, `operations.go`, `index.html` и их тесты.

Проверить точное применение всех замен, полный CI с требуемым Go, загрузку новых статических файлов, текущую CSP, авторизацию availability endpoint и все извлечения функций в старых JS-фикстурах. Проверить настоящую панель, а не только минимальный локальный стенд.

**Выход:** в полной программе воспроизводятся результаты локальных проверок; не сломаны редакторы, карточки, вход, Safe Mode и общий сценарий применения. Только после этого объединять изменения с основной веткой.

### S2. Чтение состояния не зависит от занятых сетевых операций

Создать ограниченную неизменяемую модель для отображения в существующем приложении. Она должна публиковаться целиком после завершения согласованного чтения/операции, иметь номер поколения, время получения и отдельное состояние свежести по разделам.

Не копировать в неё секреты, полные конфигурации, bearer tokens, пароли и приватные подписочные URL. Личные данные выдавать только в пределах существующей авторизации. Детальные секретные редакторы читаются отдельным защищённым путём, а не через общий кеш панели.

Начать с состояния приложения, перечня сервисов, установленных компонентов и текущих заданий. Запрос отображения не должен запускать `opkg`, DNS-пробу, диагностику WAN или обход диска. Если производителя снимка остановил сбой, показывать прежний снимок как устаревший, а не пустую «новую конфигурацию».

Не переиспользовать снимок отображения как основание для Apply. Предпросмотр и запись должны перечитывать требуемые зависимости и проверять ревизии.

Убрать загрузку всех тяжёлых разделов при каждом входе: сначала оболочка и активная страница, остальные данные по необходимости; ограничить суммарную параллельность всех существующих poller-ов, а не только `refreshAll`.

**Выход:** во время проверки резервов, применения, обновления и rollback-fence доступны навигация, задачи и последняя корректная информация с возрастом. Никакого ложного PASS и никакого чтения несогласованных Store.

### S3. Завершить общий контракт фоновых заданий

Продолжить существующие механизмы `node-checks`, `service-control/current`, self-update и автономного coordinator. Не добавлять параллельную систему с независимым владением сетью.

Минимальный контракт задания: идентификатор, вид, ресурсная область, желаемая ревизия, версия разрешений, фаза, число выполненных шагов, время следующего действия, структурированный код причины, возможность отмены и результат очистки. Секреты не попадают в публичное описание или URL задания.

Приём долгого действия возвращает идентификатор быстро; работа продолжается сервером. UI читает состояние отдельно и блокирует только конфликтующий управляющий элемент, а не весь экран. Повторное нажатие присоединяется к тому же заданию, если это тот же intent.

Для записей добавить idempotency, ограниченную сроком жизни и связанную с пользователем, видом операции, ревизией и digest тела. Новый запрос с прежним ключом и другим телом должен отклоняться. После перезапуска ключи незавершённых изменений должны сохранять смысл.

Потерянный ответ записи означает «результат неизвестен», а не «не выполнено». UI ищет прежнее задание/результат; не отправляет тот же Apply снова. Существующий повтор после доказанного `not_started` можно сохранить в рамках ограниченной политики и той же сессии.

Отмена во время подготовки останавливает подготовку. Отмена после сетевого изменения переводит задание в очистку/откат и не освобождает владение до подтверждения результата. Кнопка «Остановить» не должна обещать мгновенную безопасную остановку, когда ещё выполняется очистка.

**Выход:** закрытие вкладки, повторный клик, потеря ответа, рестарт панели и запрос отмены не создают дублирующие сетевые изменения и не скрывают работающую задачу.

### S4. Простые формы и желаемое состояние вместо цепочки Apply

Свести UI-политику подтверждений к единому классификатору, но проверять расширение полномочий на сервере. Предложенная форма `PolicyGrant` — логическая модель внутри существующей политики, а не обязательный новый sidecar-файл со вторым источником истины.

Для чисто визуальных настроек применять изменения сразу. Для черновиков — ограниченное автосохранение после паузы ввода или потери фокуса, с CAS и статусом «сохраняем / сохранено / ошибка». Несохранённый текст остаётся доступным при ошибке. Приватные конфигурации не отправляются в localStorage и не подменяются фоновым обновлением формы.

Для выбора сервиса использовать одну серверную запись intent и последующее задание. Быстрые изменения «вкл → выкл → вкл» должны сводиться к последней желаемой ревизии, пока предыдущая запись ещё не начала опасную фазу. Уже применённую операцию не выдавать за отменённую только потому, что изменился переключатель.

Для редакторов обходов хранить отдельные сессионные черновики по движку/файлу и их версии. Переход в другой раздел не должен спрашивать о потере данных, если данные действительно сохраняются. При реальном уничтожении несохранённого текста оставить один ясный выбор. Нельзя просто удалить предупреждение и потерять редактор.

Главные страницы: состояние сети; сервисы; подключения; обходы; настройки/события. Лаборатории, низкоуровневые стратегии и технические параметры спрятать в расширенный режим. Не начинать с нового CSS-переоформления до исправления семантики действий и отказов.

**Выход:** выбранный в мастере сервис подключается без ручного обхода нескольких вкладок; обычная запись внутри политики не требует повторных подтверждений; расширение области не происходит незаметно.

### S5. Восстановление наблюдателя и изоляция отказов

Разобрать `internal/systemprobe/network_epoch.go` и вызывающие `FreshWANProfile`/`freshNetworkProfile`. Зафиксировать точный сценарий потери `event-drain`, ошибки источника событий, переполнения/разрыва наблюдения и отмены контекста.

После потери наблюдения прежние доказательства остаются недействительными. Сам наблюдатель должен перейти в `resync`: заново открыть источник, получить согласованный снимок интерфейсов и маршрутов, повторно проверить изменения вокруг снимка, дождаться допустимой устойчивости и выдать новое поколение сети. Не присваивать новое поколение старому PASS.

Изменение только счётчиков трафика или посторонней записи не должно бесконечно сбрасывать существенный сетевой профиль. При этом изменение WAN, источника адресов, маршрута до узла или состава интерфейсов игнорировать нельзя. Разделение событий подтвердить тестами, а не строковыми исключениями «для того, чтобы работало».

В `cmd/razvilka/main.go` отделить необязательные менеджеры от жизненно необходимых компонентов безопасности и восстановления. Отказ каталога или диагностического модуля должен отключать его функциональность, а не обязательно останавливать панель. Не открывать неавторизованный «аварийный интерфейс» при ошибке чтения credentials.

Для каждого фонового работника: deadline, ограниченные повторы, возможность завершения, состояние последней ошибки, восстановление после разрыва. Panic при сетевом изменении не превращать generic recover-ом в успешный результат: нужен журнал и, при неопределённости, fence. OOM/падение процесса проверять внешним надзором init/watchdog, без неконтролируемого restart-loop.

**Выход:** исчезновение и возвращение WAN, потеря потока событий и отказ необязательного менеджера приводят к диагностируемому восстановлению без ручного перезапуска всего проекта.

### S6. Полный failover с классификацией причины

Доработать `autonomy_worker.go`, `autonomy_reserves.go`, адаптеры dataplane и журнал результата применения. Ошибка должна иметь не только текст, но и тип, целевой ресурс, фазу и подтверждение результата отката.

| Причина | Следующее действие |
|---|---|
| Подтверждённый отказ конкретного кандидата/сервиса | Проверить следующий разрешённый резерв в пределах бюджета |
| Неисправность локального общего движка | Один процесс восстановления зависимости; не помечать весь каталог неисправным |
| Неполный тест или ошибка проверяющего механизма | Восстановить проверку; не засчитывать кандидату ложный FAIL |
| Неизвестная/изменившаяся сеть | Повторное наблюдение и новый тест в новом профиле |
| Изменившееся разрешение или intent | Отменить старый план; построить допустимый новый, не переиспользовать старое согласие |
| Неопределённый откат | Заблокировать новые сетевые изменения, сохранить доступную диагностику |

Целевой сценарий: A действительно отказал; B получил свежий PASS; применение B не удалось; откат вернул подтверждённую прежнюю конфигурацию; ошибка B атрибутирована; C свежо проверен; C применяется и подтверждается клиентским трафиком. Если причина общая или rollback не завершён, переход на C запрещён до восстановления.

Счётчик переключений резервировать до изменения, учитывать неуспешные попытки, сохранять при рестарте. Использовать задержки и гистерезис, не переключать работающий узел ради небольшой разницы задержки. Проверку резерва выполнять независимо от активного пути и не считать cached PASS достаточным основанием для замены после изменения сети.

Не уходить на DIRECT незаметно. Допустимость прямого выхода и поведение при отсутствии обхода должны быть частью политики конкретного сервиса. Не выбранные устройства/сервисы не затрагиваются.

**Выход:** полный A/B/C-переход и обратные случаи, где продолжать запрещено, проходят с журналом и реальными проверками.

### S7. Адаптивный NFQWS2 под собственным управлением

Разделить два уровня: подбор стратегии внутри NFQWS2 и выбор транспорта для сервиса. На время ограниченного внутреннего подбора внешний coordinator не должен одновременно перестраивать тот же маршрут.

Профили различать по виду трафика и сценарию: TCP/TLS, QUIC, видеодоставка, голос/UDP при наличии подходящего теста. Сохранять историю успешных кандидатов с версией движка, версией набора, сетевым профилем и временем. Успех в другой сети — приоритет проверки, а не готовое доказательство.

На каждом раунде ограничить число кандидатов, объём проб и время. Сохранять последнюю рабочую стратегию. Обновление пакета не стирает пользовательские стратегии и проверенные рабочие варианты; старый формат мигрируется либо остаётся доступным для отката.

Стартовый режим «только NFQWS2» не должен молча переходить на VPN. Общий автоматический режим может переходить на разрешённый транспорт после исчерпания бюджета и подтверждённого отказа локального обхода.

Сбор и распространение стратегий сообщества — отдельный контур. Отправка результатов, города и провайдера только по согласию, без ключей и приватных профилей. Внешний пакет проверяется по происхождению, формату и совместимости; чужой Lua/скрипт не исполняется как произвольный root-код. Автоматически продвигать в рабочие только кандидаты, прошедшие локальную проверку и политику доверия.

**Выход:** отказ текущей стратегии вызывает реальный ограниченный подбор, рабочий результат переживает рестарт, неподходящий пакет не разрушает действующий профиль, z2k не нужен во время работы.

### S8. Зависимости, источники и сервисы: полный путь «выбрал — заработало»

Каждый способ доступа описать через явные возможности: архитектура/ядро, обязательные зависимости, способы перехвата, протоколы, проверка конфигурации, запуск, остановка, наблюдение и откат. Не объявлять компонент подходящим только по существованию бинарника.

Сначала довести один уже используемый путь Sing-box и один путь NFQWS2. Для USQUE выбрать и аппаратно проверить один конкретный путь передачи трафика. Нативные Mihomo/HEV и другие варианты добавлять через тот же контракт, когда базовый путь восстанавливается самостоятельно. Не запускать несколько tun2socks/TUN-адаптеров без необходимости.

Разрешённые зависимости устанавливать серверной задачей с проверкой архитектуры, ресурсов, версии, источника и результата. `opkg` обслуживать последовательно. Не изменять чужой стек, не обновлять зависимость под действующим маршрутом без подготовленного сценария миграции/отката. При неизвестном модуле ядра показать точное препятствие.

Каталог сервисов должен иметь локальную стартовую библиотеку и последнюю проверенную версию. Внешний источник обновляется в staging; обязательные домены/CIDR проверяются совместно. Пустой ответ, HTML вместо списка или частичная загрузка не заменяет рабочий каталог. Зеркало должно иметь то же ожидаемое назначение и проверяемый формат, а не просто отвечать HTTP 200.

Для подписок: единый приватный каталог узлов, дедупликация, ограниченный объём, ETag/Last-Modified где поддерживается, Retry-After, задержки, расписание и ручной запрос без бесконтрольного учащения. Рабочий узел, резерв и кандидат — разные состояния. Истёкшее разрешение источника не продлевается автоматически самим RAZVILKA.

Проверять конкретный узел для конкретного сервиса и сети. Простой ping/URLTest не даёт гарантии доступа к нужному сервису; главная страница Discord не подтверждает voice, страница YouTube не подтверждает видео, landing page ИИ-сервиса не подтверждает авторизацию и выполнение запросов.

Добавление своего сайта: валидировать домен; дать сохранить определение; применить прежнюю область при разрешённом наследовании; поставить задачу подбора; не требовать ручного переноса между каталогом, сервисами и применением. URL с учётными данными/локальные адреса должны сохранять действующие ограничения SSRF.

**Выход:** выбранный сервис с разрешённым источником и поддерживаемым роутером проходит подготовку, подбор и применение без ручных команд; отказ GitHub не стирает рабочее состояние.

### S9. Полностью автоматические обновления — отдельная законченная функция

Разделить действия: узнать версию, скачать, проверить, подготовить, установить, проверить работу, откатить. Наличие таймера проверки версии не выдавать за установку.

Разрешения и окно обслуживания задаются в мастере. Обновлять по одному совместимому компоненту, сохранять зависимости, конфигурации и возможность возврата. Проверять происхождение пакета и целостность, а не только имя файла. Не переходить со stable на preview без согласования.

Self-update должен сохранять идентификатор задания и фазу до перезапуска. После нового старта UI видит результат прежнего обновления. Неудачный запуск не должен требовать доступа к неработающей панели для отката. Надзор/rollback должны быть испытаны отдельно, в том числе при нехватке места и незавершённой остановке.

Создание WARP-учётных записей и получение профиля — не синоним запуска туннеля. Такие внешние действия должны быть разрешены явно; частые повторы при недоступности API запрещены. Копии ключей хранятся приватно и не попадают в UI-кеши или публикацию стратегий.

**Выход:** обновление в окне завершается проверкой или автоматическим откатом; таймер без установки не считается выполнением требования.

### S10. Аппаратная приёмка и ограничение объёма разработки

До следующего крупного расширения пройти чистую установку, обновление со старой версии, отказ источников, падение процесса, разрыв WAN, ошибки наблюдателя и failover. Начать с контролируемых рабочих узлов A/B/C, а не со случайного публичного каталога: иначе нельзя отделить баг проекта от отказа внешнего узла.

Для области устройств нужны два физических клиента с разными правилами. Проверка маршрута с подставленным source-адресом полезна, но не заменяет такой тест. Проверять IPv4 и IPv6, отсутствие захвата чужих маршрутов, реальный клиентский трафик и счётчики собственного пути.

Архитектуры ARM64, MIPS, MIPSel подтверждать отдельно. Факт сборки и формат ELF не заменяют запуск на целевом ядре и реальном Entware. Измерять RAM, CPU, число процессов, файловые записи, задержку панели, скорость восстановления и рост памяти/очереди при длительных отказах.

24 и 72 часа — длительность приёмочных прогонов, не обещание срока разработки. Вносить намеренные отказы в ходе прогона; «просто проработало трое суток» недостаточно.

**Критерий завершения:** выбранный сервис после предусмотренных отказов самостоятельно возвращается к разрешённому рабочему состоянию; панель остаётся управляемой; другие устройства не затронуты; неустранимая без нового решения ситуация сформулирована точно.

## 6. Правила работы с результатами

Для каждой проверки записывать commit, build provenance, версию Go/бинарников, архитектуру, прошивку, условия, ожидаемый и наблюдённый результат. Хранить обезличенный журнал, не ключи.

Статусы исходных планов не переписывать на «проверено» по факту добавления функции или зелёного unit-теста. Матрица этого пакета выделена отдельно и тоже не является перечнем успешно пройденных аппаратных тестов.

Пока S2–S6 не закрыты, новые вкладки, новые источники, новый язык и дополнительные движки имеют меньший приоритет, чем завершённый сценарий восстановления уже используемого пути.
