# Задание Codex: продолжить RAZVILKA, не начинать новый проект

Пользователь хочет простую программу: один раз разрешить область действий, выбрать сервисы, а далее не подтверждать каждое сохранение, проверку, восстановление или переключение. Ошибка обхода не должна блокировать весь интерфейс. Полная автономность обязательна; z2k не должен становиться обязательной внешней службой.

## 1. Сначала принять подготовленный пакет

Открой полный актуальный checkout `ArtixSx/RAZVILKA`. Этот пакет подготовлен для `c3722365dcbcee8e1c5e5909aabbbf907e457a22` (`0.18.10`). Проверь текущие HEAD, рабочее дерево и CI. Не отменяй последующие исправления.

Прочитай `README_RU.md`, `SCOPE.json`, `docs/TEST_REPORT_RU.md` и `docs/AUDIT_AND_PLAN_RU.md`. Не называй локальные компонентные проверки аппаратными или полноценной сборкой. Изолированный Go-модуль использован только для двух пакетов; `go.mod` основного проекта менять на Go 1.23 нельзя.

На отдельной ветке выполни `apply_changes.py --check`, затем просмотри `--diff`. При точном совпадении базы примени `--apply`. При несовпадении перенеси 16 изменений и новые файлы на актуальную базу вручную, с проверкой каждого действующего аналога. Не используй reset/force и не подменяй новый исходник старой полной копией.

Первая обязательная проверка: после применения сохранилась оболочка
`Security.Middleware(operationMiddleware(...))`, и новый availability endpoint требует текущую авторизацию. Убедись, что неожиданный URL/метод не получает доступ в обход существующего допуска операций.

Выполни полный Go-набор, весь набор UI-тестов и реальную сборку приложения с toolchain из `go.mod`. У пакета есть корректировки двух прежних UI-тестов; проверь остальные фикстуры, извлекающие функции из app.js. Исправляй причины несовместимости, а не удаляй проверки.

Собери и запусти настоящую панель. Проверь минимум 390px/desktop, навигацию при 409/503, редакторы, выход/вход, окончание сессии, keyboard Escape, повторный клик, форму мастера, прежние карточки и все действующие страницы. Локальная браузерная фикстура пакета не заменяет этот этап.

## 2. Дальше выполнять план в указанном порядке

Следующий законченный результат — читабельная панель и работающие статусы задач во время всех длительных операций. Не добавляй новый движок, UI-framework или второй демон автоматического управления до завершения этого результата.

Последовательность:

1. Неизменяемые, ограниченные по размеру снимки для отображения; убрать реальные чтения Store/сетевые проверки из критического пути навигации. Показывать возраст данных, не выдавать снимок за свежий PASS.
2. Единый контракт существующих фоновых задач: быстрый приём, статус, отмена, восстановление после рестарта, idempotency и неопределённый исход запроса. Продолжить существующий coordinator/job-код, не создавать параллельного хозяина firewall.
3. Единый мастер разрешений и простые изменения желаемого состояния. Обычные действия внутри политики — без модальных подтверждений; новые права и разрушительные действия — одно понятное согласование. Безопасность остаётся на сервере.
4. Восстановление наблюдателя сети и фоновых работников; отсутствие интернета или отказ каталога не блокирует обслуживание всей системы.
5. Закрыть полный A → B → ошибка применения B → подтверждённый откат → C с типизированной причиной отказа и проверкой реального трафика.
6. Ограниченное обучение NFQWS2, память успешных стратегий, согласование внутреннего подбора с внешним выбором транспорта.
7. Завершить автоподготовку зависимостей, источников, проверенных резервов, каталогов и обновлений в пределах политики.
8. Аппаратная матрица и испытания с намеренными отказами, сначала 24, затем 72 часа.

Смотри условия выхода каждого этапа и матрицу. Каждый этап закрывать конкретными проходящими сценариями, а не количеством добавленных функций.

## 3. Не нарушать следующие свойства

- Не удалять общий gate, fence, журнал применения, валидацию, CAS/ревизии, проверку области устройств и автоматический откат ради зелёного статуса.
- Не включать `confirm=true` повсюду и не хранить универсальное разрешение в localStorage.
- Не объявлять установленный процесс или отвечающий URL доказательством всей работы сервиса.
- Не повторять POST/PUT после таймаута без idempotency или доказанного `not_started`. Сначала выяснить результат сохранения/применения.
- Не освобождать сетевой допуск раньше очистки/отката. Не убивать внешний z2k, сторонние туннели или чужие сетевые правила.
- Не считать неопределённую проверку доказанным отказом кандидата. Восстанавливать проверяющий механизм отдельно.
- Не стирать пользовательские стратегии, ключи, подписки, редакторские черновики и последнюю рабочую конфигурацию при обновлении.
- Не расширять список устройств, разрешённых источников, протоколов и внешних действий без согласования.
- Не принимать пользовательский Lua/скрипт сообщества как безопасный исполняемый код. Стратегии сообщества — непроверенные кандидаты с проверкой совместимости и происхождения.
- Не делать рабочую сеть зависимой от доступности GitHub на каждом запуске.
- Не публиковать неподтверждённый релиз и не разворачивать его на основном роутере автоматически.

## 4. Отчёт по каждому завершённому этапу

Укажи точный коммит, файлы, изменения поведения, реально выполненные тесты, среду и открытые сценарии. Отделяй CI, браузерную фикстуру, настоящую панель и физический роутер. При нехватке аппаратной проверки не ставь сценарию статус «пройден».

Не заканчивай работу только новым планом: сначала интегрируй и проверь подготовленный Stage 1, затем реализуй следующий полный сценарий. Для опасного сетевого сценария при неясной причине оставляй явный диагностический статус, а не ложную готовность.
