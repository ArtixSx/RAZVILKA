## 2. Контрольные находки: факт, риск и незавершённая функция

### F01. Универсального автономного восстановления пока не доказано

Это прямо указано в `docs/CURRENT_STATUS_RU.md`. Главный P0 — не ещё одна кнопка, а автоматическая цепочка отказ→диагноз→резерв→Apply→новый клиентский поток→пополнение. Ручное переключение не закрывает P0.

### F02. Повторное получение подписки может снова давать только начало выдачи

`internal/providerfeed/parse.go`, `parse()`: URI-список прекращает отбор при `len(accepted) >= limit`; профильная ветка тоже берёт начальную ограниченную часть. `autonomyRefill`/`RequestRefill` инициируют новую загрузку, но это само по себе не задаёт курсор по остальной выдаче.

**Статически подтверждённый предел:** для неизменной упорядоченной выдачи с неудачным началом повторный fetch с тем же limit снова оставляет рабочий узел из хвоста вне NodeStore. Курсор проверок по уже импортированным ID эту проблему не решает.

Приёмка: первые 32 допустимых профиля не работают, 33-й работает; задан limit=32. Автоматика должна добраться до 33-го при ограниченной памяти и без отмены предела. Отдельно повторить на неизменном ETag/304 с разрешённым локальным продолжением сохранённого snapshot.

### F03. Неудачное применение первого резерва завершает раунд

`internal/app/autonomy_worker.go`, `runAutonomyService()`: после выбора `ready[0]` ошибка `applyAutonomyRoute()` сразу возвращает `apply-refused`. Ветка не переходит к `ready[1]` в этом раунде. Отрицательный результат перепроверки первого резерва также завершает раунд.

**Факт кода:** ранний выход. **Риск, требующий теста:** B проходит canary, но стабильно не проходит активацию; без контекстного карантина он может вновь выигрывать порядок, расходуя switch budget, пока C остаётся неиспользованным. Не заявлять бесконечный цикл на устройстве без воспроизведения.

Исправлять только после доказанного завершения rollback. При rollback-failed, утрате владения, неверной сети или общем отказе другого сервиса нельзя просто продолжить пробовать C. Не помечать B «плохим», если провалился общий компонент или другой сохранённый маршрут.

### F04. Выбор разных движков пока не универсален

В `runAutonomyService()` перебор `PreferredRoutes` расположен внутри `if current == ""`. После отказа уже применённого локального способа дальнейшая ветка преимущественно обслуживает NodeStore/Sing-box, а не общий состав всех разрешённых DNS/движков/стратегий.

Нужен общий построитель кандидатов. При этом **не отменять пользовательское закрепление**: starter NFQWS2 остаётся NFQWS2-only, пока пользователь не разрешил альтернативы. Автоматизация не означает право принудительно включить внешний VPN.

### F05. У USQUE несогласованы описание зависимости и рабочий адаптер

`internal/components/components.go`, `Specs()` говорит, что `usque-keenetic` использует собственный nativetun и Sing-box не нужен. Но `cmd/razvilka/main.go` регистрирует `NewProxyTunnelAdapter("usque", …)`; в `internal/dataplane/proxy.go` управляемый USQUE запускается в `socks`, а `sidecarBinary()` по умолчанию ищет Sing-box. Это разные режимы работы.

**Это подтверждённая несостыковка metadata и управляемого runtime, не утверждение об ошибке самого протокола USQUE.** Исправить описание, граф зависимостей, install plan и readiness выбранного исполнения. Либо довести отдельный native TUN-adapter, либо явно учитывать SOCKS+sidecar. Не лечить только заменой текста, оставляя установку без необходимого компонента.

### F06. Автоматическая установка по-прежнему закрыта

`internal/app/autonomy_api.go`: `automatic_install:false`, `component_install:false`. `autonomy_maintenance.go` выполняет check/prepare и наблюдает существующую подготовку; компоненты проверяются через `Components.List(..., true)`. Это корректно заявленное ограничение, а не готовая unattended installation.

Нужен законченный install/activate/verify/rollback для приложения и полного графа зависимостей. Недопустимо просто поставить false→true и вызвать общий opkg upgrade.

### F07. NFQWS2 starter проверяет текущий способ, но не обучается заново

`internal/app/nfqws2_starter.go`: при не-PASS возвращает `unconfirmed`; эта ветка не запускает перебор StrategyLab. `nfqwsSetupMode`/`StageNFQWSMode` сохраняют только reviewed draft. Выбор MODE_AUTO — охват автохостлиста, а не настройка стратегии и не факт live-применения.

Нужен самостоятельный конвейер подбора NFQWS2 с локальной проверкой и управляемым Apply; first-run config должен завершаться применением разрешённого плана без ручного обхода по вкладкам.

### F08. Один неполный DNS-ответ останавливает весь refresh адресов

`internal/dataplane/address_refresh.go`, `resolveRefreshPolicyRules()`: единственный `incomplete` превращает ошибку/пустой/непубличный ответ любого домена в отказ всего набора. Это намеренный предохранитель от потери работающей половины правил. Он нужен до реализации per-domain ledger, но оставлять его окончательной архитектурой нельзя.

### F09. Конфигуратор, адаптер и работающий движок — разные состояния

Mihomo/HEV имеют подготовленные части, но production-регистрация в main включает прежние адаптеры. Текущий roadmap прямо оставляет нативную интеграцию открытой. Пакеты стратегий умеют ручной обмен/проверку, но не образуют автоматически работающий облачный каталог. Не отмечать эти пункты закрытыми по факту появления формы.

### F10. Поведение при сбросах наблюдателя остаётся открытым

Документы описывают прерывистый reset observer; добавлены диагностика и ограниченный retry netlink, но историческая причина не установлена. Нельзя «починить» это игнорированием network epoch. Нужен классификатор событий с сохранением истинных границ доверия.

## 3. Главная цель и обязательные инварианты

Пользователь один раз выбирает устройства, сервисы, допустимые источники и виды изменений. После сохранения проект сам устанавливает разрешённые компоненты, проверяет пути, назначает и поддерживает сервисы, пополняет запас, обновляет данные и выполняет согласованное обслуживание. Для штатного восстановления не требуется подтверждать каждый ключ или повторно нажимать Apply.

Это не обещание доступности недоступного во всей сети внешнего сервера. При отсутствии подходящего пути приложение продолжает безопасный ограниченный поиск, сохраняет LAN-панель и объясняет следующую попытку.

1. Один владелец сетевых ресурсов и одна общая очередь. Не добавлять независимый cron/демон, который меняет те же маршруты.
2. Контроллер и LAN-панель не должны зависеть от исправности выбранного VLESS. Служебные загрузки используют отдельно разрешённый bootstrap/recovery path.
3. Стандартная чистая установка: только проверенный набор nfqws2-keenetic, дополнительные сервисы выбирает пользователь. Удаление или обновление defaults не очищает существующие пользовательские назначения.
4. NFQWS2-native не зависит от существования проекта z2k во время работы; z2k — источник идей/одноразового reviewed импорта.
5. Работающий локальный вариант не заменяется ради более низкого ping, рейтинга или нового файла подписки.
6. Imported, available, process-running, candidate-PASS, applied-PASS и client-observed — разные состояния.
7. DNS, контрольный сервер, endpoint, transport, auth, service и local runtime имеют разные причины отказа.
8. Ни ошибка проверки, ни INCONCLUSIVE, ни 429, ни ошибка очистки не превращаются автоматически в «мёртвый узел».
9. Config/network/definition/credential/engine revisions связываются с proof; изменение существенного параметра аннулирует право нового применения старого proof.
10. После активации проверяется новый клиентский путь; тест отдельного loopback-кандидата не заменяет эту проверку.
11. Приватные ключи, подписки с токенами, внутренние адреса и домены не отправляются внешнему checker или сообществу без отдельного адресного разрешения.
12. Safe Mode, Stop, ручное закрепление и отзыв разрешений имеют определённую семантику для каждой операции. Не снимать их ради демонстрации «автоматики».
13. Обновление процесса на диске не считается обновлением запущенного процесса. Роллбек проверяет бинарник, конфиг, зависимости, init/hooks, состояние и сетевые ресурсы.
14. Уже сохранённый рабочий материал не уничтожается из-за ошибки fetch, 304 или пустой выдачи. Явный отзыв credentials/разрешения обрабатывается отдельно.
15. Пользовательская стратегия и список не перезаписываются обновлением стандартного пакета. Порядок стадий NFQWS2 семантически значим; канонизация не должна переставлять их.

В картах файлов `web/…` означает `cmd/razvilka/web/…`; короткие соседние Go-имена относятся к последнему указанному каталогу. Предлагаемые новые модели помечены как проектные, а не как уже существующие API.

### PR-00. Зафиксировать базу и регрессионный прогон

**Файлы:** `docs/CURRENT_STATUS_RU.md`, `docs/EXT5_REVIEW_2026-09-19_RU.md`, `docs/ROADMAP_2026-08-30_RU.md`, `scripts/check.sh`, `.github/workflows/ci.yml`, `.github/workflows/release.yml`.

Сначала получить актуальный HEAD и проверить, не появились ли новые изменения после этой сверки. Не делать `reset --hard`, не накладывать архив EXT5 поверх main. Прочитать все применимые `AGENTS.md`, если они есть. Сохранить пользовательский diff. Выделить рабочую ветку от актуального main.

На отдельном Linux-стенде воспроизвести полный baseline. Go брать из фактического go.mod; на срезе требуется `go 1.26.0` и `toolchain go1.26.5`. Не понижать требования и не выдавать локальный Go1.23 subset за общий gate.

Проверить два уровня: source/CI и точный release artifact. Не удалять старые тесты только потому, что они мешают новой реализации. Требования, которые намеренно изменились, менять отдельно и объяснять.

**Выход:** короткий baseline report, revision, команды/exit, список воспроизводимых fail без сетевых секретов. После этого продолжать доступные программные этапы даже без доступа к роутеру.

### PR-01. Проверяемая модель разрешений и состояния автоматики

**Файлы:** `internal/autonomy/policy.go`, `decision.go`, `internal/app/autonomy_api.go`, `autonomy_store.go`, `autonomy_services.go`, `internal/config/*`.

Сохранить существующие сущности, а не заводить параллельный «Autopilot2». Для каждого сервиса определить ровно одного владельца: manual, service policy или общая autonomy policy. При миграции прежних групп не создавать второго управляющего цикла.

Разделить сохранённое желание пользователя и фактическую готовность: setup_complete, enabled, has_scope, allowed_sources, available_executor, bootstrap_reachable, checker_ready, storage_writable, applied_identity. API должен давать конечный `operational_state` и список typed blockers с безопасным пояснением, а не одну галочку auto.

Первый мастер сохраняет scope, выбранный штатный набор/дополнения, способы, доверие к источникам, график установки и разрешения на автоматическое применение. Не включать незнакомые публичные подписки, новые домены или телеметрию по косвенному наследованию.

Для уже разрешённых операций согласие постоянное: новый UUID из разрешённой подписки не требует нового клика, но проходит проверку; новый источник, клиентская подсеть или более широкий режим маршрутизации требует пересмотра разрешений.

**Приёмка:** restart сохраняет настройки; обновление каталога не выбирает новые сервисы; paused/removing корректно завершаются; после сохранения UI показывает точное число управляемых и фактически восстановимых сервисов.

### PR-02. Довести VLESS failover, включая провал первого резерва

**Файлы:** `internal/app/autonomy_worker.go`, `autonomy_recovery_helpers.go`, `node_autofallback.go`, `nodes.go`, `internal/autonomy/decision.go`, `internal/dataplane/nodecheck.go`, `node_ip_probe.go`, `proxy.go`, `internal/nodestore/route_snapshot.go`.

Разделить наблюдение текущего пути, подготовку кандидата, разрешение переключения и подтверждение применения. Сначала проверять актуальный разрешённый последний рабочий вариант. Не запускать полный expensive checker каждого сервиса каждую минуту, когда достаточно исправного runtime и короткой направленной пробы.

Для общего сбоя WAN/DNS/контрольного URL не менять все узлы. Повторная проверка должна различать `remote_unreachable`, `protocol_auth_failed`, `service_region_denied`, `rate_limited`, `dns_failed`, `local_runtime_failed`, `network_epoch_changed`, `checker_broken`, `cleanup_failed`.

После подтверждённого отказа A проверить резерв B на текущей сети. Если B не проходит, искать C в пределах бюджета. Если B прошёл раннюю пробу, но не прошёл Apply/postcheck, сначала полностью завершить откат, затем классифицировать причину. Узел B получает ограниченный карантин только при привязанном к нему отказе; общий отказ ядра/плана не портит его репутацию. При безопасном восстановленном состоянии продолжить C или поставить ближайшую задачу, не ждать обычного многочасового обновления подписки.

`INCONCLUSIVE` разрешает только безопасное исследование альтернатив, а не автоматическую замену. Нужна отдельная достаточная причина переключения: доказанный отказ текущего client-path либо восстановимая потеря его локального runtime при успешном резерве. Нельзя просто убрать canExplore/identity/cleanup guards.

Переключение одного сервиса не должно менять маршруты остальных и проигрывать из-за неприменённых чужих черновиков. При общих процессах обеспечить обратимую переконфигурацию или реконструкцию сохранённого плана, а не независимые конкурирующие демоны.

**Обязательный регрессионный сценарий:** A недоступен; B каждый раз отвечает на canary, но ломается при применении; C исправен. C должен получить попытку без бесконечного переизбрания B и без исчерпания бюджета на B. Повторить, когда ошибка B на самом деле вызвана общим компонентом: карантин B не ставить.

Далее один scoped DNS+route executor: preview, общие домены, реальные лимиты прошивки, сосуществование AdGuard/dnsproxy, контроль клиентского DNS, readback, pending_cache_convergence, rollback. До этого `DNS_LIVE_ADAPTER_UNAVAILABLE` остаётся защитой.

Smart DNS gateway отличается от обычного resolver и меняет инфраструктуру, которой доверяется трафик. Xbox/Malw/Comss/GeoHide и account-based профили использовать только как разрешённые кандидаты; заявленная поддержка сервиса не равна локальному PASS. Не перегенерировать WARP и не удалять VLESS из-за одного плохого DNS-ответа.

**Приёмка:** меняется только один RR; общий домен двух сервисов; один NXDOMAIN не замораживает весь refresh; старый кэш клиента; DNS-route loop; неработающий tunnel bootstrap; IPv6 не утёк; новый endpoint проверен; служебные источники не оказались внутри сломанного маршрута.

Сервер сетевого приёма технически видит IP источника соединения; описать его хранение/retention и не обещать абсолютную анонимность. Высокий рейтинг не является proof. Отравленный каталог не должен дать право исполнения чужого Lua/команды или Apply; local schema, resource constraints и canary остаются.

При отсутствующем правильном времени не отключать TLS/signature checks: сохранить прошлые разрешённые маршруты и отложить новое доверие.

### PR-13. Сайт и API: отображать реальную автономность

**Файлы:** `web/interface.js`, `console-autonomy.js`, `automation-setup.js`, `workspace-controls.js`, `workflow-actions.js`, `node-browser.js`, `setup-workflows.js`, `awg-workspace.js`, `extension-lab.js`, `service-dashboard-ui.js`, `app-update-ui.js`, backend DTO.

Главная показывает не просто enabled, а «управляются N / готовы к восстановлению M», активную операцию, ожидание ресурса/сети, причину паузы, следующий допустимый retry и резерв. «Процесс программы работает» не равно «все сервисы доступны»; отказ одного VLESS не превращает всю панель в «проект остановлен».

### PR-14. Система испытаний и допуск выпуска

**Файлы:** существующие `*_test.go`, `scripts/test-*.mjs`, `scripts/check.sh`, новые интеграционные/HIL harness в отдельной директории, release workflow, документы статуса.

Не ограничиваться unit-test моками. Пройти уровни по порядку:

1. Unit/property/fuzz: чистые функции, парсеры, outcomes, часы/окна, dependency graph, signatures/canonicalization, migration, idempotency.
2. Integration: настоящий HTTP/server/store с authentication и раздельной областью test state; контролируемые источники и отказ файловых операций.
3. Native engines: реальный Sing-box/Xray/Mihomo/HEV/USQUE на изолированной сети или тестовом устройстве с контролируемыми серверами. Не использовать постоянные production UUID в артефактах.
4. Router HIL: точный binary/artifact SHA, версия firmware/kernel/arch, физические клиенты, трафик, firewall/routing before/after с обязательными exit codes.
5. Soak 24–72 часа: закрытый браузер, несколько сервисов, плановые и аварийные события, память/FD/process counts/CPU/flash writes, источники/часы/нет WAN.

Минимальный стенд: основной сервер A, резерв B, C для успешного восстановления после провала B; источник, который позже публикует D; два сервиса с разной политикой; один выбранный и второй реально исключённый LAN-клиент. Там, где нужен controlled remote server, публичная случайная подписка не заменяет управляемую инъекцию отказа.

На старте снять baseline сети и убедиться, что все команды чтения завершились успешно. Два exit127 не являются одинаковым firewall. Сравнение правил исключает изменяемые счётчики, но счётчики сохраняются отдельно как часть proof клиентского пути. Нельзя выводить здоровье только из POST Apply 200 или наличия TUN.

Инъекции: внешний отказ A, неправильный ключ, silent timeout, локальный остановленный owned process, пропавшая полностью owned цепочка, частично изменённая/чужая цепочка, DNS/TTL change, WAN event, restart программы, reboot роутера, storage full, авария в durable фазах установки. Не сносить глобальные firewall-таблицы живого роутера ради теста. Перед разрушительными HIL иметь out-of-band доступ и отдельное разрешение владельца.

Измерять интервалы от момента отказа до обнаружения, до первого кандидата, до начала/конца активации и до успешного нового клиентского соединения. Отдельно gate wait/engine probe/rollback. Не обещать «30 секунд восстановления» по одному 30-секундному таймеру.

Результат каждого case: planned → automated_test_passed / native_passed / hardware_passed / failed / blocked / not_applicable. Не применять общий PASS ко всем уровням. Схема результатов есть в `ACCEPTANCE_MATRIX.json`; все записи начально planned.

## 5. Общая модель данных для реализации, а не новая параллельная БД

Ниже предложены требуемые связи, а не утверждение о готовой структуре текущего кода. Codex должен расширять существующие config/autonomy/NodeStore/evidence/journal, сохранять migration и не дублировать источники истины.

### DesiredServicePolicy

Service ID + immutable definition/version; devices; route preference или pin; допустимые executors/sidecars/DNS; source allowlist; права применять, тестировать, ставить компоненты; terminal action; lifecycle policy. Настройка должна/может, не текущий proof.

### EffectiveRouteIdentity

Service/scenario, scope digest, network/boot epoch, engine binary hash+version/features, sidecar hash/type, credential material hash, transport, endpoint/address family, DNS provider+resolution location, конфигурация/recipe/resources digest. Не переносить прежний PASS по совпадению friendly name или host:port.

### Evidence

Кто/где/каким процессом проверял, точный путь, исходное имя, выбранные адреса и покрытие, TLS, service predicate, egress identity, timestamps/fresh_until, class причины, ограниченные метрики, stage/cancel/cleanup. Не хранить raw response body, secret-bearing URLs или credential в публичном DTO. Изоляционная проба и применённый LAN-путь — два явных уровня.

### DurableJob / RecoveryRecord

ID/idempotency key, type, priority, state, references, frozen selection, cursor, permission and definition revision, expected network, attempt count, cooldown, total budget, completed/skipped/failure counters, last exact checkpoint, cleanup outcome. Сохранение перед необратимым действием; потерянный response не запускает действие дважды.

### AddressLedger

Hostname+resolver+network+family key; RRset/TTL/CNAME/negative cache; last validated material; finite grace; обязательность домена и references. Раздельно endpoints туннелей и service destination sets.

### ArtifactTransaction / RecipeReceipt

Artifact or recipe digest, publisher, signed sequence+expiry, old/new versions, dependency snapshot, schema versions, activation marker, rollback status, quarantine. Trust highwater должен сохранять смысл при rollback/restore.

## 6. Что особенно нельзя упростить ради зелёного статуса

- Не делать `INCONCLUSIVE=FAIL` и не принимать любой 200/302/403/429 за доступность нужного сервиса.
- Не заменять строгую проверку all-address coverage первым ответившим IP без нового явного уровня assurance; limit/timeout показывать как неполную проверку.
- Не отключать TLS/server pin и private-address guards. Разрешение частного ресурса — отдельный scoped workflow.
- Не считать документационный либо schema-конфигуратор рабочим маршрутом. Отдельный binary/native test обязателен.
- Не выдавать старый timestamp или загрузку 304 за новую проверку credentials/service.
- Не reset счётчик переключений/registrations на reboot и не делать безлимитный reconnect с утечкой процессов.
- Не считать busy/очередь отсутствием узла и не удалять весь reserve при общем отсутствии WAN.
- Не расшаривать публичные узлы/статистику с приватными полями. Hash частного домена не делает его автоматически анонимным.
- Не стирать личные стратегии, старый рабочий конфиг, trust receipt и единственный rollback для экономии диска.
- Не использовать отказ checker или observer как право применить неизвестный маршрут.

Выполнять на изолированном Linux build/test стенде, не на live router. Не угадывать архитектуру или перезаписывать окружение владельца. Пересверить команды с фактическим `AGENTS.md`, `go.mod` и workflow при начале работы.

**Далее:** PR-10/11: оригинальный USQUE, WARP/AWG, Mihomo/HEV; PR-12: collective hints/download/upload. Улучшения сайта из PR-13 и испытания PR-14 выполнять для каждого этапа, не откладывать одним финальным большим PR.

Разделить milestones:

- **AUTOMATION-CORE:** разрешённый установленный исполнитель, автономные проверки/резерв/пополнение/failover/restart, актуальное UI-состояние.
- **AUTOMATION-MAINTENANCE:** безопасная автоматическая установка/обновление и независимый rollback точного комплекта.
- **AUTOMATION-NFQWS:** режим/персональные сайты/совместимые стратегии/локальное обучение/сохранение пользовательского слоя.
- **AUTOMATION-EXPANDED:** DNS-композиции, новые native executors и коллективные hints с собственными gates.

Нельзя назвать полную пользовательскую цель завершённой по первому milestone. Но каждый milestone должен быть устанавливаемым проверяемым улучшением, а не очередным макетом.

**Конечный пользовательский критерий:** после одного мастера человек добавляет/убирает сервис; необходимые уже разрешённые действия выполняются сами. При отказе основного пути не требуется ручная загрузка VLESS, повторное включение Autopilot или перезапуск панели. При недоступности всех разрешённых способов система сохраняет управление, объясняет границу и продолжает ограниченные попытки, не ломая исключённые устройства.
