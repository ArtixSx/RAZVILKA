**Редакция:** V2 / ALL-INTERNET / 29 сентября 2026 года.

> Основной продуктовый режим: **весь интернет на устройствах выбранных домашних сегментов, кроме исключённых устройств и сайтов**. Выбранные сервисы — индивидуальные правила и проверки поверх общего автоматического подключения. Незнакомые и невыбранные сайты не остаются вне общего маршрута.

Это план, а не новая версия программы или патч. Никакие сетевые испытания, установки, изменения GitHub и роутера при подготовке не выполнялись. Источники и границы проверки приведены в `SOURCES_AND_BASELINE_RU.md`; предлагаемая семантика — в `GLOBAL_POLICY_SPEC_RU.md`. Не импортировать примеры этого документа как текущую JSON-схему.

## 2. Замысел продукта: весь интернет, а не список разрешённых для обхода сайтов

> Установил RAZVILKA → один раз выбрал сервисы для отдельных настроек, исключил устройства и сайты, которым обход не нужен, разрешил способы подключения и источники → дальше программа сама организует общий доступ к интернету, получает и проверяет кандидатов, применяет, наблюдает, переключает резерв и восстанавливается.

Есть **два назначения трафика** внутри одной программы:

1. **Общее подключение** обслуживает весь остальной интернет участвующих устройств. Для неизвестного сайту каталогу адреса не требуется новая запись, регистрация сервиса или ручная галочка. Нулевое количество выбранных сервисов — корректная конфигурация общего режима.
2. **Индивидуальное правило сервиса** может выбирать другой путь/DNS/сценарий/резерв для YouTube, ChatGPT, Discord, пользовательского сайта и т. д. Ошибка этого правила не означает отказ общего пути.

Исключения устройств и сайтов действуют поверх обоих уровней. Российские сервисы по согласованному автоматически обновляемому списку работают без обхода. Ручной override сохраняется. «Без обхода» означает базовую политику роутера для данного клиента, не обязательно конкретный провайдер.

Весь интернет под управлением не означает один обязательный VPN или проверку каждого сайта в мире. Нужен определённый маршрут/результат политики для каждого класса трафика. Общий выход по умолчанию использует пригодный разрешённый путь; разные сервисы могут использовать другие. Общая работоспособность пути и проверенная доступность конкретного сервиса — разные показатели.

Если подходящий общий исполнитель отсутствует, мастер показывает конкретное препятствие и разрешённые варианты подготовки. Он не сохраняет фиктивный PASS, не включает скрытый DIRECT и не утверждает, что один только service-specific Smart DNS или NFQWS2 переносит любые пакеты.

Не требовать обязательной покупки сервера/подписки. Используются существующие свои профили, разрешённые источники и совместимые способы. Бесплатный источник не гарантирует рабочий путь. Полностью ручной pin и режим «только выбранные сервисы» могут сохраняться как явно выбранные альтернативы/legacy, но не default новой установки.

Первый экран отвечает: какое общее подключение используется; работают ли индивидуальные сервисы; какие устройства/сайты исключены; что делает автоматика. Пользователь не обязан знать TUN, NFQUEUE, JSON или вручную запускать генераторы.

## 3. Фактическая база и конкретные места изменения

[S4] сообщает: часть проверок/DNS/Apply/Stop/Resume работает через постоянную очередь, panel snapshots существуют, scoped DNS+DIRECT имеет ограниченную приёмку. Исправления 0.18.14 сохраняют панель при journal fence и сокращают лишнюю фоновую работу. В 0.18.15 добавлено ожидание допуска; точный пакет установлен на AArch64, однако рабочие маршруты после этой установки в статусе не подтверждены. Это документированные результаты, не текущая проверка роутера.

**Повторно прочитанный код [S8, S9]:**

- `NetworkPolicy` уже отделяет Clients от Traffic; есть `lan_except`, `all_except`, `DefaultRoute`, rules и RussianExclusions. Это прямо названо намерением, не runtime. Расширять существующую модель.
- `ValidateNetworkPolicy` для `all_except` принимает конкретные идентификаторы usque/warp-wg/xray/sing-box node. Обычный WG/AWG и автоматическое назначение общего пула нельзя подключить только кнопкой: обновить модель/валидацию/миграции и компилятор capabilities.
- `Traffic.Unavailable` сейчас `retain` либо `base`. Нужна явно заданная политика исчерпания резервов и неподдержанных классов; не выдавать существующий enum за законченный fail-closed.
- `DecideNetworkPolicy` до общих правил возвращает `base` при `SERVICE_SCOPE_MISMATCH`. Для нового режима промах индивидуального scope должен снять только индивидуальное переопределение и продолжить общие исключения/общий путь. Это адаптация старой семантики к новому требованию, а не утверждение о сломанной прежней функции.
- Финальный `all_except` уже выбирает bypass в чистой функции. Это не доказывает, что неизвестный сайт реально пройдёт через действующие правила, DNS, TUN и правильный endpoint.
- Список российских исключений связывается с service IDs; классификация российских ресурсов не должна зависеть от того, выбрал ли пользователь эти сервисы для персонального наблюдения.

Переиспользовать существующие NodeStore, engineconfig, dataplane, operation gate, durable jobs, evidence, scoped DNS, NFQWS2/Xray/Sing-box/USQUE и WARP/AWG adapters. Регистрация adapter и парсер не равны production-ready. Пути из старых аудитов — ориентиры, контракты читать на actual HEAD.

Основные платформы: Keenetic/Netcraze Entware AArch64/MIPS/MIPSel. OpenWrt/Cudy TR3000 — самостоятельный последующий адаптер и приёмка. Сохранить одно ядро Go и локальный интерфейс; языковая перепись не является целью этого плана.

## 6. Архитектурные правила

- Один координатор сетевых изменений и существующая очередь. Параллельные безопасные чтения/подготовка разрешены по бюджету; конфликтующие изменения сериализуются. Не создавать отдельные автономные планировщики DNS/WG/WARP/каждой подписки.
- RAZVILKA владеет только своими процессами, интерфейсами, правилами, файлами и NFQUEUE. Чужой Xray, штатный WG, сторонний AWG, z2k и другие менеджеры обнаруживаются, но не захватываются автоматически. Не устанавливать HydraRoute/AWG Manager/z2k как скрытых управляющих зависимостей.
- Различать желаемые настройки, подготовленный план, применённую конфигурацию, наблюдаемое состояние, последний рабочий вариант (LKG), журнал операции и результаты проверок.
- Применение разрешено текущей сохранённой политикой или явным текущим намерением пользователя. Успех canary необходим, но сам по себе не даёт права менять scope, использовать новый источник доверия или игнорировать изменённые настройки.
- Ручной pin/отмена/Stop отзывает устаревшее автоматическое намерение. Пауза автоподбора не равна Stop, а Stop не равен удалению настроек.
- Ошибка одного сервиса не должна перезапускать всё. Общий отказ WAN/DNS/движка диагностируется отдельно от отказа конкретного узла.
- Проверки порта, процесса, TUN и handshake — частичные свидетельства. Service PASS должен иметь конкретный сценарий, путь и срок действия. Успех веба не означает успех голоса/видео/UDP/IPv6.
- Единичный timeout/429/ошибка проверяющего механизма не делают узел неисправным навсегда. Повторяемые таймауты при исправном контроле могут участвовать в ограниченной классификации отказа пути; причина и уверенность сохраняются.
- Истечение evidence запрещает новое применение по старому доказательству, но не является командой немедленно удалить здоровый действующий туннель. Нужны повторная проверка и явно заданная grace/failure policy.
- Откат возвращает согласованное безопасное состояние. Возврат конфигурации не обязательно восстанавливает доступ через уже мёртвый сервер A; для перехода к C нужны отсутствие незавершённых изменений, проверенные собственные ресурсы и неизменная политика, а не обязательная доступность A.
- Не ослаблять TLS, REALITY, проверку происхождения компонентов, auth/CSRF или ownership ради PASS.
- Секреты — локальные защищённые хранилища и ссылки, не обычные журналы/телеметрия. Не сохранять вставленные ключи в browser localStorage. Явный локальный импорт/экспорт — отдельная защищённая операция.
- Весь интерфейс и обязательные ресурсы доступны локально. Внешние каталоги, документация, генераторы и community не являются условием запуска.

Дополнения ALL-INTERNET:

- Общий путь — полноценная цель scheduler/evidence с собственными LKG/reserves/status, а не фиктивный сервис `*` в каталоге и не второй Autopilot.
- Отсутствие, удаление или несовпадение scope индивидуального сервиса означает наследование общего правила, а не DIRECT и не блокировку само по себе.
- Общий путь и отдельный сервис могут ссылаться на один runtime. Снятие последней сервисной ссылки не разрешает удалить runtime, если его использует общее назначение, paused state, резерв либо откат.
- Все классы forwarded internet имеют явное решение: через подходящий разрешённый путь, через базовый путь по явному правилу, либо ограниченно blocked/degraded. Неизвестный домен, IPv6, QUIC и прямой IP не означают implicit direct.
- Защищённые локальные ресурсы, router management, DHCP/ND и transport bootstrap не превращаются в catch-all интернет. Их сохранность — отдельный инвариант, а не пользовательский RU-список.
- Safe Mode, Pause и Stop имеют разные последствия; отключённый автоподбор не снимает работающий маршрут, явный Stop не удаляет конфиги и действует по отдельно согласованной stop policy.

## 7. G01/G02 — проверка последних замечаний, без бесконечного переписывания основы

Ниже замечания предыдущих аудитов, не новый прогон тестов. На актуальном HEAD сначала воспроизвести, затем исправить только подтверждённое.

### G01.1 Установщик 0.18.15

Различать результаты предыдущего состояния: маршруты подтверждены; известная деградация; busy; нет ответа; неверный PID/версия; journal recovery required. Временная занятость, сетевой timeout или прерывание строгой проверки не должны автоматически отключать контроль маршрутов новой версии.

Разрешить исправляющее обновление известной неисправной системы без тупика «для ремонта сначала почини сеть». Это отдельный режим с точным исходным состоянием, проверкой идентичности и доступности панели, сохранённым scope, точкой возврата и честным результатом «приложение обновлено, маршруты требуют восстановления». Не считать любое ненулевое завершение старой проверки таким разрешением.

Приёмка: old healthy / known degraded / busy / wrong identity / no response / interrupted check / fenced journal. Проверить, что требования не ослабляются из-за неизвестности.

### G02.1 Журнал и повтор ремонта

Проверить историю попыток около лимита 96 шагов: множество неудачных попыток не должно навсегда лишать возможности штатного восстановления после устранения причины. Нужен ограниченный checkpoint/отдельная история попыток, а не бесконечный журнал или отмена валидации.

Проверить прерывание между записью transaction journal и latest journal. Предлагаемая задача — проверяемое поколение/контрольная точка и recovery, а не слепое предпочтение одного файла. Ошибки записи до/после rename/fsync проверяются отдельно.

Разделить допустимое аварийное снятие подтверждённых собственных ресурсов и повторный запуск старого runtime при отказе записи журнала. Не записывать фиктивный успех, не удалять fence без доказательства. Сохранить различие между «ресурсы сняты» и «предыдущий путь восстановлен».

### G02.2 Защита входа и сохранность данных

Сохранить XSS-исправление; добавить тест конкретного шага мастера с текстом, содержащим HTML. Проверить ограниченный размер/стоимость таблиц входа и сессий. Для production-конструктора требовать корректный security gate; тестовые обходы делать явными, не ломая все тесты ради косметики.

Добавить retention backup с защитой текущей, предыдущей рабочей и упомянутой незавершённой транзакцией копий. Не удалять «всё старше трёх» без проверки ссылок. Не менять секреты, личные стратегии и staged-настройки при очистке.

**Критерий:** безопасность первого engine Apply подтверждена, панель остаётся доступной. Некритические расширения не блокируют переход к Xray. Существующие отдельные audit-пакеты не накладывать как патч; использовать их как тестовые задания.

## 8. X01–X03 — Xray: первый продуктовый приоритет

### X01. Обнаружение, установка и модель профиля

Сверить `internal/dataplane/proxy.go`, `internal/engineconfig/`, `internal/routeidentity/`, `internal/components/`, `internal/providerprofile/`, NodeStore и регистрацию в `cmd/razvilka/main.go`. Это ориентиры из прежнего аудита; реальный файл и контракт проверить.

Сначала один законченный поддержанный профиль: **VLESS + REALITY + RAW/TCP**, включая требуемый flow при его наличии. Затем XHTTP для подтверждённой версии; WS/gRPC/HTTPUpgrade — последующие совместимые наборы. Не обещать весь произвольный Xray JSON.

Каноническая модель подключения не должна быть форматом только Sing-box. Сохранить endpoint/UUID/security/flow/transport/SNI/fingerprint/Reality key/shortId/path/host/serviceName и обязательные расширения; компилятор каждого движка заявляет поддержанное подмножество. Неизвестное обязательное поле не удалять молча.

Импорт URI/JSON сохраняет проверяемый кандидат. Произвольные listeners/API/DNS/routing/imported hooks не получают права на систему; неподдержанный блок явно отклонить либо отделить исходник от безопасной компиляции с понятным diff. Импорт не равен Apply. Но явное «Использовать автоматически» после импорта может запустить всю разрешённую серверную последовательность без дополнительных модальных окон.

Capability определяется не одним номером версии: нужен native check конкретного конфига и fixture на ожидаемые возможности. Unknown не превращается в yes. Начальная доставка/установка компонента и его sidecar входят в завершённый пользовательский путь, не откладываются до общей системы ночных обновлений.

### X02. Действующее подключение

Сначала сохранить существующую проверяемую топологию Xray SOCKS + управляемый TUN-sidecar, если это рабочая база. Не обещать встроенный TUN Xray без реализации. UI показывает фактический executor и зависимость, но обычному пользователю не нужно вручную собирать эту цепочку.

Путь: подготовленный profile → native `xray run -test -config` для фактической версии → изолированная проба → существующая транзакция → точная область сервис/устройство → readback → проверка сценария клиента.

Проверять PID/start identity, digest конфига/бинарника, loopback listener, sidecar, TUN, правила и обход endpoint вне собственного туннеля. Не принимать прямое соединение вместо кандидата при ошибке прокси. Сохранить правильные DNS resolution location, SNI/Host и TLS.

Общие интерфейс/таблица/приоритеты выделяет имеющийся allocator/контракт ownership. Не занять фиксированную table 206 только потому, что такой пример был в старом тексте. Для нескольких сервисов общий runtime допустим лишь с корректными ссылками и независимыми service policies.

### X03. Восстановление и приёмка

Kill Xray, kill sidecar, исчезновение своего правила, смена WAN/endpoint, restart приложения, reboot, испорченный кандидат и rollback. Удаление одного сервиса не выключает общий runtime другого. Stop чистит только своё.

Минимальная приёмка: реальный поддержанный профиль, один выбранный физический клиент, отдельный контрольный клиент, целевой HTTPS-сценарий через Xray, отрицательный контроль прямого fallback, client scope, сохранение конфигурации и восстановление. UDP/IPv6 — отдельные сценарии для тех профилей, где поддержаны; неподтверждённые возможности так и обозначить.

**Готовность:** не только config valid или порт открыт, а полноценный ручной lifecycle и доказательства соответствующего уровня. Затем переход к WG; Xray можно оставить исключённым из Auto на непроверенной платформе, не блокируя другую работу.

**Проверки общего пути Xray:** кроме сервиса из каталога, запросить новый домен и прямой IP, которым не задано правило, с включённого клиента. Взять ноль выбранных сервисов: default route должен остаться. Клиент вне service-specific scope наследует default, а не base. На одном клиенте проверить default A и отдельный сервис B одновременно; удаление B возвращает этот сервис на A. Сначала минимальное исполнение на согласованном стенде, затем общий rollout с E/D.

Текущая документация Xray [S11] описывает первый outbound как fallback при отсутствии совпадения. Управляемый compiler обязан явно формировать ожидаемый catch-all; положение импортированного `freedom` не должно случайно стать общим выходом. Не давать чужим routing/webhooks/listeners API управляющих полномочий. Native TUN как возможную реализацию оценивать по выбранной версии и аппаратным тестам, не утверждать его отсутствие и не менять работающий sidecar только из-за пункта latest-документации.

## 9. W01–W03 — обычный WireGuard, не WARP-псевдоним

### W01. Модель и общий механизм

Добавить самостоятельный `wireguard` executor/profile kind. Пользовательский WG-сервер не требует регистрации Cloudflare и проверки признака WARP. Общую механику текущего WARP/AWG адаптера выделять аккуратно по реально совпадающим контрактам, не копировать большой файл трижды и не ломать рабочий WARP ради архитектурной красоты.

Поддержать обычный .conf: Interface PrivateKey/Address/DNS/MTU, Peer PublicKey/PresharedKey/Endpoint/AllowedIPs/PersistentKeepalive. Запретить исполнение PreUp/PostUp/PreDown/PostDown/SaveConfig и неизвестных исполняемых директив. Несколько peers — отдельная объявленная возможность: неподдержанную конфигурацию отклонить, а не оставить только первый peer.

`AllowedIPs` участвует в выборе peer и проверке адресов, но не является согласием владельца отправить весь LAN в туннель. Scope RAZVILKA компилируется отдельно; проверить их совместимость. Резервные .conf с пересекающимся 0/0 — самостоятельные кандидаты/интерфейсы, а не автоматическое добавление конфликтующих peers в один интерфейс.

### W02. Применение

Локальные ключи хранить закрыто; экспорт только по явному действию. Endpoint hostname разрешать по контролируемому bootstrap-пути, сохранять address family/TTL/identity, предотвращать маршрутную петлю. Базовый выход может быть не просто main-table, а согласованная штатная политика Keenetic.

Для недоверенных источников действует ограничение сетевого доступа/SSRF. Для явно введённого владельцем private/site-to-site endpoint не вводить безусловный запрет только потому, что адрес не публичный: требуется отдельная разрешённая область, а не ослабление общих проверок загрузчика.

Native validation WG не сводить к выдуманной общей `wg check`: strict parse плюс поддержанные проверки/настройка изолированного тестового интерфейса без изменения live peer. Native kernel и userspace варианты — по фактической платформе и профилю. Не загружать случайный модуль ради наличия галочки.

MTU и keepalive сохранять/показывать честно. Автоподбор — ограниченная диагностика по симптомам, а не универсальное 1280/25 для всех. Handshake/RX-TX подтверждают часть пути, затем проверяется нужный сервис через точный интерфейс.

### W03. Профили и восстановление

Несколько сохранённых профилей с отдельными секретными refs, primary/reserve, rename/delete protections, TTL-aware endpoint refresh. Один profile может обслуживать несколько сервисов с независимой политикой; отсутствие ссылки освобождает runtime только после корректного cleanup.

Приёмка: TCP/UDP, адресные семейства по объявленной поддержке, idle/NAT, endpoint refresh, selected/control clients, интерфейс потерян, WAN/reboot, rollback, отсутствие Cloudflare-зависимости.

**Общий WG-путь:** пригодность к default определяется покрытием заявленных destination/protocol/address-family, а не только handshake. Частный site-to-site профиль остаётся полезным, но не объявляется универсальным интернет-выходом без требуемого AllowedIPs/выходной маршрутизации. Сохранённый `0/0` не меняет scope до принятия новой общей политики. Несколько full-tunnel резервов не смешивать как peers с одинаковым AllowedIPs в одном интерфейсе; сохранить самостоятельную identity и контролируемое переключение.

Принцип WireGuard cryptokey routing и роль AllowedIPs сверены с официальным описанием [S13]. UI не должен называть успешный обмен ключами проверкой всего интернета.

## 10. A01–A03 — AmneziaWG

### A01. Совместимость без ложных обещаний

Сохранить существующий строгий `awgprofile` parser, redaction, CAS и проверки возможностей. Требуемая версия/набор функций определяется полями профиля, точным CLI, фактически загруженным модулем либо выбранной userspace-реализацией и совместимым peer.

Версии tools/module/формата не считать одинаковыми по умолчанию. Отдельно installed-on-disk, loaded, compatible, interface active, runtime owner и HIL. В старом плане упоминались AWG 3.1 и расширенные поля; поддерживать их только по проверенной реализации, а не по строке в README.

### A02. Безопасная доставка

Проверяемый manifest: модель/SoC/архитектура/ядро/ABI/vermagic, точные артефакты и hashes, источник/commit, лицензии и доверенное происхождение. Сам `.ko` на диске не даёт права insmod. Целостность по SHA не заменяет доверие к источнику.

Kernel/userspace — ограниченные платформенные наборы. Несовместимый модуль отклоняется до загрузки. Нельзя `rmmod` с живыми чужими или неизвестными интерфейсами. Ошибка module load и возможный kernel crash — разные риски: rollback файлов не объявлять защитой от зависания ядра. Reboot требует отдельного разрешения/окна.

Не устанавливать AWG Manager как второго управляющего; изучать его механизм доставки и совместимости с соблюдением лицензий. Существующие пользовательские конфиги и сторонние интерфейсы не изменять без явной передачи управления.

### A03. Работа и восстановление

Испытать оригинальный .conf с реально совместимым AWG peer. Не выдавать Cloudflare WARP за AWG3.1 сервер. Некоторые клиентские расширения обычного WG могут иметь отдельный совместимый режим, но это не доказательство всех server-dependent изменений формата.

Изолированная проба → handshake/data/service → scoped Apply → selected/control client → восстановление после WAN/reboot → возврат при плохом профиле. Миграция серверных пользователей, удалённая установка VPS и серверная ротация ключей не включены автоматически в клиентский lifecycle.

**Готовность:** законченная поддержанная комбинация модель/ядро/CLI/профиль/peer, а не универсальный переключатель «AWG работает на всём».

**AWG в общем режиме:** те же исключения клиентов/сайтов/DNS, те же references общего пути и сервисов. Точное сочетание runtime/server fields должно быть проверено; не закреплять названием «3.1» неподтверждённую совместимость всех полей. Официальная документация [S14] — источник поведения параметров, но её версия не заменяет runtime fixtures. Unsupported-функцию отразить в capabilities, не портить рабочий профиль молчаливым удалением полей.

## 11. F01–F02 — два назначения и один автопилот

### F01. Общий путь и сервисные переопределения

Минимальная предлагаемая модель внутри существующей схемы:

- `NetworkPolicy`: membership сегментов/устройств, исключения, режим всего интернета, общая ревизия.
- `DefaultPathPolicy`: allowed executors/profiles/sources/trust, требуемые классы трафика, pin или Auto, резерв, DNS и политика полного отказа.
- `ServiceOverride`: service/scenario, более узкий scope, наследуемые либо специальные DNS/path/reserves; отсутствие override означает общий путь.
- `EffectivePath`: выбранный executor/profile/version/secret refs, назначение default или service, scope, DNS context, network generation, фактические evidence и срок.

Это названия предлагаемого контракта, не требование создавать дублирующие stores. Сопоставить с имеющимися типами. DefaultRoute из [S8] расширять миграцией: `auto` не является исполнимым маршрутом, это запрос выбора; applied хранит конкретную identity. Capabilities имеют supported/unsupported/unknown, условия по runtime/platform и тип доказательства, а не набор optimistic bool из названия движка.

Сохранённая политика задаёт полномочия для автоматического commit. Повторное ручное подтверждение каждого шага не нужно. Новое доверие к публичным узлам для **всего интернета** нельзя получить из старого согласия использовать их только для одного сервиса: требуется однократное явное расширение. Оплата VPS, внешняя регистрация, reboot и отправка community-данных не следуют из слова Auto автоматически.

Общий путь проверяется набором независимых низкозатратных контрольных сценариев и состоянием своего runtime, отдельно по TCP/UDP/IPv4/IPv6. Отказ одной цели не делает весь интернет недоступным. Отдельный сервис проверяется по своим требованиям. Переход другого приложения на общий путь не требует отдельного записи этого приложения в каталог.

### F02. Восстановление, резерв и learning

Цикл: принять intent → подготовить разрешённые зависимости → обновить shortlist → изолированно проверить → после ожидания заново проверить права/сеть/ревизии → транзакционно применить → readback и сценарные проверки → наблюдать → пополнять дефицит резерва.

Default и service используют общую очередь с разными target IDs и зависимостями runtime. Сбой default не должен удалять исправный выделенный service runtime. Сбой service не переключает весь default. При общем отказе разделяемого engine группировать связанные сигналы и repair, не запускать десятки одинаковых рестартов.

Различать credential/candidate/service, общий engine/runtime, WAN/DNS/observer, изменённую политику, cleanup/rollback, unknown. Подтверждённый отказ кандидата после проверенной очистки позволяет B→C. Неоднозначное выполнение Apply сначала readback/reconcile, не повторный Apply.

Приёмка для default и отдельно для service:
`A FAIL → B isolated PASS → B attributed apply/post-check FAIL → rollback to safe state → C PASS → новый D пополнил разрешённый резерв`.

Не требовать service PASS мёртвого A для допуска C. Нужно доказать безопасное состояние собственных ресурсов и неизменность полномочий. Unknown network или cleanup failure запрещает конфликтующее применение, но не чтение панели и не штатный безопасный repair.

Рабочий LKG сохраняется при новом feed или меньшем RTT. Отзыв credentials, несовместимость и явное действие пользователя — отдельные основания. Истёкший evidence лишает права на новый commit, но сам по себе не команда снести активный маршрут. Заранее перепроверять, использовать bounded grace и явную failure policy.

Learning: нормализованная identity route/node, network profile, scenario, executor/version/config, отдельный срок/decay и ограничение памяти. Частые heartbeat/несущественное обновление observation не сбрасывают все ratings. История только ранжирует; fresh canary и текущая политика остаются обязательными. Повреждение learning не делает основную политику нечитаемой.

### Исчерпание резервов

Однократно задать режим: разрешённый base/direct после отказа либо блок только затронутого управляемого трафика. Не вводить скрытый режим по умолчанию в импортированном профиле. Во время мастера выбор обязателен и имеет понятное описание; программа не должна спрашивать заново при каждом сбое. Service может использовать общий путь как резерв лишь когда это удовлетворяет его trust/protocol/region/failure constraints. Если никто не подходит — degraded/blocked плюс ограниченный повтор, не ложная зелёная галочка.

## 12. Общая очередь и доступная панель — развитие U1/U2

20 секунд ожидания допуска в 0.18.15 — промежуточное улучшение, не замена серверного задания. Длительное действие должно быстро вернуть подтверждённый job ID и продолжиться на сервере. Повторный запрос с тем же idempotency key возвращает ту же операцию; другой payload с тем же ключом отклоняется.

Подготовку без сетевых side effects можно делать по snapshot вне глобальной exclusive-блокировки, затем перед краткой активацией заново проверить поколения/права. Проверки, использующие временные interfaces/queues, всё равно получают соответствующий ресурсный допуск. Нельзя просто убрать gate ради отзывчивости.

Приоритет: аварийный Stop/завершение cleanup → recovery → ручные изменения → автоматический подбор → обслуживание; aging предотвращает голодание обслуживания. Прерывание только в безопасных точках, cleanup не бросается ради мгновенной кнопки. Сроки ожидания клиента/сервера согласовать.

Read-only API отдаёт согласованные снимки с возрастом и ошибкой последнего обновления. Один producer/singleflight на снимок, независимость секций, ограниченное число чтений. Старые данные не означают «сейчас работает». Выход из аккаунта очищает DOM и кэш защищённых данных, поздние ответы прошлой сессии отбрасываются.

Сбой источника, checker или движка не должен мешать входу, переходу между страницами и постановке безопасного Stop. Процесс панели не убивается по кругу из-за journal fence; состояние приложения, runtime и доступность сервиса остаются разными.

## 13. E01–E02 — весь интернет выбранных LAN-сегментов и исключения

### E01. Основной режим и наследование

Для **новой** установки мастер явно предлагает `lan_except + all_except`: все устройства выбранных домашних сегментов наследуют общую политику, пока их не исключили. Имеющиеся альтернативы `selected_devices/selected_services` сохранить для миграции и явного advanced-выбора; они не являются default этого плана.

Пользователь видит общий охват перед первым включением. Guests, новые сегменты/VLAN и удалённые VPN-клиенты не добавляются скрыто. Устройство с новым MAC внутри уже согласованного домашнего сегмента может наследовать общую политику по выбранному правилу `NewDevices`; новый segment такого права не получает.

Старые установки сохраняют прежние настройки и доверие. При переходе к общему режиму — одна явная миграция, snapshot и проверяемый возврат. Не трактовать старый `AllLAN` для одного сервиса как разрешение глобального перехвата. Нулевое число выбранных сервисов не отключает общий путь.

### Правила обработки — одинаковые для всех исполнителей

Сначала сохранить системную связность: router UI/SSH, DHCP/ND/RA, локальные направления и доступ к transport bootstrap в явно определённой области. Затем:

1. Вне согласованного сегмента или исключённое устройство → базовая политика без вмешательства RAZVILKA.
2. Явное обязательное DIRECT сайта → базовый путь для соответствующей области.
3. Явный BYPASS, переопределяющий российский автосписок → выбранный разрешённый путь.
4. Российское автоматическое исключение → базовый путь.
5. Подходящий индивидуальный service override → его путь.
6. Всё остальное → общее автоматическое подключение.

Противоположные mandatory ручные правила не разрешать лексикографическим порядком ID. Показать конфликт и позволить одним изменением заменить противоположное правило. Простое добавление российского сервиса в наблюдение не отменяет его исключение. Промах scope/отсутствие/удаление service override продолжает правила общего пути, а не делает DIRECT.

Device exclusion обязателен одновременно для Xray/WG/AWG/WARP/USQUE/Sing-box/NFQWS2, сервисного Smart DNS и наследуемого общего DNS там, где он меняет политику клиента. Штатные firewall/parental control и внешняя базовая политика не отключаются.

### Идентичность и существующие соединения

Использовать наблюдаемые segment/interface/device/MAC/IP-family bindings; учитывать DHCP и IPv6 privacy addresses. Не угадывать устройство после смены MAC. Потеря данных о глобально исключённом устройстве не разрешает поглотить его catch-all правилом; сохранить последнее безопасное сопоставление/сузить только затронутую область, показать неопределённость.

Изменение исключения и смена default требуют определённой политики уже установленных flows. Нельзя обещать немедленный выход из обхода, пока старые conntrack/NAT/UDP sessions продолжаются. Ограниченно drain/reset только затронутых собственных соединений либо показать bounded convergence. Не очищать conntrack всей сети. Удаление override не закрывает чужие потоки.

### E02. Российские и ручные сайты

Списки exact/suffix/IP/CIDR и ручные overrides хранить раздельно от обновляемых данных. Российские определения банков, государственных, торговых, связи/медиа — независимо от галочек «выбранные сервисы». Обновление в пределах согласованной политики автоматическое; новый scope/trust и массовое расширение семантики требуют отдельного решения.

Все `.ru`, `.рф`, `.su` и GeoIP RU — отдельные расширенные опции. Включение `tld-ru` источником не скрывать внутри курируемых компаний. Для источника отсутствует подпись — это не signed; применить согласованный уровень доверия и локальные проверки.

Общий CDN-IP не подтверждает принадлежность сайта. Применять domain-aware разделение лишь при надёжно известном имени. При L3-only/своём DoH/ECH/прямом IP отсутствие доменной identity не решать тотальным DIRECT общего диапазона. Безопасное поведение и ограничение точности явно описать; возможные advanced FakeIP/sniffing — только через capability и собственные тесты, не обязательная магия.

Полные правила, переходы, coverage и классификация указаны в `GLOBAL_POLICY_SPEC_RU.md`. Общий режим не объявлять завершённым до тестов неизвестного сайта, нулевого списка сервисов, разных service scopes, российских исключений, второго физического клиента и отсутствия маршрутных петель.

## 14. D01–D02 — DNS/Smart DNS как часть рабочего пути

Существующий D1 развивать, не переписывать. Для Xray/WG/AWG затем WARP/USQUE расширить общий план DNS+маршрут+scope. DNS не становится «последней лабораторией» после всех остальных функций: после приоритетных движков это ранняя сквозная задача совместно с E1.

Разделить:

- кто и где разрешает домен назначения;
- через что идёт DNS-запрос;
- через что идёт прикладной трафик;
- обычный resolver и Smart DNS gateway.

Smart DNS может изменять путь к сервису; в UI его нельзя без пояснения называть обычным DIRECT только потому, что не поднят локальный TUN. Карточка показывает «Smart DNS · провайдер». Изучавшиеся Xbox DNS, Quad9, Control D, Cloudflare, Google, UncensoredDNS и другие — кандидаты с проверенной доступностью/транспортом, не гарантированный набор рабочего обхода. Прежние сведения о совместимости FlashStart/USQUE перепроверять, не превращать исторический результат в вечное правило.

Связанная проверка: фиксированные ревизии → выбранный DNS → A/AAAA/CNAME/TTL/negative response → соединение именно с проверенным адресом по выбранному executor → исходный SNI/Host → сертификат → проверка нужного сценария → единое применение → readback → post-check.

Нельзя после DNS-пробы незаметно заново разрешить имя через другой resolver и приписать успех выбранному. Один рабочий A не подтверждает все AAAA/UDP/CDN-адреса; показывать реальную область успеха, не требовать при этом невозможного доказательства всех динамических адресов сайта.

Если DNS успел примениться, а маршрут нет — общий rollback. Если readback DNS не совпал — не commit половины. Reboot и потерянный ответ восстанавливаются по факту собственных правил/процессов/настроек, не только по строке состояния.

Кэш и существующие соединения — отдельная стадия `pending_cache_convergence` с пределом ожидания; не бессрочный PASS и не немедленная авария. Разделение DNS-кэша по политикам клиентов там, где ответы отличаются. Исключённое устройство не получает сервисный Smart DNS, если оно исключено из обхода. Приложения со своим DoH или прямым IP могут не использовать перехват: показывать фактическую поддержку, не ломать чужое шифрование.

Bootstrap Cloudflare/загрузка feed/управление должны оставаться независимыми от ещё неработающего кандидата. Не менять DNS всего роутера из-за одного сервиса и не создавать новую регистрацию WARP из-за DNS-сбоя.

Address ledger: домен, тип совпадения, resolver/место разрешения, IP family, адреса, TTL/время, CNAME, network generation, service references. Обновлять порциями, не перестраивать весь dataplane для одного истёкшего домена.

Общий DNS-профиль относится к участвующим клиентам и обеспечивает обычный доступ незнакомых сайтов. Индивидуальный service DNS переопределяет его только в своём scope; excluded device/site следует согласованной базовой DNS-политике. Ошибка service scope возвращает общий DNS, не случайный системный resolver. Разделять кэш по policy/answer semantics. В shared executor одного и того же DNS-ответа нельзя приписать два разных egress без проверки.

Неподконтрольный DoH приложения остаётся частью его интернет-трафика и идёт общим транспортом, если не исключён. Но сервер не может обещать для него произвольные domain-only исключения без надёжной identity. Блокирование DoT/DoH — отдельная advanced-политика, не скрытый способ выполнить обещание «исключения всегда точные».

## 15. C01 — понятный локальный каталог сервисов

Три разных библиотеки: определения сайтов/сетей; подключения и подписки; рецепты NFQWS2. Не смешивать их под одним непонятным названием «источники».

Каталог открывается из локально сохранённого корректного снимка, встроенный минимум доступен без сети. Сначала список категорий с понятными именами, затем детали происхождения; пользователь не обязан разбираться в GitHub URL. Добавить сайт вручную можно из того же понятного потока.

Источник → ограниченная загрузка → проверка формата/схемы/происхождения → immutable normalized snapshot → просмотр изменений → продвижение по согласованной политике. Подпись и trust level отражаются честно: HTTPS и популярность не заменяют подпись. Большой список не заполняет весь реестр рабочих узлов.

Поддержать несколько адаптеров источников и последовательно разрешённые зеркала. Зеркала одного набора не считаются независимыми источниками доверия. Geo-Aggregator/HydraRoute — исследовать как сетевые каталоги; Hydra Launcher — только аналогия подключаемых источников, его игровые загрузки не являются доменами сервисов RAZVILKA.

Парсер сохраняет точные домены, домены с поддоменами и CIDR раздельно. Если обязательная доменная/IP часть отсутствует, не показывать полный импорт. Не расширять непонятные строки до больших префиксов и не выполнять внешний код/HTML/иконки из источника.

304 не продлевает service proof. Ошибка источника не очищает LKG и не удаляет выбранные сервисы. Обновление библиотеки не включает автоматически новые сервисы, не снимает manual pin и не даёт новые классы доверия.

В новом режиме каталог нужен для индивидуальных профилей и точных исключений, **не для перечисления всего доступного интернета**. Все новые/невыбранные записи библиотеки уже используют общий путь как обычные адреса, но не получают индивидуальные overrides, новых проверок и полномочий. Отказ GitHub не должен мешать открыть незнакомый сайт через сохранённый default.

Интерфейс показывает «на общем подключении», «индивидуальная настройка» и «без обхода» вместо двусмысленного одного enabled. Наличие российского определения в каталоге используется классификатором независимо от пользовательского выбора сервиса.

## 16. C02 — браузер VLESS/подписок и автоматическое пополнение

Оставить существующий NodeStore. Нужны все ключи, их происхождение/возраст/срок/последний сценарный результат/совместимые executors и привязки. Кнопки: проверить все VLESS, удалить подтверждённо нерабочие, удалить выбранные, удалить все; отдельная явная иконка удаления.

Массовая операция работает по всему подходящему набору, а не только видимой странице/первым 32 или 64 ID. Курсор и поколения feed переживают restart, reorder и 304. Дедупликация по семантике подключения/секретной identity, а не по красивому названию. Ошибка отдельной записи не обязана ломать весь допустимый пакет; частичный результат показывается.

«Удалить нерабочие» не удаляет INCONCLUSIVE/429/устаревший proof. Active/default-path/pinned/reserve/group/suspended/rollback refs защищены; удаление используемого материала требует заранее определённого согласованного действия. Временное исчезновение из источника не равно revoke.

Автоматический сценарий: выбран сервис → получить разрешённые candidates → проверить соответствие сервису → применить → наблюдать → найти замену после отказа → пополнить резерв. Никаких походов пользователя на сайт checker при каждом сбое. Секреты не отправляются внешним проверяющим сайтам.

Источники из обсуждения: kort0881, Goida, tiagorrg, CyberPortal CP и другие допустимые подписки — отдельные недоверенные адаптеры, не рекомендации доверять любому узлу. Публичные выходы только после сохранённого разрешения владельца; переход с собственного сервера на публичный не происходит скрыто.

DoD: 32 неисправных записи и пригодная 33-я; 304/429/503; пропавший и отозванный источник; заполненное хранилище; reorder; restart; появление нового D после исчерпания B/C; неизменный рабочий active при сбое загрузки.

Общий и индивидуальные пулы могут совместно ссылаться на узел без дублирования секрета. Резерв для всего интернета проверяется по общему traffic envelope; успех ChatGPT не делает TCP-only узел универсальным UDP-выходом. Сохранённое согласие на публичный узел для сервиса не даёт права отправить на него весь домашний интернет. Массовое удаление выводит полный список зависимых common/service/pin/rollback назначений до выполнения.

## 17. N01–N02 — NFQWS2 как самостоятельный адаптивный обход

Цель — удобство и устойчивость на уровне желаемого опыта z2k, но собственный lifecycle RAZVILKA. z2k — источник идей/одноразового импорта, не обязательный процесс, scheduler или владелец правил. Не переписывать Go на другой язык ради этого.

NFQWS2 — базовый локальный инструмент для подходящих протоколов/сервисов, не сайт и не обязательный универсальный внешний выход. Отдельная рабочая область настроек/стратегий сохраняется внутри единой навигации. Новая установка не запускает все движки сразу: готовит минимальную совместимую композицию под общий режим. Прежнее пожелание «по умолчанию оставить только NFQWS2-маршруты» не должно отменять последний default всего интернета; при несовместимости явно показать ограничение.

### N01. Сначала видимость и совместимость

Проверить реальные outgoing/response/retransmission, TCP/QUIC, IPv4/IPv6, policy scope, NFQUEUE и offload. Если движок не видит необходимые пакеты, новые стратегии не лечат причину. Глобально отключать ускорение всей сети нельзя по чужому примеру; нужен узкий обратимый платформенный эксперимент и замер скорости/CPU.

`Auto-hostlist` и `Auto-strategy` — разные разрешения. Выбор подбора стратегии не расширяет список сайтов автоматически. Отсутствующая политика устройства не превращает targeted scope во весь LAN.

### N02. Подбор и сохранение

Последний рабочий рецепт → небольшой совместимый набор → ограниченные вариации через существующую StrategyLab → изолированный тест → обычная транзакция → post-check. Никаких сотен тяжёлых процессов одновременно. Сохранять версию движка, порядок аргументов, Lua/assets/fake blobs, сетевой контекст и конкретный сценарий.

Пользовательские стратегии, списки и добавленные домены лежат отдельно от обновляемых стандартных данных и никогда не пропадают при обновлении. Рабочую стратегию закреплять с памятью по сети/сервису/типу трафика, а не навсегда для всех провайдеров.

YouTube web/video/googlevideo/QUIC, Discord web/media/voice и Telegram web/media/DC — разные сценарии. Для пользовательского приложения допустим согласованный локальный client harness; не читать личную переписку и не выдумывать media PASS из curl страницы.

Если разрешён только NFQWS2 — подбирать внутри него и сообщать границу. Если разрешены альтернативы — после подтверждённого отказа и бюджета передавать решение общему автопилоту. Внутренний подбор стратегии и внешний switch маршрута не меняют один поток одновременно.

При общем туннеле профиль «сервис через NFQWS2» требует согласованного вывода этого трафика на допустимый базовый путь и обработки нужных пакетов; иначе NFQWS2 может видеть лишь внешний шифрованный туннель. Компилятор задаёт порядок и исключает двойную обработку. Ни inner/outer packet visibility, ни успешный curl к сайту не заменяют реальные media/voice tests. Только NFQWS2 без общего совместимого транспорта не объявлять полным защищённым/туннельным охватом всего интернета.

## 18. T01 — WARP: одна управляемая регистрация, много совместимых представлений

Один понятный раздел WARP/Cloudflare, без двух несвязанных генераторов. Разделить регистрацию аккаунта/устройства, секреты WG и MASQUE, профиль, endpoint, DNS, формат экспорта/QR, scope и runtime.

Основной сценарий локальный: взять сохранённую регистрацию → проверить пригодность → подготовить профиль → проверить → применить. Изменение DNS/endpoint/MTU/формата экспорта не создаёт новую регистрацию. Существующая регистрация — не бесконечная гарантия: учитывать revoke/expiry/условия провайдера.

Внешняя регистрация требует отдельно сохранённого разрешения и условий сервиса; попытка и бюджет записываются до POST. Потерянный ответ — `pending/unknown`; не делать blind retry с новой identity. Сначала отличить DNS/WAN/endpoint/transport/credentials. Исчерпание нескольких UDP endpoint само по себе не доказывает необходимость нового аккаунта.

Endpoint-кандидаты ограничены, имеют источник/product/transport/family/server identity. Не сканировать огромные диапазоны и не путать «зеркало сайта генератора» с «входом туннеля». Малый RTT не гарантирует доступ к нужному сервису или желаемую страну выхода.

Локальный exporter WG/AWG-compatible/Mihomo/QR — по capabilities. Не обещать, что любой WG-профиль превращается в полноценный AWG-сервер. QR и конфиг содержат секреты: локальная генерация, явный экспорт, без внешнего QR-сервиса.

## 19. T02 — USQUE / MASQUE

Не писать протокол с нуля и не зависеть навсегда от устаревшего usque-keenetic. Поддерживать собственную управляемую поставку подходящего upstream с версиями/patch provenance/rollback.

H3/QUIC и H2 — отдельные transport candidates с проверяемыми endpoints и TLS/server identity. Поддержку конкретных полей/команд сверить с выбранной версией; открытый TCP/443 не равен MASQUE-tunnel PASS. Не отключать сертификат/pin ради подключения.

Сначала довести текущую SOCKS+sidecar схему, затем измерить native TUN и TCP-only L4 там, где они подходят. Не считать L4 заменой UDP-голосу. Маршрутизация/endpoint protection/ownership остаются у RAZVILKA.

События connect/disconnect могут будить reconciler, но не запускают вторую систему изменения сети. Позднее событие от старого процесса не выключает новое подключение. Crash без hook обрабатывает supervisor; backoff предотвращает restart storm.

WG и MASQUE credentials не смешиваются. Общую Cloudflare identity для нескольких исполнителей разрешать только после подтверждения совместимости, не по одинаковому названию WARP. Публичный генератор — не автоматическое решение отказа собственного bootstrap.

## 20. B01–B02 — Mihomo и HevSocks5Tunnel

Оба пожелания сохраняются, но не задерживают Xray/WG/AWG.

Mihomo: сначала выяснить, что реально есть — exporter, lab или управляемый runtime. Для объявленного executor обязательны native validation, controlled config, ownership, client scope, probes, Apply/recovery/rollback. Конфигуратор не является production-поддержкой.

HEV: рассмотреть заменяемый TUN↔SOCKS адаптер в существующем lifecycle. Измерить CPU/RSS/скорость/UDP/IPv6/reconnect на целевом роутере относительно текущего sidecar. Положительный чужой benchmark не является решением для всех моделей. Отсутствие выигрыша допускает optional backend; не размножать сложность ради наличия названия.

Profile overlay: исходный импорт сохраняется, управляемые defaults/DNS/scope применяются отдельно, итоговый конфиг проверяется. Не перезаписывать пользовательский оригинал и не терять обязательные transport-поля.

## 21. UX01 — интерфейс вокруг общего подключения и индивидуальных правил

Не делать третью панель и не пытаться исправить структуру одним поиском. Сохранить локальный HTML/CSS/JS и удачные существующие компоненты. Основные разделы: **Главная, Сервисы, Подключения, Устройства, События, Настройки**. Технические страницы — полноценные экспертные рабочие области с установкой/профилем/проверкой/Apply/наблюдением/откатом/обновлением/удалением, не пустые карточки.

### Главная

Первый блок: Автопилот и **общее подключение интернета**, использованный executor/profile, состояние и текущая задача. Отдельно: домохозяйство/сегменты, исключённые устройства, сайты и автоматические российские исключения. Ниже — индивидуальные сервисы, реальные проблемы, история. CPU/RAM ниже/сворачиваемо.

Пример демонстрационной копии: «Общий интернет — WARP, проверка пути 2 минуты назад; ChatGPT — отдельное подключение Xray; российские сервисы — без обхода». Это не надпись «проверены все сайты». Нулевое количество персональных сервисов не делает страницу пустой.

### Сервисы и действия

«Мои сервисы» показывает настроенные индивидуально приложения, явные исключения и ссылку на наследуемый общий путь. Одна кнопка добавления; пользователь может открыть библиотеку, ввести сайт либо загрузить список. «Удалить индивидуальную настройку» возвращает общий путь. «Без обхода» создаёт явное исключение. «Заблокировать сайт» — отдельная функция/политика, не побочный эффект удаления.

Проверка остаётся в карточке. Не путать удаление записи из библиотеки, выключение отдельного мониторинга, паузу автоподбора, снятие override и отключение интернета. Для групп ИИ используется metadata и отдельные service IDs/evidence/пути; общий выбор фиксирует текущий состав, не всех будущих. Новый участник после feed update просто наследует default до явного индивидуального действия.

### Подтверждения и повседневные формы

Навигация, чтение, обычная проверка, допустимое сохранение, обновление согласованных списков и автоматический failover — без модальных подтверждений. «Использовать» принимает одно intent, сервер сам выполняет необходимые стадии; внутренние preview/digest сохраняются для безопасности и объяснения, не заставляют человека поочерёдно нажимать пять кнопок.

Одноразовое либо контекстное согласие: первоначальный all-internet scope, расширение сегмента/trust, внешняя регистрация/ToS, необратимое удаление, reboot, отключение защиты. Обычное исключение устройства/сайта из обхода — одно действие с ясным состоянием/возможностью отмены; не повторять мастер. CAS и очередь проверяются сервером, а не ручной галочкой.

Пауза сохраняет применённые подключения; Stop явно показывает согласованное последствие для интернет-трафика, не маскируется паузой. При блокировке журнала остаются сведения и безопасный путь восстановления. Нужные настройки открываются сразу в точной области. Поиск с синонимами — дополнительный способ; основные действия находятся без знания терминов.

### Устойчивость

Снимки с возрастом, независимые секции, одно in-flight обновление, сохранённые черновики/фокус, отсутствие периодического перерендера формы. После logout очистить DOM/private cache и отбрасывать старые ответы. Desktop/mobile/клавиатура/Escape, два окна, медленные и частично отказавшие API проверяются на настоящем сервере и браузере. Не показывать «работает», если известен лишь process/TUN/old job success.

## 22. R01–R02 — Keenetic, диагностика и слабые роутеры

### R01. Сеть и причина отказа

NDM `ifstatechanged`/netfilter-события рассматривать как дополнительное пробуждение общего reconciler: debounce/dedup → новый согласованный snapshot → новое поколение сети → проверяемое восстановление. Hook не правит маршруты самостоятельно и не подменяет observer-proof. `event-drain` не лечить сбросом флага «всё известно» без повторного наблюдения.

Обнаруживать базовый WAN, резервные и сторонние туннели, не захватывая их. Route preview от лица выбранного клиента полезен, но `ip route get` не является доказательством фактического пакета. Показать отдельно ожидаемый маршрут и наблюдённый результат.

Fast health дешёвый, deep diagnostics запускается ограниченно при повторяющейся проблеме. Классы: WAN/DNS/endpoint/auth/runtime/rules/TLS/MTU/IPv6/UDP/service/observer. Не все выводы доступны по одному HTTP-коду: например, отказ сайта не всегда однозначно означает региональную блокировку. Confidence и причина остаются видимыми.

MTU, keepalive, QUIC socket buffers и ускорение — диагностика по capabilities и измерениям, не универсальный sysctl-рецепт из VPS для старого роутера. Не отключать IPv6 всей сети только потому, что один executor не проверен.

### R02. Общий ресурсный бюджет

Пользователь просил не обрезать функции на слабых роутерах, а давать больше времени и работать порциями. Настроить adaptive batch size/concurrency, общий предел временных процессов, памяти, дисковых операций и сетевых проб. Включённый manual limit — верхняя граница, не обязанность исчерпать его.

Не назначать универсальные «MIPS=1, ARM64=4» как окончательные нормативы. Использовать измерения CPU/load/MemAvailable/трафика и стоимость действия. Несовместимый архитектурно runtime честно недоступен; недостаток текущего ресурса обычно означает очередь/меньшую партию, а не удаление всей возможности.

Панель без активного пользователя можно реже обновлять, не замедляя аварийное восстановление маршрута. Сохранять cache invalidation по ревизии/байтам, а не доверять неизвестному содержимому. Метрики и история — bounded, flash-friendly. `GOMEMLIMIT` рассматривать после замера всей цепочки с движками и sidecar, не задавать число вслепую.

Общий путь увеличивает нагрузку относительно service-only. Замерять всю цепочку с прокси/sidecar и клиентским трафиком, не переносить цифры idle одного Go-процесса. Дедупликация route-check учитывает реальные значимые selectors (family, mark, ingress, protocol/ports при зависимой политике), а не безусловное допущение «любые два потока к одному IP идут одинаково». Не подтверждать policy simulation как packet proof.

Ресурсный отказ означает ожидание, меньше одновременных candidates и checkpoint/resume. Если платформа физически не поддерживает runtime/ядро/protocol, честно показать unsupported и разрешённый запасной путь — нельзя обещать, что дополнительное время реализует отсутствующую возможность.

## 23. M01–M02 — обновления и обслуживание без ручного ремонта

### M01. Используемый компонент можно управляемо обновить

Сценарий NFQWS2 из отчёта Claude — обязательный регрессионный пример [S3]: компонент занят маршрутами → согласованный резерв либо ограниченное отключение нужного scope → snapshot → обновление проверенного пакета → принять ожидаемый новый init как часть transaction → validation → восстановление маршрутов → post-check → commit/rollback.

Текущая ручная команда adoption не становится безусловным доверием любому изменённому файлу. `opkg .list` подтверждает запись пути, но не происхождение байтов. Обновление собственных package receipts, schema и runtime identity должно быть согласовано. Не делать общий `opkg upgrade`.

Та же модель для Xray/sidecar/WG tools/USQUE; загрузка AWG kernel module имеет отдельные условия, запрет вмешательства в чужие интерфейсы и reboot authority.

### M02. Автоматическое обслуживание

В мастере одноразово выбрать время/окно/дни/часовой пояс и разрешённые действия: проверка, подготовка, установка приложения, установка компонентов, обновление списков/стратегий/DNS. Существующий check/prepare не называть unattended install.

Путь: trusted source → точный release/asset manifest → hash и подтверждение происхождения → совместимость модели/архитектуры/ядра/схем → подготовка → snapshot → активация → проверка приложения и требуемых маршрутов → commit либо независимый rollback helper.

Helper работает даже если новая панель не стартует. Bad release quarantine; рабочие конфиги/секреты/user lists сохраняются. Миграция и downgrade тестируются. Не удалять rollback copy, пока на неё ссылается pending операция. При запрете reboot/установки — честное ожидание, не обход политики.

Отказ источника не ломает действующий путь; приложение не обязано сразу ставить любой последний upstream. Pin версии и отложенное обновление остаются доступны.

Update impact включает общий путь: общий runtime не отключается «потому что выбранные сервисы его не используют». Сначала проверить refs default/service/reserve/rollback и авторизованный резерв. При отсутствии резерва обновление, требующее простоя всего интернета, выполняется только в согласованное окно/по отдельному выбору. Фоновый check источников не должен каждый раз занимать тот же exclusive как Apply.

## 25. H01–H02 — приёмка именно общего режима

У каждого требования отдельные поля: implementation, unit, integration, native, hardware по platform, soak, release. Все новые кейсы этого пакета имеют `not_run`; проверка структуры плана не является проверкой программы.

### Обязательная сквозная матрица

Два физических клиента: включённый и исключённый. Включённый открывает новый домен вне каталога, прямой IP, использует общий default и отдельный service override. Исключённый остаётся в базовой политике. Российский невыбранный сервис идёт без обхода, пользовательский override работает. Удаление индивидуальной настройки возвращает default, а суженный scope сервиса не выводит остальных клиентов из общего режима.

Проверить ноль выбранных сервисов, новый DHCP-клиент внутри принятого сегмента, гостевой сегмент, изменение MAC/IP/IPv6, общий CDN-IP с противоположными правилами, свой DoH/ECH/неизвестное имя, TCP/UDP/QUIC/IPv4/IPv6/прочие пакеты согласно coverage. Неизвестное имя не означает DIRECT; unsupported класс имеет явный исход. UI/SSH/DHCP/ND/bootstrap не теряются из-за catch-all.

### Исполнители и отказ

Для Xray/WG/AWG: install/detect → профиль/capabilities → isolated probe → scoped default+service Apply → readback → клиентские сценарии/negative control → Stop → bad candidate rollback → runtime/WAN loss → restart/reboot. Native validation не равно HIL; tests с подставным executor — не запуск реального движка.

Default A падает, отдельный рабочий service B сохраняется. Затем B падает при исправном default: меняется только B либо разрешённо наследует default. Для обоих назначений A→B Apply FAIL→safe rollback→C PASS и последующее пополнение D. Ошибка общего checker не вызывает массовый failover. Существующие TCP/UDP sessions проверяются отдельно, а не только новые короткие curl.

### Среда и длительность

SIGKILL и штатный restart, firewall rewrite, observer loss, clock jumps/DST, диск заполнен, ошибки write/rename/fsync, прерывание journal generation, повтор job/потеря HTTP response, revoked consent, 429/503/304/corrupt feeds, low RAM/CPU pressure. Разрушительные воздействия — только в согласованной изоляции с возвратом.

Начать AArch64, затем физические MIPS/MIPSel и отдельно OpenWrt. Нет железа — сохранить `not_run` и воспроизводимые инструкции, продолжить другие этапы. Не создавать платные VPS или аккаунты ради галочки без разрешения.

После функциональной приёмки: 24 часа, затем 72 часа с закрытым браузером и намеренными отказами. Измерять нагрузку всей цепочки, throughput/latency under load, RAM/FD/processes, flash writes, false switches, recovery/Stop/API latency и число ручных вмешательств. Успех означает автоматическое восстановление в разрешённых сценариях, не гарантию работы любого сайта при любой внешней блокировке.
