# RAZVILKA v0.0.8: безопасная лабораторная миграция

Цель — проверить новый control plane рядом с установленным ARTEM Flow v0.0.6, не заменяя рабочий бинарник, init-скрипт и конфигурацию до отдельного подтверждения.

## Текущее состояние

- Рабочий экземпляр: ARTEM Flow v0.0.6 на `192.168.1.1:8787`.
- Safe Mode включён, pending changes отсутствуют.
- Кандидат: RAZVILKA v0.0.8-security-gate.
- Архитектурный бинарник для роутера: `razvilka-linux-arm64`.
- Кандидат должен слушать `192.168.1.1:8788`.

## Проверено на Netcraze / Entware

На реальном arm64-роутере пройдены следующие gates без изменения рабочего ARTEM Flow:

- strict config preflight и legacy schema `0 -> 1` в dry-run;
- отказ обновления при работающем ARTEM Flow без `--from-artem-flow`;
- side-by-side start/status/idempotent start/stop на порту 8788;
- boot-guard: три ошибки, блокировка с кодом 2 и явный сброс;
- fake-root apply на 8789 и ручной rollback;
- failure injection через конфликт 8787 и автоматический rollback;
- встроенный health-check отклоняет ответ ARTEM Flow v0.0.6 как чужую identity;
- после каждого сценария слушал только рабочий 8787, а SHA256 его бинарника, init и config совпадали с исходными.

## Запрещено на этапе candidate

- заменять `/opt/bin/artem-flow`;
- изменять `/opt/etc/init.d/S99artem-flow`;
- отключать или перезапускать существующие nfqws2/usque/туннели;
- менять firewall, DNS, policy routing или default route;
- переносить старую конфигурацию без schema review;
- удалять backup или старый бинарник.

## Этап 1 — read-only preflight

1. Зафиксировать SHA256 текущего бинарника, init-скрипта и конфигурации.
2. Сохранить status API, список процессов, маршруты, DNS, iptables/nftables и занятые порты.
3. Проверить свободный порт 8788, RAM и место в `/opt`.
4. Сверить SHA256 arm64-кандидата с локальной сборкой.
5. Создать отдельные каталоги `/opt/etc/razvilka-candidate` и `/opt/var/lib/razvilka-candidate` с `umask 077`.

## Этап 2 — параллельный candidate

Кандидат использует только отдельные пути; ручной запуск ниже оставлен для диагностики:

```sh
/opt/bin/razvilka-v0.0.8-candidate \
  -config /opt/etc/razvilka-candidate/config.json \
  -catalog /opt/etc/razvilka-candidate/service-catalog.json \
  -sources /opt/etc/razvilka-candidate/sources.json \
  -cache /opt/var/cache/razvilka-candidate \
  -stage /opt/var/lib/razvilka-candidate/staging \
  -backups /opt/var/lib/razvilka-candidate/backups \
  -token-file /opt/etc/razvilka-candidate/admin.token \
  -listen 192.168.1.1:8788
```

Для Entware использовать `scripts/start-candidate-entware.sh` и `scripts/stop-candidate-entware.sh`: launcher работает через BusyBox `start-stop-daemon` и не требует `nohup`.

Обязательные проверки:

- GET `/api/v1/status` возвращает v0.0.8, Safe Mode и `auth_required=true`;
- mutation без токена возвращает 401;
- mutation с токеном и правильным Origin проходит;
- token-файл имеет права 0600 и не является symlink;
- ARTEM Flow на 8787 продолжает отвечать;
- маршруты, DNS и firewall до/после идентичны;
- перезапуск candidate сохраняет токен и валидную конфигурацию;
- повреждённый source cache не становится Ready;
- остановка candidate не влияет на доступ в интернет.

## Этап 3 — наблюдение

Candidate работает минимум один полный цикл наблюдения без активного dataplane:

- контроль RAM/CPU и числа goroutine/file descriptor;
- refresh источников;
- staging/validate/discard конфигов;
- service draft/apply/discard только в manager state;
- reboot test выполняется лишь после появления отдельного candidate init-скрипта;
- Linux race CI должен быть зелёным.

## Транзакционная миграция

Dry-run не меняет файлы и сервисы:

```sh
./scripts/upgrade-entware.sh --dry-run --from-artem-flow
```

Apply разрешён только после зелёных gates и создаёт snapshot до остановки старого сервиса:

```sh
./scripts/upgrade-entware.sh --apply --from-artem-flow
```

Init выполняет встроенный HTTP health-check с таймаутом 4 секунды и сверяет имя, версию и PID отвечающего процесса с pidfile. Три неудачных запуска за 300 секунд создают `/opt/var/lib/razvilka/boot-disabled`; состояние проверяется командой `guard-status`, сброс выполняется только вручную через `clear-guard`.

Ручной rollback:

```sh
./scripts/rollback-entware.sh "$(cat /opt/var/lib/razvilka/current-backup)"
```

Snapshot хранит прежние файлы и признаки того, какой сервис работал до миграции. Rollback восстанавливает только сохранённое состояние и не включает движки обхода.

## Gate перехода

Замена v0.0.6 разрешена только когда одновременно готовы:

1. Linux race CI.
2. Arm64 candidate smoke на порту 8788.
3. Schema migration с dry-run и backup.
4. Init-скрипт с boot-loop protection.
5. Команда rollback, возвращающая старый бинарник и init без изменения движков.
6. Сравнение preflight до/после.
7. Отдельное подтверждение владельца на переключение порта 8787.

## Rollback candidate

На side-by-side этапе rollback — остановка процесса v0.0.8. После транзакционного apply используется `rollback-entware.sh`: старый ARTEM Flow, его init-скрипт, конфигурация и прежнее running-state восстанавливаются из root-only snapshot; движки обхода не изменяются.
