# Безопасное восстановление WARP · MASQUE / USQUE

## Что показал реальный эксперимент

На тестовом роутере повторная регистрация USQUE при временном использовании
Quad9 привела к рабочей сессии. Это полезный подтверждённый сценарий ремонта,
но не доказательство, что Quad9 всегда меняет страну или POP WARP. DNS способен
повлиять на разрешение регистрационных endpoint, тогда как фактический выход
Cloudflare преимущественно выбирается её anycast-маршрутизацией.

Дополнительная памятка по установке и восстановлению от 2026-08-27 разобрана
и сверена с upstream USQUE/usque-keenetic. Подтверждённые upstream возможности
отделены ниже от практических, но не универсальных наблюдений конкретных сетей.

Официальный `usque` разделяет регистрацию аккаунта и запуск MASQUE в режимах
SOCKS/native TUN. `usque-keenetic` дополнительно управляет собственным init-
сервисом и интерфейсом. RAZVILKA не должна одновременно запускать пакетный TUN
и свой кандидат на той же сессии.

## Запрещённый упрощённый вариант

Нельзя реализовывать мастер как последовательность:

1. безусловно заменить `/etc/resolv.conf`;
2. удалить `/opt/etc/usque/session.conf`;
3. запустить сервис;
4. надеяться, что интернет работает.

Такой сценарий затрагивает весь роутер, теряет last-known-good и при сбое может
сломать DNS и доступ одновременно.

## Контракт candidate-транзакции

### 1. Диагностика без записи

- проверить пакет, единственность opkg feed и поддерживаемую архитектуру
  (`aarch64`, `mips`, `mipsel`);
- проверить время, CA, свободное место и общий HTTPS;
- прочитать только `IFACE`, `IFACE_IP`, `IFACE_MASK`, `SNI`,
  `HTTP2_ENABLE` и `CONFIG_VERSION` из `usque.conf`;
- проверить `/bin/ndmc` с обычным окружением и отдельно с
  `LD_LIBRARY_PATH=/lib:/usr/lib`; не менять путь библиотек глобально;
- обнаружить зависший `OpkgTun0/opkgtun0`, но не удалять его автоматически;
- отдельно проверить системный DNS и Quad9 `9.9.9.9` / `149.112.112.112`;
- разрешить регистрационные имена Cloudflare через каждый кандидат DNS;
- необычный ответ Smart DNS считать пригодным только после нормальной проверки
  TLS-сертификата; никогда не использовать `curl -k`/`--insecure`;
- проверить Cloudflare API, MASQUE endpoint UDP/443 и HTTP/2 endpoint TCP/443;
- определить работающий пакетный runtime и RAZVILKA-owned runtime;
- прочитать только публичные `endpoint_v4`, `endpoint_v6`, `endpoint_h2_v4`,
  `endpoint_h2_v6`; ключи, license и access token не возвращать в UI или лог;
- показать маршрут до MASQUE endpoint и отдельно предупредить об IPv6, способном
  уйти мимо настроенной только для IPv4 политики.

### 2. Snapshot

- сохранить текущий `session.conf`, `usque.conf`, состояние init-сервиса,
  RAZVILKA runtime/policy и точное состояние DNS;
- выставить права `0600`, записать digest и transaction ID;
- не удалять и не переименовывать единственную рабочую копию до создания
  проверенного кандидата.

### 3. Изолированная регистрация

- создать профиль-кандидат в каталоге RAZVILKA, а не в live-пути;
- использовать явный путь конфигурации и отдельный рабочий каталог;
- сначала применить выбранный DNS только к изолированному процессу. Если
  платформа этого не позволяет, временная глобальная замена допустима только
  под эксклюзивной блокировкой, с atomic write, watchdog и безусловным restore
  сразу после завершения регистрации;
- не трогать DNS Keenetic/DHCP и не оставлять Quad9 включённым скрытно;
- учитывать Cloudflare rate limit и cooldown, не запускать бесконечные повторы.

### 4. Проверка кандидата

- строгая проверка JSON и обязательных полей без вывода секретов;
- запустить candidate USQUE SOCKS на отдельном loopback-порту;
- подтвердить реальный процесс, соединение с endpoint и трафик через SOCKS;
- получить Cloudflare trace и подтвердить `warp=on`, egress IP, `loc` и `colo`;
- проверить минимум Telegram Web, Telegram API/Core и Telegram CIDR; позднее —
  MTProto, media и voice;
- сравнить с last-known-good. Новая сессия не считается лучше только потому,
  что регистрация завершилась успешно.

Текущий профиль сначала проходит более дешёвую проверку без перерегистрации:
RAZVILKA наследует безопасный SNI пакетной установки, запускает отдельный SOCKS
и последовательно проверяет QUIC и HTTP/2. В рабочее состояние попадает только
транспорт, через который получен реальный ответ назначенного сервиса. Строка
`Connected to MASQUE server` сама по себе доказательством доступа не считается.

Проверка `warp=on`, `colo`, `loc` и egress IP описывает состояние Cloudflare,
но не заменяет проверку Telegram или другого назначенного сервиса. `warp=on`
с `colo=DME/loc=RU` может быть технически исправным туннелем, который не решает
пользовательскую задачу.

### 5. Canary, commit или rollback

- canary направляет только выбранный тестовый сервис/устройство;
- commit разрешён после повторяемого service evidence;
- при любом timeout, отмене запроса, падении процесса или ухудшении сервиса
  восстановить старую сессию, DNS и исходный runtime;
- после commit сохранить старую сессию ограниченное время для быстрого отката;
- журнал показывает причину, старый/новый egress без credentials и результат.

## Интерфейс мастера

Обычный пользователь видит:

1. **Проверить WARP · MASQUE**
2. Причина: DNS регистрации / API / ключ / UDP / TCP fallback / сервис
3. **Создать безопасный кандидат**
4. **Проверить через Telegram**
5. **Заменить рабочую сессию** или **Оставить прежнюю**

Расширенный режим показывает endpoint, транспорт, egress, страну/ASN, latency,
доказательство маршрута и журнал отката, но никогда не отображает приватный
ключ, license или access token.

До мастера восстановления нужен отдельный безопасный **USQUE Doctor**:

- пакет и версия;
- конфигурация и выбранный QUIC/HTTP/2 без секретов;
- целостность сессии без вывода ключевого материала;
- состояние init-сервиса и TUN;
- совместимость `ndmc` с библиотеками Entware;
- доступ к Cloudflare API и маршрут до публичного endpoint;
- понятная следующая рекомендация без автоматического ремонта.

## Лестница восстановления

1. Не удалять `session.conf` и не переустанавливать пакет.
2. Проверить конфигурацию, `ndmc`, TUN и доступ к Cloudflare API.
3. Исправить bootstrap NFQWS2/SNI только после отдельной проверки.
4. Проверить текущую сессию через QUIC и HTTP/2.
5. Проверить `warp=on`, затем конкретный сервис и IPv4/IPv6.
6. Лишь после snapshot пробовать другой DNS и новую регистрацию-кандидат.
7. Если DNS не меняет неподходящий POP, не повторять регистрацию бесконечно.
8. Маршрут только до MASQUE endpoint через внешний VPN рассматривать как
   расширенный chained-транспорт: обязательны защита endpoint внешнего VPN от
   routing loop, отдельный canary и явное подтверждение пользователя.

## Критерии готовности

- тесты успешной регистрации, timeout, rate limit, повреждённого кандидата;
- kill/cancel на каждой фазе с восстановлением DNS и сессии;
- конфликт пакетного TUN и RAZVILKA SOCKS исключён;
- новая сессия проверена именно через выбранный маршрут;
- Telegram подтверждён не одной веб-страницей;
- ARM64 и минимум MIPS/MIPSLE проверены на реальном Keenetic/Netcraze.

## Проверенные первичные источники

- [Upstream USQUE](https://github.com/Diniboy1123/usque): режимы SOCKS/TUN,
  регистрация, SNI, QUIC и HTTP/2, публичные endpoint и чувствительные поля.
- [usque-keenetic](https://github.com/side-effect-tm/usque-keenetic): opkg feed,
  конфигурация `SNI`/`HTTP2_ENABLE`, init-сервис и архитектуры Keenetic.
