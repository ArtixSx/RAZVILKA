# Проверка предложений по ускорению Автопилота — 22 октября 2026

Архив `RAZVILKA_Autopilot_Acceleration_2026-10-22_r1.zip` подходит как
план измерений и улучшений. Это не готовое исправление: в шаблоне измерений
указано `NO_MEASUREMENTS_PROVIDED`, а действия помечены как предложения.
Ускорение на конкретный процент или готовность к выпуску архив не доказывает.

## Что уже есть в исходниках

| Предложение | Текущее состояние |
| --- | --- |
| Сразу использовать первый пригодный узел | `autonomy_first_usable.go` и `nodestore.SearchFirstUsable` проверяют точный результат и запускают обычное применение, не ожидая проверки всего каталога |
| Предпочитать свежий рабочий результат | Приоритет очереди уже учитывает свежесть. Перед применением результат проверяется повторно; старый успех не даёт разрешения на новый маршрут |
| Сохранять прогресс перебора | Хранится ограниченный снимок очереди с курсором, привязанный к сервису, сети, исполнителю и политике |
| Подгружать полезные источники порциями | `autonomy_refill.go` использует историю источников, предел очереди и сохранённые сроки повторов. HTTP 304 не продлевает свежесть старого списка |
| Отделять отмену и ошибку среды от плохого узла | Такие исходы не должны ошибочно ухудшать историю всех кандидатов; для них есть отдельные проверки |

## Что подтвердилось на чистой установке

На `rc.51` (`a0bad5c5`, ARM64) разрешённые источники «Игорёк» загрузились
автоматически. Автопилот сам проверил и применил VLESS для Telegram.
Короткая трёхминутная проверка с ПК дала 6/6 HTTPS и 6/6 начальных обменов
MTProto; путь к официальному IP проверен отдельно. Это не сравнительный
замер скорости, не подтверждение независимого резерва и не часовая приёмка.

В последующем 15-минутном наблюдении HTTPS прошёл 25/30 раз, начальный
обмен MTProto — 24/30. Независимый резерв к этому времени не был подтверждён.
Отдельно обнаружена остановка фоновой очереди с `writer-busy`; доступность
панели и свежесть её снимка не означали, что новые задачи выполняются.
Эту ошибку нужно устранить до оценки ускорения и автоматического переключения.

В текущем координаторе выполняется один сервис за раунд. При восьми
сервисах фактическое ожидание следующей проверки может превышать указанный
интервал сервиса. Перед ускорением нужно измерять всю задержку от постановки
задачи до результата на клиенте, включая очередь, проверку и применение.
Время отдельного HTTP-запроса не заменяет этот показатель.

## Порядок дальнейшей работы

1. Завершить исправления первого запуска NFQWS2 и отображения актуального
   состояния. Ускорять повторяющийся отказ вместо исправления причины бессмысленно.
2. На одной зафиксированной сборке записать полное время холодного и повторного
   подбора, восстановление после отказа, отмены, ошибки и нагрузку роутера.
   Отдельно учитывать медленную флешку и ожидание внешнего источника.
3. По результатам измерений менять порядок очереди и задержки координатора.
   Сохранять справедливость между сервисами и возможность немедленной остановки.
4. Общий тестовый процесс для нескольких VLESS и повторное использование
   окружения NFQWS2 рассматривать только после базовых замеров. Потребуются
   отдельные доказательства изоляции кандидатов, очистки портов и ограничения
   памяти; это не небольшое изменение таймера.

Проверку точного выхода, TLS, границ сервиса, исключений и отката нельзя
убирать ради красивой цифры. Для текущего сценария VLESS проверка выхода
является частью подтверждения пути. Быстрое открытие сайта по обычному
интернету не должно объявляться работой выбранного прокси.
