# Журнал восстановления приватного импорта — основа PR-1.1

Локальный блок 31 августа 2026 года. Реализован `internal/restorejournal`:
файловый протокол восстановления, проверенный на изолированных хранилищах.
**Он ещё не подключён к App, HTTP-импорту и запуску роутера.** Рабочее поведение
панели осталось прежним; общий импорт аккаунтов Cloudflare по-прежнему закрыт.

## Протокол

До первой записи целевого файла журнал сохраняет полный ограниченный план:
состояние до и после каждого изменения, уникальный ID операции, версию формата,
контрольную сумму и привязку к конкретным хранилищам. Пустой файл отличается
от отсутствующего. В журнале нет путей назначения, команд или URL: имена целей
разрешает только набор адаптеров, переданный доверенным кодом при запуске.

| Состояние журнала | Действие после перезапуска |
|---|---|
| `idle` или журнал отсутствует | Восстанавливать нечего |
| `prepared` | Вернуть только записи, всё ещё совпадающие с новым снимком, в обратном порядке |
| `committed` | Проверить новые состояния и завершить операцию, не откатывать её |
| Повреждённый/неизвестный журнал или третье состояние цели | Остановиться, сохранить журнал и данные для разбора |

Перед восстановлением проверяются **все** цели. Если обнаружена более новая
правка, ни одна цель на этом проходе ещё не изменяется. Каждая последующая
замена дополнительно проверяет ожидаемое состояние. При ошибке в середине
отката уже восстановленные записи распознаются на следующем запуске; операция
продолжается без повторного затирания. Перед очисткой плана проверяется результат.

Отдельная запись `committed` выполняется только после завершения и проверки
всех целевых записей. Если сохранение этой отметки вернуло ошибку, решение
не угадывается: запись могла успеть сохраниться. Журнал перечитывается при
восстановлении. Отметка `committed` запрещает откат уже подтверждённой операции.
После завершения план заменяется небольшим `idle`, без приватных снимков.

Подготовленный журнал нельзя заменить новым импортом. Отмена запроса до записи
ничего не меняет; между записями запускает ограниченную по времени компенсацию.
Если последняя цель уже записана, позднее отключение клиента не отменяет
завершение операции. Незавершённый откат остаётся повторяемым.

## Файлы и защита

- Корень журнала заранее создан и принадлежит приложению; POSIX-права каталога
  `0700`, файлов `0600`. Сам модуль не создаёт произвольные каталоги по архиву.
- Постоянный `.restore.lock` и системная блокировка Linux/Windows удерживаются
  до закрытия Journal. После смерти процесса блокировка освобождается ядром;
  файл не удаляется и не заменяется. Пустые/старые/неизвестные маркеры не чинятся
  автоматически. Сбой первой инициализации может потребовать ручного разбора.
- Журнал читается с лимитом и проверкой обычного файла. Linux использует
  nonblocking/no-follow open; это исключает ожидание данных из FIFO при открытии.
- Только канонический внутренний JSON текущей схемы: повторные, неизвестные,
  неоднозначные по регистру поля, лишний JSON, неверные ID/порядок/суммы
  отклоняются. Повреждённый файл не удаляется и не заменяется новым планом.
- До 64 целей, до 4 МиБ на снимок, до 8 МиБ суммарно на старые и новые данные,
  до 12 МиБ сериализованного журнала. Более крупный архив потребуется отклонить
  при подготовке будущего общего плана, не записывать частично.
- `scope` — SHA-256 доверенной привязки ID к корням, именам и версиям форматов.
  Адаптер запуска обязан вычислять его из фактической конфигурации, а не брать
  из архива. Несовпадение не позволяет восстановить план на другой набор файлов.
- Ошибки возвращают фиксированные коды/тексты, без исходных приватных данных
  и путей. Форматирование Journal/Image скрывает содержимое. Сами структуры
  со снимками не являются HTTP/audit DTO и не должны сериализоваться в них.

Контрольная сумма обнаруживает повреждения, но не является подписью и не
защищает от root, который может переписать и данные, и сумму. Снимки локально
не зашифрованы: защита соответствует правам private state. Замена на `idle`
не гарантирует физического стирания старых блоков диска; прерванные временные
файлы не удаляются по маске. Для их безопасного учёта нужен отдельный контракт.

На Linux после атомарной записи синхронизируется и файл, и открытый каталог.
Новый `ownedfs.Root.Sync()` не меняет поведение старых вызовов `WriteAtomic`.
На Windows синхронизируется файл; backend предназначен для разработки и
проверки сбоя процесса, **не** обещает устойчивость directory entry при потере
питания. Неподдерживаемые ОС не получают небезопасный запасной способ записи.

## Что проверено

- Успех, отсутствие изменений, повторное восстановление, отсутствующий/пустой
  файл, отказ до и после каждой целевой записи.
- Отказ до и после сохранения `prepared`, `committed`, `idle`: результат
  восстанавливается по тому, что действительно записано, а не по прежней ошибке.
- Ошибка каждого шага отката и повторный запуск; поздняя чужая правка во время
  отката; запрет нового плана при незавершённом старом; отмена запроса.
- Усечённый, слишком большой, повреждённый и чужой журнал; неверные scope,
  schema, checksum, цели и порядок; неизвестные/повторные поля и лишний JSON.
- Два открывающих журнал writer: второй не допускается. Неизвестные маркеры
  остаются нетронутыми; после сбоя используется тот же файл блокировки.
- Реальный отдельный процесс принудительно завершался после подготовки,
  каждой из трёх целевых записей, commit и очистки. Затем проверено восстановление.
  Дополнительно процесс завершался в каждой точке частичного отката; следующий
  запуск доводил его до конца. Всё на синтетических файлах в test TempDir.
- Пакет журнала прошёл 10 повторов на Windows. Полный `go test ./... -count=1
  -timeout=90s`, `go vet ./...` и пять JS regression suites прошли.
- Go-пакеты и тестовые бинарники restorejournal/ownedfs/cloudflareprovider/App
  собраны для Linux arm64/mips/mipsle. Linux-only FIFO/symlink/POSIX tests
  скомпилированы, но локально не выполнялись.

Отключение питания, Linux runtime/race, Entware shell regression и HIL не
проверялись. Принудительное завершение процесса в тесте не заменяет эти проверки.

## Следующий шаг — подключение к настоящим хранилищам

1. Реализовать адаптеры config/catalog/devices/staging/provider: ограниченное
   чтение, точный compare-and-swap, атомарная запись и flush. Тестовые file targets
   этого блока **не** являются такими адаптерами и не подключаются к App.
2. Обеспечить исключительное владение со стороны **всех** изменяющих API,
   фоновых задач и других процессов. Блокировка журнала сама по себе не запирает
   существующие менеджеры. Их отдельные mutex и кэши пока не дают этого контракта.
3. Запускать восстановление до загрузки изменяемых кэшей/фоновых задач и открытия
   API. При неизвестном состоянии не разрешать новые изменения поверх него.
4. Подключить полный приватный архив с preview/revision review и совместимостью
   версий. Только затем снимать запрет `ProviderSnapshots` в общем импорте.
5. Проверить fault injection на реальных адаптерах, Linux CI/race и аппаратный
   reboot/power-loss до объявления стабильности.

Протокол не обеспечивает изоляцию нескольких файлов для читателей, не
применяет рабочие маршруты, не регистрирует аккаунты и не управляет WARP/USQUE.
В этом блоке GitHub, UI, настройки роутера и зависимости не изменялись.
