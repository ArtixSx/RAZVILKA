# Cloudflare: адаптер восстановления копий аккаунтов

Локальный этап 31 августа 2026 года, продолжение PR-1.1 после staging (`d1ab62c`).
Это работа с сохранёнными копиями аккаунтов, **не ремонт подключения WARP**.
Регистрация, DNS, исходные USQUE/wgcf/WireGuard-файлы и runtime не меняются.

## Реализовано

- `cloudflareprovider.OpenRestoreTarget` открывает только доверенный каталог
  provider и фиксированный `accounts.private.json`. Его можно открыть до
  обычного `OpenStore`; создавать каталог по данным архива нельзя.
- Используется существующая постоянная `.import.lock`, а не отдельная новая
  блокировка, которую прежние writers не замечают. `ImportSnapshot`, отдельное
  восстановление архива и recovery target исключают друг друга между Store
  и процессами. Старые неизвестные/частичные маркеры не удаляются и не чинятся
  автоматически. Подготовка может создать только постоянный протокольный маркер.
- `Store.BeginRestore` возвращает target-сессию, удерживающую gate, mutex Store
  и ту же OS lease. Она не ждёт другой операции при захвате; `Close` освобождает
  владение. Обычные вызовы того же Store используют свой прежний gate/context.
- `Read` возвращает точные ограниченные байты; `CompareAndSwap` сравнивает их
  с ожидаемым состоянием и не затирает неизвестную последующую правку.
  Содержимое закрытого target недоступно. Логи target/Image не раскрывают ключи
  или путь; Binding — hash доверенного корня, имени и версии формата.
- Отсутствующий файл — допустимое пустое хранилище. Пустой **существующий**
  файл, повреждённая структура или невалидные аккаунты отклоняются, а не
  превращаются молча в пустой список. Undo сохраняет исходное форматирование
  и неизвестные поля byte-exact, не пересоздавая файл из модели.
  Исправлен прежний случай `{}`/`null`/отсутствующего schema/owner: значения
  пустого Store больше не подставляются при чтении существующего документа.
- `MergeImage` только готовит образ для общей транзакции. Он использует те же
  проверки/merge, что отдельный архив: существующие копии сохраняются, одинаковые
  ID с другими ключами дают конфликт, дубликаты и чужой provider отвергаются.
  При отсутствии новых копий сохраняются исходные байты без перезаписи.
  Новые копии остаются `imported-unverified` и не становятся рабочим обходом.

## Запись и ограничения

Обычные provider writers и новый target используют общий атомарный writer:
временный приватный файл → file sync → rename → directory sync на Linux.
Удаление файла при undo отсутствующего исходного образа также синхронизирует
каталог. Нет fallback на неатомарную запись.

Ошибка может возникнуть после фактического rename/unlink. Теперь это явный
`ErrRecovery`, а не обещание отсутствия изменений. HTTP сообщает, что копия
могла сохраниться, и предлагает обновить список; исходники и рабочие маршруты
при copy-only операции не менялись. Это не означает, что все записи приложения
автоматически заблокированы: provider не имеет кэша, общий recovery gate ещё
не подключён.

Чтение обычного Store тоже стало bounded/identity-checked, на Linux используется
nonblocking/no-follow open, включая случай FIFO между stat и open. Проверяются
обычный тип файла, приватные POSIX-права и контекст запроса.

Лимиты не расширены и не скрыто уменьшены:

| Объект | Ограничение |
|---|---|
| Отдельная исходная копия | 256 КиБ |
| Provider Store | 32 аккаунта, прежний storeLimit 16 МиБ + 64 КиБ |
| Образ provider для общего журнала | 4 МиБ |
| Весь план всех targets, before + after | 8 МиБ, проверяет journal |

Существующий Store выше 4 МиБ по-прежнему можно читать и дополнять через обычный
copy-only import в пределах его ёмкости. Coordinated target/новый MergeImage
отказывают при превышении journal-бюджета до записи. Нельзя автоматически
удалять копии или увеличивать память роутера ради обхода ограничения. Для
больших общих архивов нужен отдельно спроектированный ограниченный формат.

## Проверки

- Локальный полный `go test ./... -count=1 -timeout=90s`, `go vet ./...`.
- Пять повторов provider recovery tests: реальный Store, lease, CAS, конфликт
  ключей, отсутствие изменений от builder, no-op, точный undo, отмена,
  ошибка до/после реального writer, закрытая сессия, release после отказа.
- Большой синтетический Store: новый coordinated adapter отказывает выше
  4 МиБ, обычные импорт и список сохраняют прежнюю работоспособность.
- Реальные дочерние процессы: остановка после prepare, после замены файла,
  во время undo и после завершённого commit. Для каждого проверены исходное
  отсутствие/наличие файла и межпроцессный запрет обычной записи.
- Recovery запускается до `OpenStore` и возвращает точные before bytes либо
  сохраняет завершённый результат. Внешняя последующая правка блокирует recovery
  без перезаписи файла; постоянный lock inode сохраняется.
- HTTP regression проверяет честную классификацию неопределённой записи,
  отдельную ошибку journal-бюджета и отсутствие private path/token в ответе.
- Синтаксис `app.js` и шесть существующих JS suites пройдены.
- Все Go-пакеты и provider/App tests собраны для Linux arm64/mips/mipsle.
  Linux-only FIFO/symlink/permissions tests только скомпилированы, не выполнены.

Тесты выполнены на Windows с синтетическими аккаунтами. Linux/race,
Entware shell, browser visual QA, HIL и потеря питания не проверены.
Сборки лежат в игнорируемом `.tmp/truth-safety`, не являются install/release
bundle. Зависимости, опубликованные версии, GitHub и роутер не менялись.

## Следующий шаг

Теперь есть отдельные typed targets для config, custom services, devices,
engine staging и provider. **Общий импорт и startup ещё не вызывают journal**;
запрет `ProviderSnapshots` в общем router-архиве остаётся.

Нужен coordinator: доверенный набор roots/targets, стабильный порядок leases,
общий бюджет, исключение конкурирующих API/background/process writers,
startup recovery **до** Load/кэшей/изменяющих API. Только после интеграционных
crash/conflict/cancellation tests можно включать общий router+provider restore.
Прямые shell/root writers, alias paths и чужие runtime не входят в протокол;
старые provider writers защищены лишь в части общей `.import.lock`.
Startup gate должен отдельно исключить запись старого процесса до recovery.
