# З11: браузерная проверка сохранённых подключений

Запускаемый клиент — `scripts/test-ui-real-http-browser.mjs`, сценарии находятся в `scripts/ui-real-http-scenarios.mjs`. Файла `test-ui-linux-real.mjs` нет. Клиент подключается к уже поднятому координатором одноразовому Linux QA серверу и использует установленный Chrome. Сервер, VM и роутер он не запускает и не меняет.

Новый сценарий выполняется с прежним флагом `--draft-mutations`, сразу после существующего сценария импорта и удаления узлов. Он использует оставшиеся два тестовых подключения с адресами `.invalid`; новых профилей и бизнес-записей сценарий не создаёт. Режим без этого флага новый сценарий не выполняет. Прежние проверки одноразового стенда, пустого начального хранилища, выключенной автоматики, неизменных рабочих настроек и запрет Apply сохраняются.

При уже подготовленном QA аккаунте и policy:

```text
node scripts/test-ui-real-http-browser.mjs --draft-mutations
```

Нужен прежний приватный env: `RAZVILKA_QA_UI_FIXTURE=disposable-linux`, `RAZVILKA_QA_UI_URL`, `RAZVILKA_QA_UI_INSTANCE`, `RAZVILKA_QA_UI_CHROME` и либо `RAZVILKA_QA_UI_SESSION`, либо пара `RAZVILKA_QA_UI_USERNAME`/`RAZVILKA_QA_UI_PASSWORD`. `RAZVILKA_QA_UI_OUTPUT` задаёт каталог отчёта. Для свежего QA policy координатор может добавить прежний отдельный `--prepare-policy`; новый сценарий не меняет условия и разрешения подготовки аккаунта или policy.

Собранный сервер должен включать production commit `29e6d1e2` или его интегрированный эквивалент. Новый сценарий проверяет:

- Настоящее разрешённое чтение `/api/v1/nodes` создаёт санитизированный `/api/v1/panel/nodes`: только `id`, `name`, `protocol`, `transport`, правильный instance и сохранённые ID.
- Локальный браузерный отказ чтения списка с кодом busy, затем локальная ошибка транспорта показывают отдельные сохранённые карточки. Они не подменяют `state.nodes`, не содержат health, действий или выбора. Поиск остаётся локальным.
- Явная кнопка повторного чтения выполняет настоящий успешный GET и возвращает обычные элементы управления.
- Дополнительный ответ памяти сначала действительно получен по HTTP, затем удерживается в Promise браузера. После нового настоящего live GET открывается редактор и вводится локальный черновик. Поздний сохранённый ответ не закрывает редактор, не стирает ввод и не возвращает сохранённый режим.
- Локальное старение времени получения убирает истёкшие карточки без действий записи.

Busy/offline, задержка публикации DTO в браузере и TTL — **модели**. Серверный admission не удерживается и не подменяется; реальный офлайн всего браузера и настоящий reboot не моделируются. HTTP Response не подделывается. Любая попытка POST/PUT/PATCH/DELETE во время модели отклоняется до транспорта, включая Apply и проверки узлов. Остановка принятых заданий здесь не вызывается; проверяется доступность перехода к их штатному управлению.

В `result.json` каждый завершённый шаг теперь сохраняет статическую строку `boundary`. Для нового шага она явно указывает `server_admission_held=false`, `business_writes=0` и перечисляет модели. Ошибки помечаются фиксированными `UI_NODE_SAVED_*` checkpoint ID без приватных ответов, названий и содержимого профилей.

Локальная проверка harness без сервера и браузера:

```text
node scripts/test-ui-real-http-client.mjs
node --check scripts/ui-real-http-scenarios.mjs
node --check scripts/test-ui-real-http-browser.mjs
```

Эти команды проверяют модель транспорта, запрет записей, передачу настоящего тела через задержку и санитизацию ошибок. Они не подтверждают прохождение Linux/HTTP/Chrome сценария; такой запуск выполняет координатор отдельно.
