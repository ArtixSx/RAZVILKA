# PR-1.1 — отдельный зашифрованный архив копий Cloudflare

31 августа 2026. Локальная разработка `0.18.1-dev`, без публикации,
регистрации аккаунтов и изменения роутера.

## Для пользователя

В «Настройки → Копии аккаунтов Cloudflare» появился блок «Перенести копии
аккаунтов»:

1. Скачать отдельный зашифрованный JSON-архив, задав и повторив пароль.
2. Выбрать такой архив и ввести пароль для проверки без записи.
3. Увидеть количество новых и уже сохранённых копий; добавить новые одним
   подтверждением или отменить. Если все копии уже есть, запись не требуется.

Архив не включает настройки маршрутов, конфигурации работающих обходов,
логин панели или ключ восстановления. Для него не подходит общая резервная
копия настроек выше. Секреты на диске по-прежнему защищены правами доступа,
а не шифрованием от root; шифруется переносимый архив. Пароль передаётся в
локальную панель: HTTP не становится защищённым благодаря шифрованию файла.

Копии остаются `imported-unverified`: восстановление не подтверждает аккаунт,
handshake или доступность сервиса и не активирует обход.

## Границы восстановления

- AES-256-GCM / PBKDF2-HMAC-SHA256: используется существующий формат, без
  нового собственного криптографического протокола.
- Сначала проверяется весь архив; только потом объединение записывается
  атомарно под блокировкой. Ошибка пароля, формата, размера, лимита копий или
  конфликт ключей под одним ID не приводит к частичному восстановлению.
- Совпадающие ID/тип/содержимое сохраняются без перезаписи; разные ключи под
  тем же ID отклоняют весь архив. Два независимых ID не объявляются одним
  аккаунтом только из-за похожего содержимого.
- Preview возвращает только digest и числа, без ключей или файлов. Restore
  сверяет digest расшифрованного архива и заново проверяет текущее хранилище.
  Digest — защита от подмены выбранного архива между действиями, не отдельное
  разрешение доступа и не серверный журнал подтверждения.
- После разрыва соединения результат записи может быть неизвестен браузеру.
  UI предлагает обновить список; повтор того же архива идемпотентен.
- Неизвестная блокировка записи не удаляется. Автоматическое восстановление
  после падения writer пока не реализовано.
- Общий backup/import роутера продолжает отклонять provider-содержимое до
  изменения настроек. Совместной транзакции двух видов архивов пока нет.

## API

Все пути ниже — `POST /api/v1/cloudflare/backups/` с указанным окончанием:

| Действие | Поля запроса | Результат |
|---|---|---|
| `export` | `password` | Только зашифрованный envelope; пустое хранилище не выгружается |
| `preview` | `password`, `envelope` | `review.digest/added/existing/total`, `copy_only=true`, `saved=false` |
| `restore` | Те же поля, `preview_digest`, `confirm=RESTORE_ACCOUNT_COPIES` | Публичные сведения о копиях; не runtime export |

Требуется вход администратора даже до setup; действуют Origin/JSON и
`Cache-Control: no-store`, включая ошибки. Вход не принимает пути/URL/команды.
Лимит тела export — 4 КиБ, preview/restore — 18 МиБ; дополнительно действуют
ограничения ciphertext/расшифрованного payload и до 32 копий по 256 КиБ.
Общий payload ограничен 8 МиБ, поэтому архив с предельными записями может
не поместиться после JSON-кодирования. Ошибка не меняет исходное хранилище.
Неизвестные, повторные, неоднозначные по регистру поля и лишний JSON отклоняются,
включая поля envelope. Тело не попадает в audit.

Все шесть HTTP-операций архивов (новые три и общие export/preview/import)
делят один незапирающий лимит на экземпляр App: только одна операция,
остальные получают `429`/`Retry-After` до чтения тела и PBKDF2. Это не глобальный
лимит криптографии всего устройства: учётная запись панели и другие процессы
не входят в него. Вызов PBKDF2 синхронный, прервать его посередине нельзя;
контекст проверяется до/после, следующая операция не начинается раньше.

## UI и проверка

Пароли не сохраняются в browser storage. Ссылки на пароль/архив сбрасываются
после результата/ошибки/отмены, выхода, закрытия раздела или смены вкладки.
Изменение входных полей отменяет подготовленное подтверждение. Поздний ответ
не открывает восстановление и не начинает скачивание после ухода с экрана.
Это не гарантия физического обнуления памяти Go/JavaScript.

Проверено локально:

- Go: round-trip, preview без файлов, digest mismatch, повтор без перезаписи,
  конфликт после preview, capacity, пароль, общая crypto gate, auth/Origin/
  Content-Type, строгие поля, сохранность config и отсутствие секретов в audit.
- JS: export, preview/restore, отмена, ошибки, очистка, повторный клик, уже
  существующие копии, невалидный preview, поздние ответы всех трёх операций.
- Полный `go test ./... -timeout=90s`, `go vet ./...`, JS syntax/regressions;
  все Go-пакеты и App tests скомпилированы для Linux arm64/mips/mipsle.
- Реальный браузер на изолированном loopback-стенде: синтетический archive
  preview → restore → list; export скачан и прочитан обратно, показано
  «будет добавлено: 0, уже сохранено: 1». Пароль очищен. Ширина 390 px без
  горизонтального переполнения. Это проверка нового раздела, не всех вкладок.

Linux/race, Entware shell regression, отключение питания и аппаратная
матрица этого блока не выполнялись. Сборки не означают аппаратную стабильность.
