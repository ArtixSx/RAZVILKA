# Native WARP: приватная копия и восстановление

Локальная реализация от 6 сентября 2026 года. Она расширяет существующий
зашифрованный private backup; отдельного архива или новой кнопки не требуется.
Аппаратные copy-only миграция и общий encrypted export/preview/import прошли.
Установочный lifecycle итоговой сборки проверяется отдельно.

## Сохранённые данные и полномочия

`warp-state/native-enrollment.private.json` — один канонический приватный
image-файл schema 1. В нём сохраняются исходные байты `current.json`,
`pending.json`, ключей, сырых HTTP-ответов, регистрационных snapshots и старых
private provider stores всех сохранённых попыток. Allowlist имён исключает
произвольные пути; размер image ограничен 4 MiB и 258 файлами. Перед новым POST
резервируется место для ответа и производного регистрационного snapshot.

В генераторе и восстановлении используется одна OS lease и атомарная CAS-запись.
До запроса сохраняются намерение и оригинальный ключ; запрос выполняется один
раз. Полученный ответ сохраняется отдельно от проверки схемы, с ограниченным
контекстом, который переживает отмену HTTP-запроса пользователя. Неизвестный
исход блокирует новый POST даже при `fresh=true`.

`fresh=false` использует валидированный сохранённый аккаунт без регистрации.
Восстановление pending использует исходные локальные данные. Генератор только
сохраняет EngineConfigs draft; перенос регистрации через backup сам по себе
не создаёт даже новый engine draft. Если архив содержит engine files, общий
импорт восстанавливает их как черновики. Health, действующий туннель и Apply
не возникают из наличия аккаунта.

## Миграция прежнего формата

Старый `warp-state/native-enrollment/` читается как виртуальный image, пока
канонический файл отсутствует. Status, startup и экспорт не выполняют миграцию.
Первый успешный Generate/reuse или restore записывает канонический image.
Каталоги попыток, `current.json`, ключи, ответы и provider-файлы старого формата
остаются нетронутыми, включая исходные bytes/mode/mtime. После миграции
канонический файл является единственным источником текущего состояния.

## Общая зашифрованная копия

Необязательное поле `native_enrollment` входит в checksum всего private payload
и затем в существующее AES-GCM шифрование. Старый decoder, не понимающий поле,
не может успешно принять тот же payload digest и молча потерять регистрацию.
В публичные профили, диагностику и HTTP preview материал регистрации не входит.
Узкий Cloudflare-only restore отказывается от архива с native enrollment.

Общий coordinator имеет отдельный typed target `native_warp`, привязанный
к доверенному `-warp-state`. Новый startup journal `private-restore-native-v1`
открывается после восстановления прежних journal-протоколов. Все прежние
instance leases удерживаются до остановки приложения. Неправильный root,
отсутствующий Manager или конфликт останавливают импорт до любых записей.

Импорт объединяет прежние аккаунты и сохраняет текущий выбор. Имеющийся
неразрешённый pending нельзя заменить или удалить старой копией: несовпадение
вызывает отказ с сохранением исходных данных. Старый архив без native-поля
вообще не меняет этот target. Журнал отменяет native и остальные изменения
вместе при ошибке; после аварии recovery выполняется до загрузки приложения.

Скрипты обновления и возврата не откатывают WARP state к более старой копии.
Бинарник назначения обязан поддерживать read-only capability
`-native-enrollment-schema` со значением `1`, если существует канонический
image, legacy `native-enrollment/current.json` или `pending.json`, либо файл
`private-restore-native-v1/restore.private.json`. Символическая ссылка на такой
marker тоже вызывает проверку; пустой каталог сам по себе её не вызывает.
Команда capability не читает и не создаёт stores.

Проверка выполняется до остановки и после неё. Rollback дополнительно проверяет
capability после private recovery, до деактивации и замены бинарника: recovery
может вернуть native state из журнала. Отказ сохраняет данные. После общего
private restore оставшийся journal-файл консервативно требует совместимый
бинарник даже в состоянии idle и без native-поля в последнем архиве; скрипты
не удаляют журнал ради обхода проверки. Возврат к старому несовместимому
бинарнику в этом состоянии заблокирован.

## Подтверждённые проверки

- One-POST, reuse без wgcf, unknown-pending после restart, offline recovery и
  сохранность прежних аккаунтов/рабочего профиля.
- Copy-only миграция настоящего старого private provider store: профиль тот же,
  новый POST отсутствует, исходные bytes/mode/mtime не меняются.
- Зашифрованный round-trip бинарного ключа и сырого ответа; неправильный digest
  и старый decoder отказывают без потери native-поля.
- Общие HTTP export/preview/import сохраняют pending и AppliedServices.
- Online/offline typed restore, удержание Manager/OS lease до handover,
  конфликт старой копии с новым pending до записи остальных stores.
- Ошибка следующего target возвращает все before-images. Настоящий дочерний
  процесс завершён после native-записи; новый coordinator восстановил исходное
  состояние до загрузки stores.
- Полные Go tests затронутых семи пакетов, vet и diff check прошли локально.
- Затем полный `go test ./...`, `go vet ./...` и полный Windows/amd64 race
  suite прошли для снимка до последующих recovery/cleanup исправлений.
  Это не Linux-specific race и не проверка будущего release artifact.
- Роутер: legacy → canonical offline reuse прошёл; original legacy и staged
  profile/key hashes не изменились, новый POST не выполнялся. Артефакт
  `.hil/native-migration-router-results.json`.
- Роутер: настоящий encrypted export → preview → импорт в отдельный control
  plane прошёл. Canonical image SHA совпал с исходным, account registered,
  повторный offline reuse не изменил image. AppliedServices/AppliedRevision
  остались прежними, целевой service runtime STOPPED. Артефакт
  `.hil/native-backup-router-results.json`.
- Обычный и Windows race suites этого снимка: 47 пакетов, 1519 успешных тестов,
  16 ожидаемых platform/helper skips. ARM64 SHA-256 проверенного снимка:
  `48f3e1efab048b0f5f8f3ce8948283b62e94e6fd53547370724ae9eaab89a34c`.
- Capability supervision regression проверяет четыре marker-файла, пустые
  каталоги, отсутствие state и checkpoint, появившийся после первой проверки.
  Это локальные проверки скриптов; итоговый installer HIL учитывается отдельно.

Это проверка сохранности и восстановления, а не подтверждение работы WARP.
Финальный WG/MASQUE HIL остаётся неуспешным или неустойчивым:
[результаты транспорта](WARP_CANDIDATE_HARNESS_RU.md).
