# Адаптер восстановления конфигурации и защита обычных записей

Локальный блок 31 августа 2026 года, продолжение PR-1.1.
Первый настоящий адаптер подключён к хранилищу `config.Store`. **Общий журнал
ещё не вызывается из HTTP-импорта или main/startup**: остаются другие хранилища
и координатор. На рабочий роутер изменения не устанавливались.

## Что уже изменилось в коде приложения

Обычная запись конфигурации теперь проходит через `restorejournal.FileTarget`:

- ограниченное чтение через открытый корень каталога, только обычный файл;
- системная блокировка на конкретное имя файла, общая для новых Store/процессов;
- сравнение текущего файла с точными байтами, которые читал этот Store;
- атомарная замена с правами `0600`, синхронизация файла и каталога на Linux;
- отказ при устаревшем снимке, а не перезапись более новой конфигурации.

Таким способом сохраняются обычные изменения сервиса, Safe Mode, Apply/Discard,
компенсации импорта и миграция схемы. Чтение/проверка существующего файла не
создаёт файлов блокировки. Отсутствующая конфигурация при обычном Load по-прежнему
инициализируется безопасными значениями — именно поэтому будущий startup recovery
должен выполняться **до** Load.

Рядом с конфигурацией появляется постоянный `.state-<hash>.lock`. Имя выведено
из имени файла, маркер проверяется перед использованием; файл не удаляется по
возрасту/PID. Неизвестный или незавершённый маркер блокирует запись до разбора.
Если во время восстановления другой процесс прочитал промежуточный файл,
его запись всё равно не проходит занятую блокировку.

Если запись вернула ошибку после возможной замены файла, Store перечитывает
результат под той же блокировкой. Только точное совпадение со старым снимком
позволяет считать файл неизменённым. Иначе старый кэш больше не допускается
к записи до перезагрузки/восстановления состояния. В памяти остаётся последний
подтверждённый вид, не обещание текущих байтов диска. Общий приватный импорт
распознаёт такую ошибку как неполное восстановление, а не подтверждённый откат.

В UI добавлены пояснения для занятой записи, устаревшего снимка и неизвестного
результата. Обычное обновление страницы не обещает перечитать файл в серверный
кэш: при внешней правке требуется повторная загрузка настроек самой службой.
Автоматический перезапуск или повтор записи не добавлялись.

## Адаптер для журнала

- `config.OpenRestoreTarget` открывается до загрузки кэша. Проверяет конфигурацию
  текущим валидатором, не допускает удаление файла и не принимает произвольные
  пути из архива. Обычные Store writers используют ту же блокировку.
- `Store.BeginRestore` дополнительно удерживает mutex текущего Store на время
  операции; устаревший/неопределённый кэш не допускается. Сессию нельзя держать
  во время ожидания решения пользователя.
- `DraftImage` строит конфигурацию из текущего состояния: меняются только
  желаемые сервисы и Revision. Применённые маршруты, Listen, Safe Mode и прочие
  поля сохраняются. Полная проверка содержимого архива остаётся обязанностью
  будущего координатора до построения этого образа.
- Закрытие сессии перечитывает файл под блокировкой и согласует кэш с диском.
  Ошибка чтения/проверки запрещает дальнейшую запись устаревшего кэша.
- Binding учитывает путь и тип/версию адаптера без вывода пути в публичные данные.
  Общий scope должен дополнительно учитывать ID и bindings всех целей.

`FileTarget` пригоден и для следующих адаптеров, но сам не проверяет формат
их содержимого. Каталог, устройства, staging и Cloudflare пока **не** переведены
на этот механизм.

## Проверки

- Два Store одного файла: устаревший не может изменить сервис, Safe Mode,
  применить/отменить черновик или просто сохранить старый снимок.
- Занятая restore-сессия запрещает другую сессию и запись второго Store.
  После успешного commit/rollback память соответствует фактическому файлу.
- Настоящий config target работает с журналом, не с тестовой копией его логики.
- Принудительное завершение дочернего процесса: после подготовки журнала,
  записи config, во время отката и после полного завершения. Родитель открывает
  typed targets, выполняет recovery, закрывает их и только потом вызывает Load.
  Старые байты восстанавливаются точно; подтверждённый результат сохраняется;
  применённый YouTube и Safe Mode не изменяются.
- Отказ записи до/после фактической замены и запрет дальнейшей записи при
  неопределённом результате; ошибки не раскрывают внутренние данные/пути.
- Отсутствующий/пустой файл, неверный JSON/схема, предел 4 МиБ на образ,
  зарезервированные имена журнала и Windows-устройств, закрытая сессия.
- Полный `go test ./... -count=1 -timeout=90s`, `go vet ./...`, синтаксис app.js
  и пять JS suites прошли. Пакеты config и restorejournal прошли 10 повторов.
- Все Go-пакеты и тестовые бинарники config/restorejournal/App собраны для
  Linux arm64/mips/mipsle. Linux-only FIFO/symlink/permissions tests только
  скомпилированы; локально Linux-бинарники не выполнялись.

## Границы и следующий этап

Старые версии RAZVILKA, shell-редакторы и сторонние программы не участвуют
в новом протоколе блокировки. Сравнение обнаруживает завершённую внешнюю правку,
но не защищает от root/неучаствующего writer в окне самой замены, hardlink aliases
или злонамеренной подмены каталога. Нельзя одновременно запускать старый writer
и новое восстановление. На Windows запрещены device names и неоднозначные
окончания имён; backend остаётся проверкой process crash, не power-loss guarantee.

Восстановление конфигурации не обеспечивает общую атомарность всех хранилищ.
Следующий шаг: такие же адаптеры/защита обычных записей каталога и устройств,
затем staging/provider, общий порядок захвата и блокировка новых операций при
незавершённом журнале. После этого — startup recovery до загрузки кэшей и фоновых
задач, общий архив router+provider и аппаратные gates. До этого запрет
`ProviderSnapshots` в общем импорте сохраняется.

Linux runtime/race, Entware shell regression, browser visual QA, HIL и потеря
питания не проверялись. GitHub, рабочая сеть и зависимости в этом блоке не менялись.
