# NET1: подтверждение текущей сетевой сессии

> Исторический документ конкретного этапа. Версии, команды и состояние функций
> ниже относятся к тому этапу. Сейчас используйте [план](ROADMAP.md),
> [текущий статус](CURRENT_STATUS_RU.md) и [установку](INSTALL_RU.md).

Дата: 6 сентября 2026 года. База: `bd36e160af5eabd40c0a8bab77c2454d4e4fb06d`.
Статус: **реализовано локально, частично проверено на Keenetic ARM64**.
Это контракт рабочей копии, а не объявление нового stable-релиза или установки
обновлённого daemon на роутер. Уровни готовности — в
[CURRENT_STATUS_RU.md](CURRENT_STATUS_RU.md).

NET1 запрещает использовать результат проверки узла, план или AUTO-наблюдение
после потери подтверждённой непрерывности сети. Раньше одинаковые имя WAN и
шлюз могли вернуть прежний идентификатор после переподключения; краткая смена
сети между проверкой и сохранением также могла остаться незамеченной из-за
кэша. Теперь право использовать proof связано с наблюдаемой сетевой сессией.

## Контракт systemprobe

| API | Назначение |
|---|---|
| `FreshWANProfile(ctx) (WANProfile, error)` | Новый ограниченный по времени снимок и чтение накопленных событий; используется перед активными решениями |
| `DetectWANProfile() WANProfile` | Пассивное отображение той же identity с кэшем до 10 секунд; не источник разрешения на запись proof или применение |
| `ValidWANProfileID(string) bool` | Принимает только `wan-` и 12 строчных шестнадцатеричных символов; пустое значение и `network-unknown` не дают права на маршрут |

ID строится из приватного случайного значения при запуске наблюдателя и
счётчика поколений. В течение его жизни поколения не повторяются; исчерпание
диапазона закрывает дальнейшее подтверждение. Перезапуск создаёт новую
случайную область ID, а boot identity входит в снимок. Формат остаётся
совместимым с существующими полями Store и плана, новой схемы NodeStore нет.
ID не раскрывает адреса или содержимое DNS-файлов. Это локальный токен с
48-битным пространством, а не криптографический сертификат или глобально
уникальный идентификатор сети.

Изменение снимка, релевантное событие, потеря наблюдателя или ошибка чтения
отзывают прежнюю identity. Последовательности `A → unknown → A` и наблюдаемая
`A → B → A` не возвращают старому proof силу. Ошибка, отмена, переполнение
очереди или невозможность получить согласованный снимок дают unknown/error;
последующая успешная синхронизация создаёт новую сессию.

## Что именно наблюдается на Linux

Снимок включает boot ID, IPv4/IPv6 unicast default routes таблицы `main`,
gateway, метрику, preferred source, multipath, адреса WAN, состояния его links
и доступных нижележащих/master-интерфейсов. Source учитывается и при наличии
gateway. Порядок строк нормализуется; обычное уменьшение времени жизни адреса
не меняет identity, смена его значимого состояния меняет.

Постоянный неблокирующий rtnetlink socket получает link/address/route events.
Перед снимком и после него очередь читается до ограниченного предела. При
изменениях во время чтения допускается один повтор; нестабильность, потеря
сообщений, усечённый ответ или прерванный dump не считаются успешным снимком.
Нельзя заменять это сравнением двух строк default route: оно пропускает ABA.

Наблюдаемый underlay определяется по основной таблице и связям WAN. Собственные
live/candidate route tables вне `main`, loopback exact-canary и недефолтные
служебные TUN routes не меняют его identity. При этом исключения по префиксу
имени `rz-*` нет: чужой интерфейс с таким именем, если он участвует в основном
default route, наблюдается на общих основаниях. Событие нового основного
default route учитывается и для ещё не известного ifindex.

DNS-часть читает видимые `/etc/resolv.conf`, а при наличии — `/etc/hosts` и
`/etc/nsswitch.conf`. Учитываются содержимое, цель symlink, inode, mtime и
идентичность файла. Inotify наблюдает файлы и нужные родительские каталоги,
поэтому замена файла и изменение с возвратом прежних байтов отзывают старую
сессию. Для resolv.conf нужна фактическая строка nameserver с IP-адресом.

Лимиты: до 3 секунд на Fresh с учётом ожидания доступа к наблюдателю; до 1 МиБ
и 8192 сообщений на netlink dump, до 256 links, 1024 адресов, 64 default routes,
8 уровней связей интерфейсов, 64 КиБ на DNS-файл и 32 inotify watches.
Превышение даёт unknown, а не частичный успешный профиль. На Windows production
backend недоступен; переносимая логика проверяется через подставляемый источник.

## Где проверяется сессия

| Участок | Поведение локальной реализации |
|---|---|
| Exact node checker | Fresh до сетевой проверки и после завершения/cleanup, пока занят слот checker. Смена сети делает результат inconclusive и убирает право на PASS, включая ранние DNS/transport failures |
| API сохранения node proof | Captured profile перед проверкой; сверка node/service/route/profile результата и новый Fresh непосредственно перед `RecordCheck`. Несовпадение возвращает `NODE_NETWORK_CHANGED` без сохранения результата |
| NodeStore и группы | Unknown или proof другой сессии не допускаются к выбору/материализации. Сохраняются существующие ограничения TTL, node identity, service и LKG |
| Preview / Plan | `NetworkProfileID` входит в план и его digest. Node/group routes требуют известную identity; построение повторно проверяет её. Переданный Manager план прежней сессии отклоняется; обязательное подтверждение digest из UI относится к PR-NB1 |
| Materializer / proxy adapter | Использует identity плана; Fresh до и после получения приватного материала и перед изменяющими runtime фазами. Результат нельзя перепривязать к сети, наблюдённой только в конце |
| Apply | Проверки после получения operation gate и на границах snapshot/stage/validate/canary/activate/health/commit. До изменений runtime отказ имеет состояние `network-stale`; после изменений запускается существующий rollback. Старый committed journal не заменяется неудачным планом |
| Recovery / refresh | Старый node-план или unknown дают `network-stale`; это не успешное восстановление и не boot-loop failure. При отказе до reconcile работающий runtime не разрушается. Между адаптерами continuity проверяется снова |
| SmartRoute | `ObserveForProfile` получает identity начала проверки и повторно проверяет её перед сохранением; история не меняется при unknown/mismatch. Старый `Observe` без начальной identity возвращает ошибку |
| TestLab | Batch выполняется без публикации промежуточной истории, затем профиль начала сравнивается с Fresh после cleanup. `RecordRoutesForProfile` проверяет текущую identity и не меняет чужую метку сети; snapshots/aggregates отклоняют stale/mixed evidence |

Финальная общая проверка TestLab/SmartRoute, node pipeline и обработки отмены
завершена: все 44 Go-пакета, vet, форматирование и проверки diff прошли.
Это локальный результат; новый commit/CI/release не создавался.

При отмене node-плана до активации работающий runtime не откатывается.
После начала изменений RefreshPolicy и Reconcile очищают затронутое состояние
в отдельном ограниченном контексте, который не отменяется вместе с запросом.
Ошибка восстановления сохраняется в результате, а не скрывается.

Транзакционные network gates сейчас обязательны для маршрутов
`sing-box:node-*` / `sing-box:group-*`. Они не объявляют все legacy adapters
полностью переведёнными на Evidence v2. Перезапуск daemon требует нового
exact proof для повторной активации сохранённого node-плана; старый журнал
остаётся читаемым, но не является разрешением применить его заново.

## Границы гарантии

1. Это **ограниченная наблюдаемая сессия underlay**. Она не доказывает состояние
   скрытого DNS upstream, DPI провайдера, удалённого сервера или всех policy
   routing rules. На проверенном Keenetic resolv.conf указывает локальный
   forwarder; его приватный upstream непрозрачен. Кэш resolver приложения тоже
   не становится частью exact DNS binding только от чтения файлов.
2. ABA обнаруживается для событий, которые ОС доставила наблюдателю.
   Переподключение без доступного link/route/address/DNS события невозможно
   доказать этим механизмом. Наблюдатель не обещает глобальный непрерывный
   журнал всех сетевых изменений.
3. Fresh и последующая запись/активация не образуют атомарную операцию с ядром.
   Границы повторной проверки сужают окно; следующая проверка отзывает старую
   authority. Для непрерывного контроля live-потоков нужен отдельный lifecycle.
4. Сетевой токен не заменяет revision/generation конфигурации, node identity,
   service ID, owner generation, device/policy scope, TTL и exact route proof.
   PASS одного URL не доказывает все сценарии YouTube, Instagram или Discord.
5. Snapshot обходит ограниченный dump маршрутов и адресов. При многократных
   AUTO/view/planning вызовах стоимость повторяется: до 3 секунд на вызов в
   неблагоприятном случае, около 10 мс в снятой аппаратной проверке. Follow-up
   P2 — пакетировать работу без возврата к кэшированной authority; повторный
   Fresh перед публикацией результата/commit должен сохраниться.

## Уточнения из дополнительных чатов

Исторические задачи «План развития проекта» и «Чат для nfqws2-keenetic» изучены
как контекст требований; локальная сводка — `.hil/context-review.md`.
**Старые команды из переписки не исполнялись.** Прежние утверждения ассистента
и запущенный NFQWS2 не считаются доказательством работоспособности сервиса.

- Домашний `eth3` и `ppp0` у другого пользователя относились к разным сетям.
  Интерфейс нельзя запоминать как универсальный WAN или уникальную identity.
- NFQWS2 должен стать собственной управляемой подсистемой; z2k остаётся
  источником идей, без runtime-зависимости. Выбор обхода сервиса должен
  управлять охватом его потоков, а не только состоянием процесса.
- Каталог собственных/сторонних узлов и рецептов должен показывать источник,
  актуальность и короткий путь проверки/применения. Популярность, город,
  провайдер и успешность чужой сети не заменяют локальный exact proof.
- YouTube web/API/search/Shorts/video/seek/TV, Instagram Feed/Reels/Stories/Direct
  и Discord voice требуют отдельных сценариев. Старые гипотезы QUIC/checksum/DPI
  и сообщения «не помогло» не закрывают их проверку.
- Selective Xbox DNS, WARP Configurator/USQUE, Lite/Pro, сайт и переносимость
  остаются отдельными требованиями. Они не разрешают экспериментальный DNS,
  отключение IPv6/QUIC или NFQUEUE-захват для всей LAN.

## Открытые gates и следующий шаг

1. Выполнить Linux/race и CI на будущем commit. В локальной среде нет C compiler
   для race; cross-build и обычные ARM64 tests его не заменяют.
2. Отдельно проверить настоящий WAN/PPP reconnect с тем же интерфейсом,
   включая наблюдаемый `A → B → A`, unknown и истечение TTL. Namespace SKIP
   этот gate не закрывает; для live reconnect требуется согласованный сценарий.
3. Получить два собственных узла, которые проходят transport/protocol/egress/
   service, и выполнить N1.4 HIL: node/group switch, service scope, ранний отказ,
   WAN change, отмена, cleanup failure, failover и rollback.
4. После этих gates развивать PR-NB1 и AUTO. Оптимизацию многократных снимков
   вести отдельно с тестами сохранения сетевой привязки batch.
