# PR-0.2 — строгие результаты проверок

Дата: 30 августа 2026 года. База: `5522735`, цикл `0.18.1-dev`.

## Что изменено локально

- Общий HTTP-классификатор используется Test Lab, изолированными проверками и
  canary в dataplane. Прежний критерий `HTTP < 500` удалён из этих canary.
- `302` не считается успехом. Переходы за пределы разрешённых хостов, смена
  схемы/порта и запрещённые перенаправления останавливаются до запроса к цели.
  В Test Lab сохраняется цепочка переходов без query, fragment и credentials.
- Каталог поддерживает ожидаемые `2xx`-статусы, политику redirect, тип ответа,
  JSON с обязательными полями и признаки тела. Для YouTube `generate_204`
  требуется именно `204`; подпись прямо говорит, что это не тест видео.
- Ответы `403/451`, известные страницы блокировки с `200`, поддельный JSON и
  несоответствующее содержимое не становятся `service-confirmed`.
- Добавлены итоги `PASS`, `PARTIAL`, `BLOCKED`, `MISROUTED`, `INCONCLUSIVE`,
  `ERROR`. UI объясняет их обычным языком и не показывает зелёное подтверждение
  по одному `status=pass` без достаточного уровня доказательств.
- Несовпадение ожидаемого и наблюдаемого пути либо подтверждённый отрицательный
  контроль снимают route/service proof. Smart Route отзывает прежний успех
  такого маршрута. Неподтверждённый вариант с высоким баллом больше не скрывает
  действительно проверенного кандидата.
- Общий итог обязательных сценариев сохраняет худший результат, включая
  блокировку с HTTP `200`; результат первого сценария не перекрывает остальные.
- Старый JSON читается без миграции схемы, но объявленный успех без HTTP-ответа
  больше не повышается до подтверждения сервиса. Проверяется максимум 32 KiB
  тела; сохраняется только SHA-256 образца, не содержимое ответа.

## Проверки

Автоматические fixtures: `302 → ISP portal`, промежуточный чужой redirect,
подмена суффикса домена, HTTPS downgrade, `403`, `451`, `429`, block page `200`,
невалидный JSON, отсутствие обязательного JSON-поля, неверный Content-Type,
обрезанный JSON, route mismatch/direct-leak input, отзыв старого успеха,
недоверенный TLS-сертификат, агрегация сценариев и canary-отказ.

TLS SAN и цепочка доверия проверяются штатным Go TLS-клиентом; отключения
проверки сертификата не добавлены. Произвольный issuer pinning не используется.

Локально прошли `go test ./...`, `go vet ./...`, проверка синтаксиса JavaScript,
исполняемые проверки UI-вердиктов, проверка ссылок документации и сборка Linux
ARM64. GitHub CI и аппаратные тесты этой версии ещё не запускались.

## Что ещё не доказано

1. Новая реализация пока проверена локально, не на роутере и не опубликована.
   Для стабильного релиза нужны CI и аппаратная проверка NFQWS2/YouTube baseline,
   Telegram через каждый доступный обход, отказ кандидата и rollback.
2. Поле отрицательного контроля — fail-closed контракт для **подтверждённого**
   обнаружения direct leak. Независимый активный отрицательный контроль для
   каждого внешнего SOCKS/туннеля ещё не реализован. Равенство egress IP само по
   себе не используется как доказательство утечки: у NFQWS2 оно нормально.
3. Route proof остаётся доказательством локального адаптера: source/interface,
   scoped NFQUEUE counter либо SOCKS CONNECT с локальным паспортом запуска.
   В продолжении PR-0.2 добавлены проверки процесса, конфигурации, статического
   выхода и владельца SOCKS-порта — см.
   [ROUTE_PASSPORT_LOCAL_RU.md](ROUTE_PASSPORT_LOCAL_RU.md).
   Независимое подтверждение remote egress и выбранного узла динамического
   пула остаётся незакрытым gate.
4. JSON-предикат проверяет синтаксис и обязательные поля, не полную JSON Schema.
   Не все сервисы уже имеют собственные fingerprints. Общая веб-проверка не
   доказывает воспроизведение YouTube или работу Telegram MTProto/звонков.
5. Старый Strategy Lab имеет отдельные транспортные тесты. Их унификация и
   сервисные сценарии входят в дальнейшую работу; этот PR не объявляет их
   проверками полноценного сервиса.

## Безопасность изменения и откат

Во время разработки не менялись DNS, WAN, firewall, процессы или профили на
роутере. Новых автоматических регистраций и подключений публичных узлов нет.
Перед аппаратной проверкой сохраняется стабильный `v0.18.0`; обновление только
транзакционным installer с существующим backup/rollback. Не ослаблять TLS или
предикаты, чтобы искусственно получить зелёный результат.
