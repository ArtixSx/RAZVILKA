# Работа над RAZVILKA в нескольких чатах

Принято 28 сентября 2026 года: один основной чат и два рабочих.
Общий остаток плана остаётся в [14 ветках](BRANCHES_RU.md). Отдельный чат
получает ограниченное задание; все 14 направлений одновременно не запускаются.

## Первая пара заданий

| Роль | Ветка | Задание | Рабочая папка относительно каталога проекта |
| --- | --- | --- | --- |
| Основной чат | `chore/unified-branch-plan` на этапе организации | Контракты, проверка результатов, интеграция, роутер и выпуск | `unified-lan-review` |
| Панель и состояние | `work/plan-01-panel` | [01.1: сохранённый снимок и свежесть](tasks/PLAN_01_PANEL_RU.md) | `worktrees/plan-01-panel` |
| Очередь и операции | `work/plan-02-queue` | [02.1: подготовка вне сетевой блокировки](tasks/PLAN_02_QUEUE_RU.md) | `worktrees/plan-02-queue` |

Каждая папка — отдельный Git worktree с собственной веткой. Ветка — место
хранения изменений, worktree — отдельные файлы на диске, чат — исполнитель задания.
История Git общая, но рабочие файлы двух чатов не должны совпадать.

Приложение сейчас знает внешний каталог `C:/Projects/RAZVILKA` как проект,
а репозиторий находится во вложенной папке `unified-lan-review`.
Встроенное создание worktree из внешнего каталога вернуло `Not a git repository`.
Поэтому для этой конфигурации рабочие копии создаются обычным Git; новый чат
остаётся в проекте RAZVILKA, но каждую команду выполняет в назначенном worktree.
Рабочие копии не регистрируются как отдельные репозитории и не дублируют `.git`.
Эта особенность локальной среды не является требованием установки программы.

## Общий контракт первой пары

- Базовая реализация — 0.18.13. Документы организации не меняют версию программы.
- Первый шаг сохраняет существующий формат API и panel DTO schema 1.
  Если требуется несовместимая схема, сначала описать её основному чату;
  самостоятельно обновлять только одну сторону контракта нельзя.
- `available`/`retained`, возраст наблюдения, состояние настроек и доказательство
  работоспособности маршрута различаются. Сохранённое состояние не даёт новое
  право на сетевое действие и не продлевает proof.
- Основной вход, очистка при logout, защита от поздних ответов, CAS, границы
  клиента и блокировка незавершённого rollback/cleanup сохраняются.
- Панель меняет только представление и чтение своего состояния. Очередь меняет
  приём и исполнение операций. Обход единой блокировки для ускорения UI запрещён.

ожидание решения не разрешает молча расширить область работы.

## Запуск и проверки

1. Первым действием проверить абсолютный путь, текущую ветку, чистоту дерева
   и базовый commit. Не переключать ветку в чужой рабочей копии и не менять
   внешнюю папку проекта вместо своего worktree.
2. Прочитать своё задание, общий контракт и нужный участок плана. История всех
   прежних чатов не требуется: важные ограничения и подтверждённое состояние
   передаются файлами. При противоречии проверить код и сообщить о расхождении.
3. Сначала воспроизвести проблему либо зафиксировать, что гипотеза не подтвердилась.
   Выполнить один законченный шаг с подходящими регрессионными проверками.
4. Для временных файлов использовать `.hil/` своего worktree; порты локальных
   серверов первой пары: панель `18841`, очередь `18842`. Перед запуском проверить,
   что порт свободен; чужой процесс не завершать. Не использовать данные роутера
   для локальных тестов. Сборочные результаты остаются в своей папке.
5. Проверять затронутые Go/JS-сценарии, затем при необходимости AArch64.
   Среда проекта: Go 1.26.5, Node.js 24, `GOTOOLCHAIN=local`.
   В Linux `RAZVILKA_BUILD_TARGETS=arm64 ./scripts/check.sh` выбирает AArch64;
   полный общий CI и окончательный выпуск сохраняют все цели сборки.
6. Новые MIPS/MIPSel-сборки и общий полный прогон выполняются основным чатом
   на принятом этапе/перед выпуском. Целевой тест не считается полной приёмкой.
   Указать недоступные проверки и настоящую причину, а не только «всё зелёное».

Рабочие чаты тестируют код локально. Доступ к роутеру, установка компонентов,
смена маршрутов, обновление панели и сетевые сбои выполняются основным чатом
последовательно. Worktree не изолирует физический роутер, порты и общие процессы.

## Передача результата и объединение

Рабочий чат сохраняет небольшие коммиты в своей ветке и записывает свой отчёт:
база/HEAD, воспроизведение, исправление, изменённые файлы, команды и результаты
проверок, ограничения и следующий шаг. Временные секреты и приватные снимки
не входят в отчёт или коммит. Если работа не закончена, это указывается явно.

Основной чат читает отчёты и состояние задач, проверяет diff, общие контракты
и тесты, после чего объединяет изменения по одному. Он публикует рабочие ветки
и принятый код, создаёт выпуски. Рабочие чаты самостоятельно не меняют `main`,
не публикуют релизы и не управляют чужими ветками. В этом репозитории GitHub
называется `github`; `origin` — старый локальный bundle.

Изменения интегрируются обычным Git merge/fast-forward с сохранением истории.
Перед началом зависимой задачи её ветка получает уже принятые зависимости.
Общая исходная точка, переданная при создании чата, не остаётся вечной базой.
Для переноса контракта не копировать файлы вручную между рабочими папками.

После завершения текущего шага рабочий чат заканчивает отчётом. Следующая задача
выдаётся явно с актуальной веткой и границами. Одновременных реализаций остаётся
две; основной чат сосредоточен на интеграции. Это схема организации работ,
а не автоматический фоновый планировщик и не обещание экономии токенов.
