# Как устроены версии RAZVILKA

[Скачать стабильную версию](https://github.com/ArtixSx/RAZVILKA/releases/latest) ·
[Статус проверок](CURRENT_STATUS_RU.md) · [История изменений](../CHANGELOG.md)

Этот файл объясняет правила версий. Список добавлений и исправлений находится
в Changelog и описаниях выпусков — здесь он не повторяется.

## Где смотреть версию

| Место | Что оно означает |
| --- | --- |
| [VERSION](../VERSION) | Версия исходников в выбранной ветке или коммите |
| Git-тег `vX.Y.Z` | Ссылка на конкретный коммит выпуска |
| GitHub Release | Описание и прикреплённые файлы выпуска; может быть черновиком или предварительным |
| `/opt/bin/razvilka -version` | Версия бинарника, действительно установленного на роутере |
| [Releases / latest](https://github.com/ArtixSx/RAZVILKA/releases/latest) | Опубликованный стабильный выпуск, который получает установщик по умолчанию |

Изменение README или документации не обновляет установленную программу.
Строка последнего коммита рядом с файлом на GitHub тоже не является его версией.

## Правило VERSION

В `VERSION` хранится одна версия без начального `v` и без метаданных `+...`:
например, `0.18.6`, `0.18.7-dev` или `0.18.7-rc.1`.
Числовые части не начинаются с лишних нулей. Суффикс после дефиса обозначает
предварительную версию.

Значение должно совпадать с запасным значением `Version` в
[internal/app/app.go](../internal/app/app.go), подписями версии и ключом
кэша `app.js` в [index.html](../cmd/razvilka/web/index.html).
Это проверяет [internal/projectmeta](../internal/projectmeta).

[build.sh](../build.sh) читает `VERSION`, собирает `amd64`, `arm64`,
`mips` и `mipsle`; обе MIPS-сборки используют soft-float.
Внутрь бинарника передаются версия, коммит, время сборки и признак изменённых
исходников. Для CI их задают переменные `RAZVILKA_VERSION`,
`RAZVILKA_COMMIT`, `RAZVILKA_BUILD_TIME` и `RAZVILKA_DIRTY`.
При обычной локальной сборке неизвестные сведения остаются `unknown`.

## Что делает GitHub

[Обычный CI](../.github/workflows/ci.yml) запускается на push и Pull Request.
Он добавляет к версии исходников `+<короткий коммит>` для различения проверяемых
сборок. Это не публикация стабильного выпуска.

[Release workflow](../.github/workflows/release.yml) запускается для тегов `v*`:

1. Читает `VERSION` и убирает только конечный `-dev` для сопоставления.
   Тег без начального `v` должен совпасть с полученной базой или иметь вид
   `<база>-rc.N`, где `N` — положительное целое без начального нуля.
   Например, `VERSION=0.18.7-dev` допускает `v0.18.7` и `v0.18.7-rc.1`.
2. Запускает [полный набор проверок](../scripts/check.sh) и четыре сборки.
   Версия полученного бинарника должна совпасть с тегом без `v`.
3. Создаёт Entware-архивы, контрольные суммы и attestations происхождения.
   Проверяет состав архива, чтобы не включить приватные файлы и ссылки на них.
4. Создаёт **черновик Release** с `latest=false`. Версия с дефисом дополнительно
   получает признак prerelease.
5. Если есть `docs/releases/<версия>.md`, использует его краткое описание.
   Иначе GitHub генерирует описание автоматически.

Успешный CI и наличие тега ещё не означают публикацию. Перед публикацией
проверяют точные прикреплённые файлы, их происхождение, установку и работу
на роутере. Затем владелец публикует выпуск и выбирает его статус Latest.
Проверка другой локальной сборки не заменяет проверку файлов выпуска.

## Изменение уже созданного выпуска

Исправление программы получает новую версию и новый тег. Старый тег
не передвигают на другой коммит. Неудачный неопубликованный черновик можно
удалить, сохранив тег, исходную историю и результаты проверки.

До `1.0.0` интерфейс и форматы могут меняться. Обновление должно сохранять
пользовательские данные и создавать снимок для отката; совместимость и
реально проверенные сценарии указываются в [текущем статусе](CURRENT_STATUS_RU.md).
Номер `1.0.0` не заменяет проверку поддерживаемых роутеров, обновления,
восстановления и безопасности.
