# AmneziaWG 3.1 + локальный WARP: кандидат для проверки

## Основа и границы

Основа — полный сохранённый R5, локальный commit `18fa5268f93069377f70e1f482820d1099d88856`, а не незавершённый малый R5_DELIVERY. VERSION остаётся `0.18.2-dev`; имя этой итерации — `AWG31-WARP`. Фактический новый commit, время сборки и SHA артефактов находятся в отчёте поставки. Это не опубликованный tag и не hardware-approved stable. Удалённый main и пользовательский роутер не менялись.

Изменены настоящий Go backend и встроенная панель R4.2. Сохраняются отдельная главная-наблюдение, сетка сервисов, AI только как категория UI, самостоятельные проверки и маршруты каждого сервиса. Новый конфигуратор находится внутри существующего редактора AmneziaWG.

## Источники и принятое решение

Предоставленная статья https://teletype.in/@revelix/AmneziaWG3.1 описывает VPS с AmneziaWG, экспорт оригинального `.conf`, запуск через AWG Manager в Kernel-режиме и маршрутизацию через HydraRoute. Это источник пользовательского сценария, не доказательство поддержки любого роутера. Видео https://www.youtube.com/watch?v=miTrpl4bnlk отдельно просмотреть/получить расшифровку не удалось (ограничение получения); выводы о шагах взяты из текстовой статьи, которая названа её автором текстовой версией видео.

Исследован индекс https://repo.hoaxisr.ru/ и опубликованные файлы AWG Manager v2.18.2. Никакие installer, `wget | sh`, opkg-пакеты, модули ядра или внешние VPN в этой работе не запускались. RAZVILKA НЕ устанавливает AWG Manager или HydraRoute как второй менеджер.

Формат сверялся с https://docs.amnezia.org/documentation/amnezia-wg/ и валидатором https://github.com/hoaxisr/awg-manager/blob/v2.18.2/internal/tunnel/config/validate_awg3.go . Код parser/validator написан отдельно в RAZVILKA; код менеджера, kernel-модули и его frontend не вендорились. Новые локальные лимиты — политика безопасности данного кандидата, не утверждение об универсальных ограничениях протокола.

Популярный wgcf (https://github.com/ViRb3/wgcf) указан в панели как reference совместимости. Используется уже имеющийся native Cloudflare registrar RAZVILKA, а не скрейпинг публичного генератора и не новый обязательный бинарник wgcf. Его существующий ручной compatibility-path не выдаётся за новый автономный runtime.

**Отличие от инструкции:** VPS и конфигурацию сервера предоставляет владелец; RAZVILKA заменяет клиентское управление и маршрутизацию. Покупка VPS, SSH-развёртывание сервера, выдача серверных peers и глобальная настройка DNS не автоматизированы.

## Реализовано: AWG

1. `internal/awgprofile`: ограниченный разбор клиентского `.conf`, canonical serialization и редактированное представление. Поддерживается один Interface + один Peer. Неизвестные/повторные поля, hooks, SaveConfig, некорректные ключи и опасные CPS не игнорируются молча.
2. Распознаётся минимальная требуемая версия WG/AWG 1/1.5/2/3/3.1 по параметрам, не версия удалённого сервера. Отсутствие новых флагов не доказывает старую версию peer.
3. Поля S1–S4, H1–H4, I1–I5, Jc/Jmin/Jmax, HeaderProtectionKey, ContentPaddingAddition, диапазоны таймеров, RandomTrailers, DisableCookies проходят валидацию. HeaderProtectionKey — ненулевые canonical base64 32 байта, при его наличии S1–S4 явно заданы и >=12. Диапазоны H не пересекаются, включая подразумеваемые дефолты. Флаги нормализуются в `on/off` для native `awg`.
4. Лимиты: 256 КиБ/профиль, 16 КиБ/строка, 64 CPS-токена и 4096 суммарных байт на I-пакет, размер одного r/rc/rd 1..1000, Jc <=128. Это начальная локальная ограниченная поддержка; превышение даёт отказ с причиной, а не обрезку.
5. Ключи не входят в обычные JSON/строковое представление parser. HeaderProtectionKey не добавлен в открытые Guided values: он остаётся в защищённом импорте/экспертном редакторе. Маскированный обзор показывает только наличие ключа.
6. Read-only inventory загруженного `amneziawg` и установленной утилиты `awg`, включая `/opt/sbin/awg`. Для AWG 3.x проверяются обе версии. Новый `.ko` на диске не считается загруженным. Нет автоматического insmod/rmmod или перезагрузки.
7. Исправлен native fallback адаптера: AWG создаётся как `type amneziawg`, а не `wireguard`. Advanced 3.x не передаётся старому quick-скрипту. Неизвестная совместимость останавливает запуск до команды создания интерфейса.
8. Endpoint собственного AWG закрепляется в staged-конфигурации за проверенным публичным IP; повторного неконтролируемого DNS в `awg setconf` нет. Смешанные public/private DNS-ответы отвергаются. Импортированное имя сохраняется в исходном профиле.
9. Собственному AWG не навязываются fallback-порты Cloudflare. Canary собственного AWG не требует `warp=on`; WARP WireGuard продолжает требовать этот сигнал на Cloudflare trace.
10. Применение остаётся в прежнем transaction manager. `Table=off` и смысл AllowedIPs не дают разрешения на весь LAN. DNS из конфигурации — данные, не право менять системный resolver.

### API и UI

- GET `/api/v1/amneziawg` — маскированный профиль, возможности, препятствия, `network_verified=false`.
- POST `/api/v1/amneziawg/preview` — разбор без запуска и без записи live.
- POST `/api/v1/amneziawg/import` — `content`, `expected_sha256`, `base_sha256`, `confirm=STAGE_AWG_PROFILE`; только Stage под общей exclusive admission. Не поддержанный оборудованием, но корректный draft можно сохранить.
- POST `/api/v1/amneziawg/canary` — `service_id`, `base_sha256`, `confirm=PROBE_AWG_PROFILE`; existing ProbeCandidate и cleanup, до 110 секунд. Safe Mode и общая остановка блокируют временные сетевые мутации. Произвольного URL запроса в этом API нет.

В панели: файл/текст → redacted preview → явное сохранение черновика → выбор сервиса → изолированная проверка → обычное применение из существующего редактора/сервиса. Импорт не устанавливает runtime и не включает трафик автоматически. Контрольные проверки профиля, загруженного модуля и сетевой доступности разделены.

Успех canary относится к изолированному IPv4 веб-сценарию роутера, а не ко всем LAN-устройствам/IPv6/звонкам/медиа. Эта кнопка не создаёт право автоматического Apply и не подменяет серверный Evidence. Локальный UI-результат привязан к хешу профиля, сервису, runtime и короткому сроку; изменённый/просроченный результат не остаётся зелёным.

## Реализовано: локальный WARP и ограниченное восстановление

В той же вкладке есть второй раздел «WARP-конфигуратор». Он использует **тот же** существующий WARP Manager и native Cloudflare registrar. Дублирующих DOM ID, секретных хранилищ, таймеров или второго процесса панели нет.

Обычный WARP WireGuard и AWG 3.1 на собственном VPS — разные peer-протоколы. Добавление HeaderProtectionKey/RandomTrailers в Cloudflare-профиль не создаёт AWG 3.1 на Cloudflare. Новый WARP нельзя использовать как автоматическое переиздание ключа собственного VPS.

Порядок восстановления в `internal/app/warp_recovery.go`:

1. Сначала Safe Mode, global stop/manual, актуальная политика, отсутствие посторонних несохранённых черновиков, ownership и сеть. Старое поведение генерации до проверки Safe Mode устранено.
2. Наблюдение проверок сервисов: сеть хранится отдельно; несколько событий одного раунда не увеличивают кворум. Между независимыми обычными раундами не менее 30 секунд. Успех хотя бы одного сервиса предотвращает account-wide refresh по отказу соседнего сайта.
3. После кворума выполняется изолированный canary **с прежним живым профилем** и ограниченными WARP-портами. При его успехе ставится repair-кандидат с прежними ключами, без регистрации.
4. Только определённый тип transport-handshake exhaustion, без присоединённой ошибки cleanup, может разрешить следующую ветку. Обычный timeout/ошибка checker/отказ сайта не разрешают регистрацию.
5. Нужны отдельные AllowAccountRefresh и TOS, работающий независимый registration HTTPS control, неизменные policy/network и native generator. Это не доказательство, что перерегистрация устранит общую блокировку UDP: она остаётся ограниченной разрешённой попыткой.
6. Попытка записывается **до** remote POST. Неуспешные/неопределённые попытки расходуют квоту и сохраняются после restart. Existing pending enrollment не повторяется вслепую.
7. Новый профиль остаётся кандидатом. При разрешённом AutoApplyCandidate вызываются existing engine-scoped plan, review guard, canary, Apply и post-health/rollback. При запрете auto-apply остаётся черновик; это режим пользователя, не полная автономия.

Поля новой политики: `check_interval_seconds` (60..3600, старые настройки=180), `allow_account_refresh` (по умолчанию false). Existing threshold/min-services/cooldown/MaxRotations сохраняются. Лимит ограничивает теперь и попытки; начальное значение 1/сутки, pause24h. Интервал обслуживания берётся существующим reconciler: включённый health уменьшает интервал legacy-routes; отдельного browser/engine scheduler нет. Нагрузка и длительность общей exclusive операции требуют аппаратного измерения.

Статусы и кнопки не гарантируют непрерывность TCP/UDP-сессии при смерти удалённого узла. Недоступная Cloudflare, общий WAN/DNS-сбой, лимит, неизвестный исход регистрации, несовместимый kernel или отсутствие разрешённого резерва могут потребовать ожидания/действия. Обходить границы доверия ради зелёного статуса нельзя.

## Что намеренно НЕ сделано

- Не поставлены AWG kernel .ko, `awg` tools или отдельный пакет AWG Manager. Без совместимой **загруженной** пары AWG3.x blocked. Нужен отдельный signed/model/ABI-compatible component pipeline.
- Не реализованы полноценные NativeWG+awg_proxy и amnezia-box/Sing-box AWG backends. Не объявлять их возможностями по чужому README.
- Один основной AWG-профиль/peer в существующем адаптере; несколько одновременно работающих AWG-профилей требуют отдельной registry/binding/lifecycle модели.
- Нет VPS provisioning, server-side key rotation, remote peer synchronisation, новых AWG регистраций у стороннего провайдера.
- Нет вызова публичного генератора, Telegram-бота, внешнего QR, iframe или remote shell.
- Не завершены общая подписанная nightly installation и автоматическая доставка всех движков; существующий check/prepare не превращается в install.
- Не выполнены реальные Cloudflare регистрации, AWG handshakes, маршруты LAN, WAN/reboot/power-loss и 24–72h HIL. Cross-build не заменяет их.

Результаты данного запуска, конкретные бинарники и ограничения см. `VALIDATION_AWG31_WARP_RU.md` и `reports/` в поставке. Предыдущие цифры R5 не выдаются за новые тесты.
