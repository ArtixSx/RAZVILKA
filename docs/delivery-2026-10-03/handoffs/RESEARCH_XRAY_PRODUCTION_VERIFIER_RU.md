# D03: production verifier для scoped Xray без постоянного LAN-агента — 04.10.2026

Запрос координатора: scoped Xray runtime уже есть, но production `NodeTUNProbe=nil` требует external selected/control callback; обычный пользователь не может включить этот backend. Нужен небольшой настоящий verifier, который проверяет actual TUN, отдельно показывает LAN evidence и не подменяет его loopback SOCKS. Это **дизайн и чтение кода**, production/runtime/tests/live не изменены и не запускались. Межчатовых сообщений VLESS/root не отправлено; документ передаётся координатору для распределения.

Baseline runtime: `delivery-review` commit `f1d0768170458cf07c9d45f17c1bc580e486e386`; VLESS source snapshot HEAD `76d817b1fb45db9c280f6fe8582866956c868208`. Абсолютные source links указывают текущие worktrees, а не immutable export. Новые имена API/файлов ниже — предложения, не уже реализованные symbols. Native acceptance на Keenetic/Netcraze остаётся у координатора.

## 1. Решение: два уровня вместо неподключённого callback

Первый production slice: IPv4 TCP HTTPS к **уже разрешённому, pinned service IP** через существующий live gVisor TUN → loopback SOCKS → scoped Xray node. Origin — собственный действительно назначенный адрес TUN роутера, не подставленный адрес LAN-клиента. Обычный kernel TCP socket привязывается к source+owned TUN device и получает короткую scoped RPDB lease. Это проходит через настоящий TUN в обе стороны, поэтому сильнее отдельного SOCKS canary.

Apply принимает только совокупность `RuntimeOwned + ForwardingConfigured + RouterTUNService` при неизменных generation/receipts. `LANFlowObserved` и `LANServiceObserved` остаются отдельными полями: после Apply сначала unknown; первое можно подтвердить реальными пересылаемыми пакетами на роутере, второе — доверенной одноразовой проверкой с устройства. Это **новый согласованный capability/evidence contract CORE**, а не разрешение просто убрать nil-check и объявить нынешний `NodeTUNObservation` полученным.

Пользовательский результат: «Маршрут применён; TUN и сервис проверены с роутера. Трафик выбранного устройства ещё не подтверждён». Открытие сервиса устройством может повысить LAN-flow статус без постоянного агента на ПК. Включение полного LAN application PASS требует своего доказательства и не происходит от счётчика либо router probe.

## 3. Конкретный RouterTUNService algorithm

Один verifier запускается в existing Manager operation/effect authority, после Activate и до Commit; тот же verifier пригоден для bounded committed health **с отдельным CORE effect grant для временной probe lease**. Добавление/снятие RPDB — kernel mutation; read-only `ObserveCommittedRuntime`/status/health admission не дают такого разрешения. No reconcile/start/stop из verifier. Proposed budget: 10s на один service probe, 30s на batch, existing evaluator response limit32KiB, concurrency1, явный лимит числа targets; превышение — incomplete coverage, а не partial global PASS. Точные time/count limits и состав representative probes согласуются с существующим service catalog; это не измеренная производительность.

1. Получить immutable current Plan, private scoped manifest, materialized service destinations и exact `{engine,nodeID,serviceID,probeURL,pinnedIP}`. Probe destination должен уже принадлежать request и фактически configured Xray IP rule соответствующего node. Разрешить redirects только как заранее проверенный catalog contract; каждый новый target обязан быть уже admitted. Не добавлять ipify/Cloudflare либо весь CDN subnet ради health.
2. Проверить [runtime identity](C:/Projects/RAZVILKA/delivery-review/internal/dataplane/proxy_node_identity.go:48), launcher receipt/process start ticks, engine+sidecar executable identity и args/config hashes/netns, socket owner и [owned interface](C:/Projects/RAZVILKA/delivery-review/internal/dataplane/proxy_node_interface.go:81). Current executable check — path/`SameFile`, не digest содержимого; integrity digest при необходимости отдельный component contract. Bind identity включает bootID/network/control/policy generation, runtimeID и ifindex; одинаковое имя интерфейса после recreate не достаточно.
3. Выбрать **действительно назначенный** owned TUN IPv4 source из `TunnelCIDR`, проверенный на интерфейсе. Для Xray current default — `rz-xray`, `172.31.22.1/30`; это пример, не предположение о каждом runtime. Не bind LAN address, не `IP_FREEBIND`/`IP_TRANSPARENT` для имитации устройства. Проверить family/source/ifindex до Dial.
4. CORE выдаёт короткую typed `NodeTransitLease`: exact local source `/32` + `oif=ownedTUN` + pinned destination `/32` → owned TUN route/table. Перед добавлением snapshot/preflight foreign conflicts; priority/table из общего allocator, не hardcoded WG slots219/18050. Нет default policy для всего router OUTPUT. `oif` в upstream iproute2 selector доступен для локальных сокетов, привязанных к устройству: [primary iproute2 man source, pinned commit](https://kernel.googlesource.com/pub/scm/network/iproute2/iproute2/+/6e15d27aae947510efd824c7ce4bc7ea3b8a5aae/man/man8/ip-rule.8).
5. Kernel TCP Dial идёт к literal pinnedIP:443 с real local source и проверяемым `SO_BINDTODEVICE`. Existing [wgSocketDialer](C:/Projects/RAZVILKA/delivery-review/internal/dataplane/wg_canary_socket.go:13)/[Linux binding](C:/Projects/RAZVILKA/delivery-review/internal/dataplane/wg_canary_socket_linux.go:11) дают пригодный primitive, **не готовую Xray lease/lifecycle**. Ошибка binding закрывает probe. TLS использует original catalog SNI/Host, стандартную проверку certificate; proxy env выключен. Этот HTTP transport не вызывает SOCKS dialer и не fallback-ит на обычный WAN Dial.
6. Фактический путь: kernel OUTPUT packet → owned TUN fd → gVisor → existing literal-IP SOCKS hop → exact scoped Xray destination/node → удалённый service → обратно в TUN → local socket. Current sidecar выбирает gVisor и не создаёт маршруты сам: [buildSOCKSTunnelConfig](C:/Projects/RAZVILKA/delivery-review/internal/dataplane/proxy.go:1715). Upstream описывает gVisor как L3→L4 translation; актуальная документация отдельно меняет stack в1.15, поэтому capability проверяется для установленной версии, не для «latest» абстрактно: [Sing-box TUN](https://sing-box.sagernet.org/configuration/inbound/tun/).
7. Ответ проверяется существующим строгим [service evaluator](C:/Projects/RAZVILKA/delivery-review/internal/probecheck/check.go:19); TCP connect, TLS handshake или произвольный HTTP200 отдельно не заменяют semantic criterion сервиса. Записать tuple local socket, chosen literal target, timing и результат. Проверить runtime/network/control/manifest/ifindex и exact lease readback после ответа; любой drift отменяет proof.
8. Закрыть все sockets, cancel/join probe; удалить **только exact owned temporary lease**, verify removal до возврата. Ownership intent должен быть durable до первого kernel add и иметь crash/reboot recovery внутри existing transaction resources. Для committed/background проверки нужен новый private attempt root, например `StateRoot/<engine>/transit-probes/<attemptID>`, зарегистрированный в Manager recovery authority; original committed policy receipt не переиспользуется/не переписывается при каждом probe. Это отдельный resource receipt текущего lifecycle, не второй control journal. Known cleanup разрешает bounded GC; unknown attempt остаётся fenced. Cleanup unknown/Stop race → recovery fence; успех сети не превращается в Commit при неизвестном cleanup. Stop не ждёт нового внешнего LAN callback.

Capability preflight/native acceptance должен подтвердить, что конкретная gVisor/ядро комбинация принимает source собственного TUN адреса и возвращает ответ локальному kernel socket. Effective `rp_filter` на return TUN path — отдельная проверка: strict reverse lookup может выбрать WAN и отбросить router-bound ответ, поскольку local-only `oif` selector не является гарантией input reverse FIB. Ни global sysctl rewrite, ни предположение о native fixture settings не допустимы; несовместимый текущий mode закрывает capability. Если assigned source/return path не работает, **первый slice UNAVAILABLE**; другой probe address требует отдельного конкретного address/ownership/return-path contract и не является fallback этого алгоритма. Нельзя молча переключиться на SOCKS и сохранить тот же proof label. Поддержка `oif`/checked binding/parser/readback на установленном Entware ip/kernel тоже проверяется. Эти проверки здесь не выполнялись.

Primary Linux contract: strict reverse-path check сверяет incoming interface с лучшим reverse FIB; effective mode берётся как max(all,interface), а `src_valid_mark` отдельно задаёт участие mark. Это причина проверить оба значения и текущие tuple routes, не только interface setting. Применение к proposed local TUN probe — проектный вывод, не измеренный отказ на Netcraze. [Linux IP sysctl](https://www.kernel.org/doc/html/latest/networking/ip-sysctl.html).

Изоляция от loopback: scoped lease совпадает только с TUN-source/oif/pinnedIP; фактические Xray backend remote sockets должны быть доказанно disjoint с этим selector. Current materializer не гарантирует их WAN source/device binding: verifier проверяет реальные process-owned source/oif/egress и generation либо CORE/VLESS добавляют строго ограниченный backend egress contract. Unknown isolation закрывает probe, без предположения о bind. Проверить exact service/node selection. Backend materializer сохраняет отказ conflicting destination owners: fixed SOCKS hop теряет LAN source, source-disjoint RPDB не создаёт source-aware Xray routing для одного shared destination разных nodes. Baseline [scopedXrayRules](C:/Projects/RAZVILKA/delivery-review/internal/dataplane/proxy_nodes.go:184) проверяет одинаковые keys; более строгие nested/overlapping scope checks прочитаны отдельно в [VLESS snapshot](C:/Projects/RAZVILKA/worktrees/sol-vless/internal/dataplane/proxy_nodes.go:184), не приписаны baseline.

## 4. Typed evidence и правдивый normal Apply

Proposed `ProxyNodeRuntimeHealth` — новое immutable DTO с независимыми результатами и причинами. Каждый proof привязан к plan/config/manifest hash, bootID, control/network epoch, runtimeID+ifindex, engine/node/service, observedAt/expiresAt. Flow proof дополнительно включает exact original 5-tuple, selected/control role, actual ingress/device binding revision и источники наблюдения. API JSON не может сам создать receipt.

| Поле | Что означает PASS | Чего оно не доказывает |
|---|---|---|
| `RuntimeOwned` | Exact live process/config/socket/interface receipts совпали | Сервис или LAN пакеты прошли |
| `ForwardingConfigured` | Native source+iif+destination policy, chain order/NAT exemptions; effective forwarding/rp_filter prerequisites и relevant conflict snapshot проверены | Foreign ACL/клиент реально пропускает пакет; настройки нельзя автоматически переписывать ради PASS |
| `RouterTUNService` | Новый ordinary socket прошёл actual owned TUN и pinned service evaluator | LAN PREROUTING/FORWARD/MAC/DNS/IPv6/QUIC |
| `LANFlowObserved` | Current selected exact original flow реально наблюдён LAN→TUN и обратный flow TUN→LAN в same generation; control отдельно | Зашифрованный service application принят; IP является именем домена |
| `LANServiceObserved` | Доверенная LAN application probe/receipt для exact flow и service criterion | Все адреса/протоколы/другие устройства сервиса проверены |

States PASS / UNKNOWN / UNAVAILABLE / BLOCKED / INCONCLUSIVE должны различаться. `UNKNOWN` LAN при выключенном компьютере не становится failure engine health. Изменённый binding/runtime/epoch либо expiry понижает соответствующий статус, не переписывает history как current. Fresh router service PASS не повышает `RouteEvidence.Observed` до client-selection/service proof: [existing Manager source-scoped evidence boundary](C:/Projects/RAZVILKA/delivery-review/internal/dataplane/manager.go:1477) сохраняется.

Для normal Apply обязательны первые три fields только после native acceptance данного backend/capability. Нельзя продолжить активацию, если configuration/readback/owner/probe не прошли. Установка policy и выполнение validated router transit не означают закрытие всего D03; выбранная/контрольная LAN application приёмка остаётся отдельным критерием release/HIL. Согласование split устраняет неопределённый external production dependency и сохраняет границу доказательности.

Optional direct WAN control к тому же pinned IP идёт по отдельному подтверждённому baseline grant. Недоступность direct сервиса при блокировке провайдером ожидаема и не отменяет успешный bypass probe. `SelectedEgress/ControlEgress` нельзя заполнять внешними IP из других запросов, DNS или выбранного интерфейса.

В native [test service](C:/Projects/RAZVILKA/delivery-review/internal/dataplane/proxy_nodes_native_linux_test.go:174) controlled HTTPS server возвращает observed `RemoteAddr`; обычный Telegram/Netflix/YouTube такого контракта не даёт. Поэтому production egress остаётся unknown, если сам authorized test service не возвращает его. Existing [isolated node egress check](C:/Projects/RAZVILKA/delivery-review/internal/dataplane/node_egress.go:35) полезен для candidate identity, но не сертификат live LAN TUN. Разные public IP сами по себе не uniquely identify node ownership.

## 5. LAN наблюдение с роутера: следующий bounded slice

Router-side observer не требует программы на компьютере. Внутри той же owned firewall/receipt grammar предлагаются точные packet observation points: selected packet на exact LAN ingress с current MAC binding/original 5-tuple; packet перед выходом в owned TUN; return packet из same owned ifindex и далее к client на LAN. Для control — отдельная исходная tuple вне **всех** selected scopes, с baseline egress, без TUN traversal. NAT exemption existing adapter сохраняет client source для **нового** NAT решения, не отменяет старый SNAT mapping. Proof принимает наблюдённый flow-start/SYN и conntrack generation/mapping либо уже доказанный непрерывный owned flow; reused 5-tuple без этой связи недостаточен.

Это новый механизм, не нынешний `verifyForwarding`: ограниченные owned NFLOG/аналогичные доступные kernel observations с exact filters, event budget/drop detection и before/after owner checks. NFLOG hook может предшествовать последующему DROP и **сам по себе только HookObserved**, не `LANFlowObserved=PASS`. Нужны actual interface/terminal-verdict evidence либо, для первого TCP slice, корреляция sequence/ACK: ответ из owned TUN и последующий ACK этих bytes от actual client на LAN ingress, связанные с новым flow и original tuple. Так подтверждается доставленный обратный packet и живой TUN path; несовместимый/неполный capture остаётся inconclusive. Нельзя взять общий interface/chain counter и приписать его сервису. Observer read/parse не меняет routes и не reconcile; установка/снятие observation hooks — только existing Manager effect admission. Kernel/module support и влияния packet offload/FastPath/hardware acceleration требуют native capability проверки; если path обходит hooks, отсутствие событий inconclusive, не failure. Не отключать firmware offload глобально ради доказательства.

Correlated TCP tuples/sequence/direction/bytes подтверждают пересылку и ответ в поддержанной capture path, не расшифровку TLS и не service success. IP-origin observation не заполняет FlowName для domain policy. Budget overflow, unknown NAT/remapping, ifindex/epoch/binding drift → inconclusive. Ни payload collection всего LAN, ни broad conntrack flush не нужны; минимальные tuple/counters records с короткой retention достаточны.

Наивысший LAN service proof даёт optional **одноразовый** trusted selected/control probe на доступном тестовом ПК/устройстве: pinnedIP, original SNI/Host, strict service evaluator, runtime nonce/generation, source tuple и сопоставление router observation. Он нужен для независимой приёмки, не каждого Apply/постоянного background daemon. Обычная кнопка в браузере не обеспечивает автоматически IP pinning/SNI/CORS/remote egress; self-report API не превращается в trusted receipt. Можно показывать «пользователь подтвердил работу» отдельным UX полем.

## 7. Матрица coordinator acceptance

1. Ordinary scoped Xray Apply без external callback: checked owner/forwarding/router-TUN service и unknown LAN; Commit только после exact lease cleanup. Service evaluator отказ/TLS mismatch/target вне materialization не PASS.
2. Packet capture подтверждает ordinary socket действительно идёт в TUN и обратно; отключённый/заменённый TUN, sidecar, node, binding failure или fallback WAN дают отказ. Actual node выбран exact destination; чужой/baseline service не подменяет результат.
3. LAN selected/control реальные устройства к одному admitted test target: original ingress/MAC/source scopes, FORWARD/NAT, TUN traversal selected и отсутствие TUN control; semantic selected service и отдельно control outcome/egress. Foreign earlier ACL не bypass-ится.
4. Runtime/ifindex/network/control/policy/source binding меняются между lease, Dial, reply и Commit; timeout/Stop, partial add/remove, crash/reboot; cleanup unknown сохраняет fence. IPv4-only probe не объявляет IPv6/UDP/QUIC/voice/media accepted.
5. Компьютер выключен, observer event drop/FastPath, LAN receipt expired: user status unknown/inconclusive, живой проверенный runtime не зацикливает recovery. Direct WAN control blocked не отменяет успешный router TUN service.

Матрица здесь **не запускалась**. Проверка документа: source/code contracts + первичные upstream sources; package/kernel/runtime support не проверен. Реализацию, локальные targeted code tests и native/HIL выполняют владельцы/координатор в своём окне. До реализации нового typed contract текущий fail-closed nil gate сохраняется.
