# NET: named WireGuard profile API checkpoint

Готовый handler factory находится в `internal/app/wireguard_profiles.go` и регистрирует `/api/v1/wireguard/profiles` и путь с ID. Он получает каталог через принятый `Manager.WireGuardProfileCatalog`: тот же явно зарегистрированный Store используется WG runtime. Создание второго Store и обнаружение его пути из HTTP отсутствуют.

- GET collection: `{profiles:[{profile:{id,name,revision,engine,verification},route,reserve,references}],config_revision}`; GET ID возвращает один такой view. Revision — полный hash привязки ID, имени и нормализованного приватного config; private config/endpoint/ключи в ответ не попадают.
- POST collection: `{id,name,content}`; PUT ID: `{name,content,expected_revision}`; DELETE ID: `{expected_revision}`. Успех возвращает `saved` или `deleted`, `live_applied:false`. Syntax-only не даёт check/Apply evidence или автоматического разрешения переключения. `reserve` означает только сохранённый профиль без известных ссылок.
- Auth обязателен даже для GET до setup; обычный Security middleware даёт JSON/Origin CSRF barrier. Для mutation factory повторно использует **существующий** exclusive operation admission. CORE обязан добавить WG prefix в exclusive predicate и вызвать factory из actual Handler; этот checkpoint сам общие app/main/operations файлы не меняет.
- Read/mutation держат реальный Store.BeginRestore full-image/file lease, читают InspectBytes, не вызывают Store.Get/Update под его lock. Никакой альтернативный config CAS не добавлен. Ссылки включают выключенные draft, applied, suspended routes/services, обе network default policies, latest и committed планы. Plan/private owner authority проверяется до изменения и снова после него; незавершённый execution/WG operation и partial/orphan runtime удерживают удаление. Ошибка readback/close после catalog CAS вызывает причинный CAS undo и публичный `outcome:unconfirmed`; отдельный флаг сообщает, подтверждён ли undo. Неизвестный I/O результат не выдаётся за сохранение или известный CAS отказ.
- Новый `CheckWireGuardProfileReferenceAuthority` только читает существующее WG ownership/reference и transaction journals. Он не выполняет cleanup, Stop, recovery settle или probe.

Проверки Windows: `go test ./internal/app -run '^TestWireGuardProfile' -count=1` — PASS; auth/pre-setup, CSRF, приватность, create/replace/delete CAS, все retained reference scopes, disabled draft, pending/committed plan, чужой файл, unfinished journals/orphan runtime, late plan change с успешным/неизвестным undo, существующий config lease. Отдельная проверка общего Handler после CORE wiring ещё обязательна. Native Linux, race и actual startup регистрация здесь не заявлены; D05/D12 целиком не закрыты.

Manual assignment `wireguard:<id>` должен использовать обычный CORE service writer с его policy fence. Factory не записывает service choices, не запускает Apply, не выдаёт автоматический резервный маршрут. UI check/Apply progression должен показывать trusted evidence именно текущего profile revision и runtime generation; такого evidence CRUD не создаёт.
