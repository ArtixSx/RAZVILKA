## Решение и закреплённая база

Для первого прототипа предлагается **отдельный owned TUN для одной физической admission class → tun2socks/core → DomainPolicy.HandleTCP → выделенный loopback inbound выбранного Xray node**. Один допущенный MAC, один ingress, IPv4 public TCP80/443. TUN и kernel additions остаются у существующего Adapter/Manager; библиотека создаёт только TCP stack и net.Conn. Этот путь не требует импорта всего sing-box, его router/config/lifecycle или второго менеджера.

В этом mode embedded stack заменяет чтение named TUN внешним sing-box sidecar: два reader/process не подключаются к одному интерфейсу. Нынешний fixed SOCKS mode сохраняется как отдельная проверенная capability; его runtime proof автоматически в новый mode не переносится.

Stock sing-box может самостоятельно sniff/route внутри своего процесса. Но проверенный TUN→SOCKS путь не доставляет original source tuple и admission generation в наш Go consumer; stock sniff не обеспечивает его NameState/Stop/Lease contract. Поэтому ранее предложенное расширение stock builder из `RESEARCH_UI_TUN_AUDIT_RU.md` остаётся ссылочной возможностью самостоятельного routing, а не готовым подключением нынешнего Go guard.

## Что уже написано и чего не хватает

[domain_policy_tcp.go](C:/Projects/RAZVILKA/worktrees/sol-lan-dns/internal/dataplane/domain_policy_tcp.go:17) принимает `Generation`, `FlowID`, original `Source`/`Destination`, trusted `ClientPacket`, coverage и coalescing state. HandleTCP проверяет scope до чтения, разбирает ограниченный prefix, повторяет guard перед Dial и первым payload, передаёт прочитанные bytes один раз и присоединяет relay при Stop. Dial получает literal destination. `BaselineDial` требует отдельного доказательства baseline. Это actual byte consumer, но **не listener, не TUN reader и не source producer**. Production call site HandleTCP в прочитанной интеграции не найден.

[lan_policy_runtime.go](C:/Projects/RAZVILKA/worktrees/sol-lan-dns/internal/dataplane/lan_policy_runtime.go:180) выполняет early negative MAC/address gate для обеих IP families, затем positive membership. [LANPolicyReceiptBinding](C:/Projects/RAZVILKA/worktrees/sol-lan-dns/internal/dataplane/lan_policy_runtime_binding.go:9) связывает additions с общим receipt и запрещает удаление gate при remaining/unknown consumers. Suspension знает exact capture class после mangle admission и retained protected flow. Ни gate mark, ни совпавшая conntrack tuple сами по себе не создают TCPFlow authority.

В [proxy.go](C:/Projects/RAZVILKA/delivery-review/internal/dataplane/proxy.go:1717) TUN sidecar имеет gvisor, auto_route=false, один fixed SOCKS final; для schema1.14 DNS отключается явно. [proxy_nodes.go](C:/Projects/RAZVILKA/delivery-review/internal/dataplane/proxy_nodes.go:202) честно отказывает destination-overlapping node owners: LAN source теряется после общего SOCKS hop. В прочитанном production коде нет готового `Dial(nodeID, generation, originalDestination)` с revocable LAN flow lease. Egress/probe dialers не являются таким producer или lease.

## Почему одного stock config недостаточно

В [sing-box TUN inbound](https://github.com/SagerNet/sing-box/blob/af6e64c3b69e6132ebaee0e1a3d24e93903f6709/protocol/tun/inbound.go#L528) callback имеет conn+source+destination и кладёт обе стороны в InboundContext. В [SOCKS outbound](https://github.com/SagerNet/sing-box/blob/af6e64c3b69e6132ebaee0e1a3d24e93903f6709/protocol/socks/outbound.go#L65) вызов клиента получает network+destination. [Общие DialerOptions](https://github.com/SagerNet/sing-box/blob/af6e64c3b69e6132ebaee0e1a3d24e93903f6709/option/outbound.go#L75) этого пути не предлагают передачу original source/generation в SOCKS. Loopback peer в Go — адрес sing-box, не LAN client; отдельный port на клиента даёт class context, но не потерянный source port. Наличие go-proxyproto в module graph не доказывает экспорт metadata в этом пути. Новый authenticated metadata bridge был бы дополнительным протоколом/изменением upstream, его реализация stock config не подтверждена.

Текущий [TLS parser1.14.2](https://github.com/SagerNet/sing-box/blob/af6e64c3b69e6132ebaee0e1a3d24e93903f6709/common/sniff/tls.go) возвращает ClientHelloInfo.ServerName и protocol, не отдельную ECH/ambiguity authority. Native LAN parser уже имеет visible/absent/ambiguous/encrypted-outer-only/timeout/bound-exceeded/opaque. Замена его stock sniff без сохранения этих состояний нарушила бы существующий contract. Ни source rules внутри sing-box, ни Xray routeOnly после fixed SOCKS не восстанавливают физический ingress/MAC.

## Библиотека и ABI: узкое подключение

У sing-tun [StackOptions/NewStack](https://github.com/SagerNet/sing-tun/blob/ddaa4ca25e3bcb776d6ce81f4477b3becb5426de/stack.go) и [gvisor TCP callback](https://github.com/SagerNet/sing-tun/blob/ddaa4ca25e3bcb776d6ce81f4477b3becb5426de/stack_gvisor_tcp.go) непосредственно сохраняют original tuple. Однако [LICENSE](https://github.com/SagerNet/sing-tun/blob/ddaa4ca25e3bcb776d6ce81f4477b3becb5426de/LICENSE) — GPL-3.0-or-later. Встраивание в распространяемый Go binary нельзя представить как обычную MIT dependency без отдельного решения о лицензионных условиях. System stack к тому же реинжектирует TCP в случайный local listener с NAT session lookup и требует INPUT lease; это уже объяснённый отказ в нашем builder. Go module sing-tun требует Go1.25, x/net0.57 против текущего0.56 и включает netfilter/netlink/gvisor dependencies.

У альтернативы tun2socks/core проверены конкретные публичные API:

1. [core.CreateStack(Config)](https://github.com/xjasonlyu/tun2socks/blob/4127937ea7c450a5230b273f406c9410acec2be7/core/stack.go) принимает LinkEndpoint и TransportHandler. Adapter передаёт собственный endpoint; `engine.Start`, global engine state, proxy/router пакеты и automatic interface configuration не импортируются.
2. [TCPConn](https://github.com/xjasonlyu/tun2socks/blob/4127937ea7c450a5230b273f406c9410acec2be7/core/adapter/adapter.go) — net.Conn с ID. В [core/tcp.go](https://github.com/xjasonlyu/tun2socks/blob/4127937ea7c450a5230b273f406c9410acec2be7/core/tcp.go) ID сохраняется из ForwarderRequest: `RemoteAddress:RemotePort` = LAN source, `LocalAddress:LocalPort` = original destination. Это producer из actual packet stack, без DNS/IP догадки.
3. [fdbased.Open](https://github.com/xjasonlyu/tun2socks/blob/4127937ea7c450a5230b273f406c9410acec2be7/core/device/fdbased/fd_unix.go) принимает числовой FD, а [Linux endpoint](https://github.com/xjasonlyu/tun2socks/blob/4127937ea7c450a5230b273f406c9410acec2be7/core/device/fdbased/open_linux.go) использует gvisor fdbased с EthernetHeader=false. FD wrapper Close закрывает FD: ownership необходимо передать один раз, исключить двойное Close/FD reuse. Сам gvisor endpoint FD не владеет и требует оставить его открытым до reader Wait; его Close пустой, зато Attach(nil) останавливает dispatchers и joins reader. Число FD не приходит из HTTP/config.
4. Kernel owner открывает `/dev/net/tun`, создаёт exact named `IFF_TUN|IFF_NO_PI` интерфейс, MTU1280, без vnet/GSO header и persistent/multiqueue режима в первом slice. [Linux TUN ABI](https://docs.kernel.org/networking/tuntap.html) отдаёт IP packets; там нет исходных Ethernet MAC, iif, skb mark или policy generation. Ifreq/ioctl выполняются архитектурным x/sys Linux wrapper, не захардкоженной 64-bit memory layout. Flags/MTU/ifindex/readback входят в existing owned receipt.
5. [MIT LICENSE tun2socks](https://github.com/xjasonlyu/tun2socks/blob/4127937ea7c450a5230b273f406c9410acec2be7/LICENSE) и [Apache-2.0 gVisor](https://github.com/google/gvisor/blob/eede7a881b20000bcaa22e7c17c63bc027f6a2b2/LICENSE) позволяют рассматривать этот candidate без GPL relicensing requirement; соответствующие notices всё равно входят в distribution review. go.mod tun2socks требует Go1.23.1, gVisor указанного pin и x/time0.11; весь module graph шире фактически импортируемых core packages. Точный `go list -deps`/MVS/SBOM ещё предстоит, здесь размер binary/graph не измерен.

[Upstream Makefile](https://github.com/xjasonlyu/tun2socks/blob/4127937ea7c450a5230b273f406c9410acec2be7/Makefile) задаёт CGO_ENABLED=0, linux armv5/6/7, arm64, amd64, mips/mipsle softfloat/hardfloat; соответствующие [release assets2.6.0](https://github.com/xjasonlyu/tun2socks/releases/tag/v2.6.0) действительно перечислены API. Это наличие upstream artifacts, **не доказательство** сборки RAZVILKA с Go1.26.5 и текущими selected dependencies или работы на Keenetic kernel4.9. Минимальный admission gate: isolated compile matrix amd64/arm64 + actual router arch/endianness/GOMIPS, Затем native TUN/ioctl/packet/Stop acceptance. C library/Entware loader ABI для этого core пути не требуется; kernel ABI и runtime arch остаются обязательными.

## Как не потерять физический допуск и generation

Первый TUN нельзя делить между несколькими MAC/ingress classes. Его trusted frozen descriptor принадлежит одному reviewed ingress+MAC, public TCP80/443 selector, LAN digest/control epoch/generation и original interface instance. Только exact capture rules с positive admission перед routing направляют пакеты в него; WAN, guest, router OUTPUT и неподтверждённые clients не имеют пути к этому FD. IPv6 negative gate сохраняется, хотя named slice IPv4-only. Любое unknown ownership/readback сохраняет fence.

NET должен компилировать selector в существующий addition plan: после LAN mangle gate проверить exact iif/source/MAC+admitted mark, public destination и TCP dports80/443; поставить отдельный reviewed capture mark с собственной collision-checked mask, направить его exact iif+mark RPDB rule в owned TUN table. Admission bits и чужие marks не перезаписываются. Значение нового mark/table/priority здесь не назначается без текущего allocator/firmware admission. На kernel4.9 не рассчитывать на sport/dport ip-rule как замену packet selector. Один public default route без селектора захватил бы также DNS/UDP и не соответствует first slice. Capture effect/rule order и exclusion of local/private/tunnel/bootstrap endpoints требуют общего receipt/readback; production compiler этого descriptor здесь не реализован.

В HandleTCP wrapper адреса берутся из TCPConn.ID; `ClientPacket` получает **физическую class identity из trusted capture descriptor**, а Address — из actual source tuple. Это допустимо лишь при доказанной единственной class для FD и полном current gate/capture ownership. Это не измеренный MAC внутри TUN, не ARP lookup после capture и не доказательство от spoofing допущенным устройством. При shared FD либо неизвестном альтернативном пути к TUN такой способ запрещён; потребовался бы отдельный per-flow metadata producer перед потерей L2 контекста.

FlowID назначает тот же capture owner для нового TCP instance и связывает original5-tuple, FD instance и frozen generation с revocable flow lease. Одна 5-tuple без instance недостаточна после повторного соединения. Bounded active-flow bookkeeping живёт в существующем adapter runtime, не создаёт второй durable journal/epoch/manager. Runtime.Guard проверяет class admission, неизменный plan/control epoch, lease и tuple перед parse/Dial/payload; Runtime.Lease synchronously invokes forward once и joins. Эти hooks ещё должны быть подключены владельцами, одних DTO и kernel tuple readback недостаточно.

Startup: staged node listeners/stack готовы при closed capture → gate и exact owned rules/routes подтверждены → capture открывается последним. При Stop сначала прекращается callback admission и перекрывается retained exact capture class; затем endpoint.Attach(nil) останавливает и joins TUN reader при ещё открытом FD, отменяются и присоединяются flow leases, stack.Close/Wait и оставшиеся endpoint writers. Лишь после этого FD wrapper.Close освобождает owned FD, затем node retirement и exact additions cleanup. [fdbased Attach/Wait](https://github.com/google/gvisor/blob/eede7a881b20000bcaa22e7c17c63bc027f6a2b2/pkg/tcpip/link/fdbased/endpoint.go#L418) и [Stack.Close/Wait](https://github.com/google/gvisor/blob/eede7a881b20000bcaa22e7c17c63bc027f6a2b2/pkg/tcpip/stack/stack.go#L1901) — разные barriers: один Close не является settlement. Process death/reboot теряет in-memory flows; existing persisted receipt/fence остаётся до cleanup readback, поток не возрождается по старому FlowID. Rollback меняет admission generation только после old-flow settlement; unknown consumer оставляет gate+fence.

## Выбранный outbound и DNS

Go решает route до любого upstream Dial. Для prototype: один управляемый Xray процесс с **двумя private SOCKS inbounds** для default node A и service node B. Каждый inbound имеет уникальные frozen port/tag и правило `inboundTag → exact outboundTag`; остальные входы/traffic ведут в explicit blackhole. [Xray routing contract](https://xtls.github.io/en/config/routing.html#ruleobject) поддерживает такой выбор. Не создавать отдельный Xray process на каждый flow.

Dial callback по `decision.Route` получает уже проверенный binding node ID → generation/process identity/listener/config digest. Он connects к соответствующему literal loopback SOCKS, отправляет original numeric destination IPv4:port, не SNI hostname. Domain/source policy больше не выбирается повторно по shared destination в Xray. Нужны exact listener ownership и cancellation на каждом выбранном входе. Удалённый/сломанный совпавший node — execution failure, не переход в иной default/DIRECT. Модель default/service на разных соединениях к одному IP теперь различается портом выбранного inbound.

Это **изменение trusted materializer и validator у VLESS**, а не разрешение принимать arbitrary Xray JSON. Текущий validator ожидает один inbound и старые destination rules; он не поддерживает описанный mapping. Его отказ overlap в старом режиме сохраняется. Новый mode/version должен валидировать весь frozen inboundTag→node map и запретить sniff destination override, balancer/re-resolution/неявный fallback. CORE/DEFAULT coverage не считается достаточной только потому, что появился SOCKS listener. WG default/service, Usque, NFQWS комбинации в этом first slice не доказаны.

Для target TCP **per-flow DNS не нужен**: original destination уже дан packet stack. Resolver не выбирает новый адрес по sniffed имени. DNS для tunnel endpoints — отдельные frozen bootstrap pins с guard; provider queries — отдельный existing LAN DNS consumer со своим client/ingress/generation lease, response TTL/CNAME contract. DNS observations никогда не дают FlowName authority. FakeIP/reverse mapping не вводятся. UDP/TCP53 не должны случайно попасть в этот TCP80/443 TUN.

Первый executable slice допускает только policy, у которой требуемый default и override покрыты выбранными nodes. Visible known miss/removed override/source mismatch/direct-IP идут в явный default по текущей visibility policy. Domain exclusions/unknown/ECH не реализуются обычным router direct socket: без отдельного NET baseline grant соответствующая mandatory capability при review отказывается либо использует явно согласованный scoped block. Полное baseline LAN forwarding этим TCP proxy не доказано. TLS SNI относится к соединению; поздние encrypted HTTP2 coalesced requests нельзя обнаружить/перемаршрутизировать по этому имени. Coalesced flag не считается автоматически измеренным самим TLS parser.

## Альтернативы и проверяемая следующая порция

| Вариант | Что даёт | Почему не выбран для первого TUN→Go prototype |
|---|---|---|
| Stock sing-box1.14.2/Xray config | mature TCP stack и routing внутри engine | Нет доказанного original source+generation bridge в Go; native NameState/Lease guard остаётся вне пути |
| Embedded sing-tun gvisor | прямой original tuple callback | GPL boundary, более широкий package surface; system/mixed требуют собственного INPUT lease |
| tun2socks/core + supplied TUN FD | original tuple net.Conn, MIT/Apache components, CGO0 upstream matrix | Предпочтительный candidate, но capture class proof, outbound binding, dependency/Stop/resource acceptance ещё нужны |
| REDIRECT + SO_ORIGINAL_DST | net.Conn без новой TCP-stack dependency | [Kernel docs](https://www.kernel.org/doc/html/latest/networking/tproxy.html) прямо предупреждают о race original destination; нужен trusted NAT receipt и INPUT lease, не автоматический equivalent TUN |
| TPROXY + IP_TRANSPARENT | kernel TCP, original destination без NAT | Требует подтверждённых socket/TPROXY modules, RPDB/local route и INPUT ownership; capability на нашем kernel не проверена |

Следующая implementation portion: LAN связывает TransportHandler с HandleTCP и isolated class descriptor; NET/DEFAULT доказывают capture/gate/routes+baseline coverage; VLESS добавляет frozen per-node inbound map; CORE удерживает общий authority и adapter lifecycle. Это конкретные пробелы существующих владельцев, не новый standalone proxy/control plane.

Обязательная приёмка: два controlled TLS имени на одном IP выбирают A/B; original source/sport и dest/port остаются в matching flow receipts; fragmented TLS/HTTP1 bytes доходят byte-for-byte один раз. Excluded MAC с чужим/IP-spoofed source, новый IPv6 privacy address, WAN/guest/OUTPUT и direct listener access не достигают owned capture/DNS/NFQ. Miss/deleted override идут в default; absent matched node отказывает. Stop barriers до parse/Dial/первого byte, sidecar death, stale generation, FD reuse и rollback не создают новый outbound после revoked admission; gate не удаляется при unknown capture.

Отдельный resource gate нужен до router rollout. Upstream core TCP forwarder допускает `2<<10` pending attempts, не proposed128 application flows; public API не предоставляет отдельного maxConnAttempts option. TCP buffers и packet queues также требуют измеренного budget. Лимит128 в callback сам по себе не ограничивает SYN/handshake ресурсы. Bounded handler parsing до64KiB/2s уже существует, но выбранные production limits, upstream backlog containment и RAM/CPU на actual router ещё не приняты. Сборка/byte fixtures в VM не заменяют selected-client LAN proof. До этих receipts общий executor guard не снимается.

Межчатовая сверка не состоялась: send_message_to_thread в «RAZVILKA LAN DNS · 6.1 sol» отклонён auto-review из-за отсутствия подтверждённого прямого разрешения пользователя на передачу внутреннего архитектурного/WIP контекста; сообщение не отправлено. Отчёт основан на read-only source audit и подготовлен для отдельного явного разрешения на отправку.
