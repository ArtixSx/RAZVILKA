# Разработка в чатах 6.1 sol

Пользователь поручил программирование отдельным чатам модели `gpt-6.1-sol`. Чат «RAZVILKA Astra» ведёт координацию, независимую проверку, тестирование и объединение. Это продолжение поставки 03.10.2026, не возврат к прежнему плану.

## Общие правила

Работать только в назначенном Git worktree. `C:/Projects/RAZVILKA` — внешняя папка, не репозиторий. `current` содержит сохранённую работу владельца; `delivery-review` — интеграционная копия координатора. Их не изменять из рабочих чатов. Не выполнять reset/clean, не переносить весь архив поверх дерева. H00/IM уже включены.

Сначала прочитать CHANGES_RU.md, TEST_REPORT_RU.md, REMAINING_AND_AGENTS_RU.md, VALIDATION_RU.md, этот файл и профильный технический отчёт. Первые два отчёта описывают исходную поставку; новые результаты находятся в VALIDATION_RU.md. Актуальные статусы — TASKS.json, а не исторические `not_run` из первоначального задания.

Go: `C:/Projects/RAZVILKA/tools/go/bin/go.exe`, версия 1.26.5. Production go.mod/go.sum не понижать. Node: `C:/Users/Artix/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/bin/node.exe`. Shell: `C:/Program Files/Git/bin/sh.exe`. Запускать адресные тесты своей правки; полный Linux gate, native runtime и аппаратные испытания выполняет координатор. Секреты, локальные журналы и бинарники не включать в коммиты. Не публиковать GitHub и не менять VERSION.

VM, роутер, сетевые пространства и порты принадлежат одному координатору. Рабочие чаты готовят воспроизводимые стенды, но не запускают live-мутации самостоятельно. Изоляция Git не изолирует сеть. Нужное изменение чужого файла оформить как конкретный контракт/запрос в отчёте, а не менять его параллельно.

Все чаты сохраняют Stop, auth, CSRF, TLS, CAS, ownership, recovery fence и rollback. Вход и чтение UI не запускают изменения сети. Неизвестный результат не является разрешением повторить opkg, регистрацию или применение. Сохранять LKG до подтверждённого принятия. `NETWORK_POLICY_EXECUTOR_REQUIRED` остаётся до настоящей реализации общего пути и DNS.

## CORE — интеграция и общий исполнитель

Первый проверяемый результат: законченный путь восстановления D11 на уровне приложения. Сейчас установлен консервативный fence: pending/corrupt component journal запрещает фоновые изменения, допускает явный Stop и чтение состояния. Но matching repair API, принятие реального runtime и завершение обновления не подключены. Поэтому текущий checkpoint не предназначен для установки вместо рабочего приложения.

Реализовать авторизованное восстановление строго по transaction ID и component: актуальные CAS/Stop/SafeMode, отсутствие повторной package-команды после unknown, доверенная проверка отсутствия активных opkg/scripts, независимое подтверждение реального runtime. Исправить routing обновлений неиспользуемых компонентов: обычный Apply теперь намеренно не обновляет installed managed package. Нельзя обойти guard или объявить candidate probe live acceptance. Проверить startup, закрытый браузер, manual/scheduled path, повреждённый journal, повтор HTTP, Stop и смену revision. Восстановление должно быть достижимо через реальный HTTP, а не только прямой вызов Manager.

Дальше: согласовать с VLESS и NET подключение точного Xray checker/профилей WG в app, общую квоту проверок; затем D07 all-except executor. Отсутствие выбранных сервисов и неизвестный сайт используют default, исключения выше overrides. Удаление override не отправляет трафик в DIRECT. Проверить `applyRecordedPolicy`: существующий `route replace default` не даёт права перезаписать чужой default. Удаление уже стало точным, но создание тоже требует доказательства владения.

## VLESS — Xray и резерв

Первый результат: engine-aware сохранение и использование доказательства Xray в NodeStore и библиотечном диспетчере проверок. В базе уже есть `NewExactXrayNodeCheckerSlots`, `EngineID`, `VLESSProfileFromJSON` и native TLS/REALITY тесты. Не писать повторный checker. Путь `xray:<id>` не должен превращаться в Sing-box при сохранении/применении; unsupported до DNS/слота не ухудшает репутацию. Предоставить CORE точный небольшой контракт подключения без самостоятельных правок app/worker.

Дальше D03: настоящий TUN/selected-control путь, endpoint changes, падение sidecar, restart, rollback. Проверка SOCKS не закрывает этот пункт. Затем D10: first-usable без ожидания всего резерва, справедливый refill/cursor32/33, B apply-fail → проверенный rollback → C; approved sources, разнообразие резерва, отсутствие наказания узла за локальный сбой checker. XHTTP — только отдельная проверяемая реализация, никаких потерь параметров.

## NET — WireGuard, AWG и DNS

Первый результат: завершить Generic WG D05 на принятой базе endpoint/profile patch, с точной проверкой маршрута до сервера, владения, revalidation и восстановления. Не добавлять фиктивный TTL к системному resolver. Без реального TTL результат noncacheable; перед изменением сети нужен новый resolve. Изменение DNS/WAN требует свежей проверки кандидата, сохраняя LKG. Профили уже имеют CAS/revision и приватное хранение; подготовить CORE контракт API/выбора профиля. Проверить cleanup чужих маршрутов и правила pin по полному tuple, не по диапазону priority.

Критичный незакрытый сценарий D04: live и candidate с одинаковым peer/key могут менять endpoint сервера и вытеснять Noise-сессию друг друга. Успешный native тест доказывает изоляцию трафика кандидата, но пока не сохранение доступности live после него; fixture явно пересоздаёт live между IPv4/IPv6. Добавить проверку live ПОСЛЕ успешного и неуспешного candidate. Определить запрет проверки уже используемого peer либо проверяемый протокол восстановления; не скрывать нарушение LKG перезапуском только тестовой fixture.

Далее D06 AWG: проверенный CLI/module/kernel/ABI, неподходящий модуль отклоняется до изменения сети. D08 после CORE D07: согласованный DNS, CNAME/min TTL, устройства/сайты исключены из всех owned путей, guest только opt-in, IPv6/UDP и shared CDN. D09: bounded NFQWS2 preferred/only/manual, сохранение пользовательских стратегий и честные уровни проверки media/voice. На общие policy/ownership файлы сначала передать контракт CORE.

## OPS — обновления и WARP/USQUE

Первый результат: аудит и завершение отдельного persistent журнала self-update приложения. Package journal компонентов уже реализован; не переписывать его вторым журналом. Вынести нужную низкоуровневую логику из app в принадлежащий OPS модуль или подготовить контракт CORE. При crash сохранять LKG; unknown не replay; downgrade должен понимать retained receipts. Подготовить реальный воспроизводимый native opkg сценарий и матрицу fault boundaries; исполнитель — координатор. В начале проверить текущий journal на непокрытые границы и сообщить блокирующие ошибки CORE.

После этого D13: различать регистрацию, export, DNS, endpoint; unknown enrollment не запускает новую регистрацию. H2/H3, UDP capability, provenance и TTL источников, read-only offline каталог. Mihomo/HEV не объявлять production без native benefit.

## UI — понятные действия и настоящий HTTP

Первый результат: воспроизводимые сценарии D01 на настоящем локальном приложении с изолированными данными: 401/409/500, быстрые переходы, повторные клики, dirty forms, logout/CSP. Исправить ошибки загрузки/состояний, найденные этими сценариями. Не обходить серверные запреты. D00 уже проверил первый вход, сохранение dirty и focus/inert; не повторять всё без причины.

Затем D12: единый путь «установка → профиль → проверка → применение» на карточке; честные версии и pending/recovery, массовые подключения, раскрываемая AI группа, устранение legacy-дублей с сохранением URL/ID/API. Не показывать зелёный статус по одному процессу или макету. Подготовить метрики запросов/render-cost; ARM64 измеряет координатор. Новые backend endpoints сначала согласовать через отчёт для CORE.

## Приёмка каждой порции

Первый заход каждого чата заканчивается небольшим завершённым коммитом и отчётом в `docs/delivery-2026-10-03/handoffs/<ROLE>_RU.md`: исходный commit, изменённые файлы, результат, команды/RC, ограничения, запросы к другим владельцам. Если найден общий блокер — сначала описать точный контракт и продолжить независимую часть. Следующую крупную вертикаль начинать после проверки координатора, чтобы не накопить несовместимые реализации.

Координатор просматривает diff, запускает адресные регрессии и общий Linux gate; затем native и AArch64 в единственном live-окне. MIPS/MIPSel cross-build не заменяет реальные роутеры; 24/72 часа и аппаратная матрица остаются D14. Итоговый релиз только после фактической приёмки. Отчёт «собирается» не является отчётом «весь план выполнен».
