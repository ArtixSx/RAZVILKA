# Исключения устройств: native NFQWS2 policy и сохранение baseline — 16.10.2026

Это исследование исходников и документации. NDM, роутер, VM и GitHub не изменялись; перечисленные команды не выполнялись. Наличие native policy exclusion не снимает `NETWORK_POLICY_EXECUTOR_REQUIRED` для общего исполнителя сервисов, маршрутов и DNS.

## Что подтверждено

- [Официальный справочник Ultra NC-1812, NDMS 5.0](https://files.support.netcraze.ru/Download/CLI/5.0/RU/cli_manual_nc-1812.pdf), редакция 1.169 от 29.07.2026, прочитан напрямую по HTTP: MAC policy и удаление привязки — стр. 375–376; наследование политики сегмента `conform` — 376–377; создание/описание профиля — 407–408; разрешённые WAN и приоритеты — 410–411; readback policy с mark/table — 620–622. Аналогичный [официальный справочник KeeneticOS 5.0](https://storage.googleapis.com/docs.help.keenetic.com/cli/5.0/en/cli_manual_kn-4110.pdf) подтверждает тот же контракт. Нативное исполнение именно на установленной 5.1 ещё должно быть проверено координатором.
- [Документация Netcraze для NC-1812](https://support.netcraze.ru/ultra/nc-1812/ru/17892-connection-policies.html) объясняет, что профиль выбирает подключение для хоста/сегмента и ограничивает доступные ему DNS-серверы. Это настройка baseline, а не отдельная метка исключения. В документах есть расхождение по пределу профилей: текущий CLI справочник указывает 64, общая статья — 16. Реализация должна проверять возможности устройства.
- [NFQWS2 upstream, закреплённый SHA 077f9af6068cd3380527085ca351b503a2dcf926, common](https://github.com/nfqws/nfqws2-keenetic/blob/077f9af6068cd3380527085ca351b503a2dcf926/etc/init.d/common#L72-L96): `POLICY_NAME` сопоставляется с **описанием**, а не внутренним ID политики; результат mark фиксируется в `.conf.run`. При отсутствии совпадения mark пуст, и policy filter не действует. Простого `POLICY_EXCLUDE=1` без подтверждённого runtime mark недостаточно.
- В [том же исходнике, строки 219–287](https://github.com/nfqws/nfqws2-keenetic/blob/077f9af6068cd3380527085ca351b503a2dcf926/etc/init.d/common#L219-L287) exclude mode возвращает совпавшие по native mark пакеты из собственных NFQWS chains перед очередью. Это исключение из NFQWS2, без принудительного выбора main. Возвратный путь, обе семьи и порядок firmware hooks требуют фактической проверки на целевом образе; текст init не заменяет её.

## Командные шаблоны, не команды для применения

Значения в угловых скобках должны поступать из проверенных фактов; это не выбранные пользователем имена, MAC или интерфейсы. В CLI profile context используются отдельные строки `description` и `permit`.

```text
ip policy <name>
description <label>
permit global <interface>
ip hotspot host <mac> policy <name>
no ip hotspot host <mac> policy
show ip policy [<name>]
```

Создание profile, разрешённые WAN и привязка MAC — отдельные эффекты. Хост должен быть зарегистрирован заранее. Приоритет каждого разрешённого WAN, multipath, IPv6/static routes, разрешения будущих подключений, DNS и `conform` нельзя считать одинаковыми с baseline по одному выбранному WAN. Снятие явного host policy не доказывает восстановления прежнего наследования: нужно сохранить и проверить исходные host/segment/default-policy и `conform`. Разрешение доступа хосту и его расписание — самостоятельные настройки; ради обхода их не менять. Удаление всего host либо общего профиля вместо точного восстановления недопустимо.

## Минимальная безопасная область native policy

1. Первое полезное применение — **существующая политика**, чьи фактические устройства в выбранном домашнем сегменте целиком совпадают с исключаемой группой. Не переименовывать чужую политику и не перепривязывать MAC: проверить уникальность description, её ID/mark и состав; изменить только собственную подтверждённую конфигурацию NFQWS2. Один `POLICY_NAME` выбирает одну policy mark; произвольные подмножества разных baseline-политик таким параметром не выражаются.
2. На стенде координатор увидел пустой результат чтения custom policies. Это позволяет исследовать создание собственной политики для **нынешней default-группы**, но не доказывает эквивалентность автоматически. До реализации нужны точные running host/segment/default bindings и baseline WAN/DNS/IPv4/IPv6 facts, затем сравнение с кандидатом. Нельзя заполнять профиль произвольным ISP или предполагать, что `permit auto` воспроизводит приоритеты и дальнейшие изменения исходной политики.
3. Если исключаемое устройство уже использует VPN/отдельную DNS policy, перенос в новую «исключающую» policy изменяет его baseline. Клонирование всех параметров и отслеживание дальнейших изменений — дополнительный исполнитель, а не малая правка. В первой области такой перенос нужно отклонять.
4. Даже подтверждённое native исключение относится только к NFQWS2. Оно не исключает устройство из Sing-box/Xray/TUN, собственного DNS или AUTO другого engine. UI не должен обозначать это общим «устройство без обхода».

## Что уже есть в RAZVILKA и предпочтительный общий путь

- `internal/engineconfig/nfqws_mode.go:26–56` показывает draft policy и readback `.run`, но это только наблюдение: нет owned NDM CRUD, журнала прежней host policy или атомарного восстановления.
- `internal/dataplane/nfqws_scoped_direct_selector.go:73–85` уже производит отрицательные MAC/source `RETURN` перед всеми положительными selectors **своей** цепочки. `lan_policy_direct_runtime.go:9–17` специально сохраняет firmware mark/RPDB. Это более узкая опора для произвольных device exclusions с сохранением их baseline, чем перепривязка NDM policy. Требуется подключённый первоначальный owner, подтверждённый Home ingress и полное native/readback покрытие; существование compiler не является runtime PASS.
- `internal/dataplane/lan_classifier.go:14–30` прямо отмечает ограниченность прежнего MAC RETURN: он не закрывает другие service selectors. Нужен отрицательный gate у каждого реально используемого consumer, включая DNS, до его захвата. Принудительный `lookup main/254`, очистка чужой маркировки и глобальный ACCEPT подменяют baseline и не подходят.

## Владение и транзакция для возможного NDM backend

Использовать существующий admission/Stop/config CAS и общий execution journal. До первого эффекта сохранить точные before/after образы native profile, отдельных host bindings и related inherited state; отсутствие явной привязки записывать как отсутствие, не как «main». Отдельно закрепить ID/уникальное описание/mark, firmware identity, конфигурацию и `.run` NFQWS2, граф очередей и исходный baseline. Пользовательская policy/description сама по себе не становится собственностью приложения.

Каждый effect: актуальность before → durable intent → один узкий write → независимый readback → durable receipt. Перепривязка допускается только для согласованной области с доказанной baseline-эквивалентностью. Exit 0 CLI и совпавшее имя не являются квитанцией. У NDM нет подтверждённого здесь атомарного compare-and-swap с другими администраторами: внешний дрейф между проверками должен давать отказ/восстановление, а не перезапись.

При rollback восстанавливать только те поля, которые всё ещё совпадают с собственным after. Сначала вернуть собственные host bindings, затем удалить только собственный, неизменённый и более никем не используемый profile. При неожиданном чужом изменении оставить журнал и recovery fence; не импортировать старый полный startup-config поверх новых настроек владельца. Boot recovery проверяет те же receipts. Restart NFQWS2 должен подтвердить новый непустой `.run` mark; исчезновение/переиспользование политики закрывает positive activation. Сохранение конфигурации NDM — отдельный эффект с явной политикой crash/reboot, а не безусловный глобальный save чужих pending edits.

Приёмка координатором: исключённый MAC с IPv4 и новым privacy IPv6; baseline VPN и DNS до/после; другой клиент той же политики; unrelated Guest; уже существующие flows; исчезновение/смена mark; firmware/firewall reload; Stop; crash после каждого эффекта; восстановление исходного `conform`; внешний edit до rollback. До этой приёмки native policy остаётся проектом узкой capability, не закрытием общего executor.
